\section{Linux Kernel Observability}
\label{sec:linux-kernel-observability}

Application logs provide valuable domain-specific information, but only for
actions that the application was designed to record. The kernel provides a
different view. Process creation, credential changes, file access, memory
management and inter-process communication all pass through it, including
operations that span applications or are absent from their logs. Observing
these operations while they occur supplies the evidence needed for runtime
monitoring
\cite{linux_tracing_index,gbadamosi2024ebpf}.

There is no universal kernel event source. Linux instead exposes instrumentation
points at several stages of execution, each with its own timing, context and
dependence on implementation details.

\medskip
\noindent\textbf{System-call observation.}
A system call is the controlled interface through which a user-space process
requests a service from the kernel. It is not itself an instrumentation
mechanism. Monitoring systems commonly observe this boundary through
system-call tracepoints, such as entry and exit events. An entry event exposes
the requested operation and its original arguments, whereas an exit event
exposes the returned result. Correlating the two can distinguish an attempted
operation from one that completed successfully. This view is broad and
process-oriented, but it remains close to the user-space request: one system
call may traverse several internal functions, and its original arguments may
not identify the final kernel object or security decision
\cite{linux_tracepoints,linux_tracing_index}.

\medskip
\noindent\textbf{Tracepoints and raw tracepoints.}
A tracepoint is a static observation point deliberately inserted into the
kernel source by kernel developers. It has a name, belongs to an event
category, and defines the data made available when that point is reached. A
tracepoint remains inactive until a tracing component is attached to it. In an
eBPF-based monitor, this component is an eBPF program loaded from user space
and attached to the selected tracepoint. Each time kernel execution reaches
that point, the kernel invokes the attached program and provides a
tracepoint-specific context containing the declared event fields.

A regular tracepoint supplies a structured context whose layout follows the
format exported for that event. A raw tracepoint uses the same underlying
instrumentation site but exposes its original kernel arguments with less
intermediate transformation. The latter reduces preparation before the eBPF
program runs, at the cost of requiring kernel-aware argument decoding. Both
forms remain limited to the tracepoints provided by the target kernel
\cite{linux_tracepoints,linux_libbpf_program_types}.

\medskip
\noindent\textbf{Kprobes and kretprobes.}
A kprobe is a dynamic probe placed at a selected kernel instruction at run
time. Monitoring tools usually identify that instruction through the symbol of
a kernel function and place the probe at its entry. Unlike a tracepoint, the
observation point does not need to have been prepared explicitly by the kernel
developer. When execution reaches the probed instruction, the kernel
temporarily transfers control to the probing infrastructure, which invokes the
attached eBPF program before normal execution continues. The program receives
a snapshot of the processor-register state. Function arguments are not
presented as a tracepoint-specific event structure; they must be recovered from
the appropriate registers according to the architecture and calling
convention.

A kretprobe observes the corresponding function-return path. It causes an
attached program to run when an invocation of the probed function finishes and
makes the return value available through the register context. A kprobe can
therefore describe the operation requested at function entry, while a
kretprobe can reveal the result produced at function exit. Entry and return
records are separate observations: when both the original arguments and the
result are required in one logical event, the monitoring system must save the
entry data and correlate it with the return observation, commonly by using the
current thread identity.

Kprobes and kretprobes reach functions for which no tracepoint exists, but this
flexibility increases coupling to the kernel implementation. A renamed or
inlined function, a changed signature, a different calling convention or an
unavailable symbol can invalidate either attachment or argument decoding.
Dynamic probes consequently require more target-specific validation than
tracepoints
\cite{linux_kprobes}.

\medskip
\noindent\textbf{Linux Security Module hooks.}
The \gls{lsm} framework inserts security mediation points into kernel
operations involving files, credentials, processes, sockets, and other
protected objects. At these points, registered security modules can inspect an
operation and, for hooks with authorisation semantics, permit or reject it.
An LSM-related function can expose a resolved kernel object at a
security-relevant stage of an operation, rather than only the original
system-call request. Here, the hook and the attached program are distinct: the
LSM hook is the kernel mediation point, while an eBPF LSM program is one means
of attaching logic to a supported hook. If that program type is unavailable or
unsuitable, a monitor may observe the corresponding security function with a
kprobe. Entry-side observation alone does not necessarily reveal the final
outcome; a compatible return-side probe is needed when that result matters
\cite{linux_lsm_development,linux_libbpf_program_types,linux_kprobes}.

\medskip
\noindent\textbf{The role of eBPF.}
eBPF is the execution facility attached to an observation point, not another
name for the point itself. The hook determines when the program runs and which
context it receives. The program can then extract fields, filter an observation,
update a map or submit an event to user space. Thus, ``tracepoint'', ``kprobe'',
``LSM hook'' and ``eBPF program'' refer to different parts of the monitoring
path \cite{linux2024ebpfuserspaceapi,linux_libbpf_program_types}.

Choosing among these sources depends on the evidence required, the facilities
available on the target kernel and the acceptable coupling to kernel internals.
In practice, a monitor often combines them because no single source exposes
every stage of an operation
\cite{linux_tracing_index,her2025ebpfsecuritytools}.

\section{eBPF Fundamentals}
\label{sec:ebpf-fundamentals}

\gls{ebpf} allows programs loaded from user space to run inside the Linux
kernel when a selected event occurs. Each program is constrained by its type
and attachment point, and the kernel verifies it before execution
\cite{rfc9669_bpf_isa,linux2024ebpfuserspaceapi}.

This mechanism extends kernel behaviour without requiring a source change or a
traditional module for every use case. Programs can be loaded, replaced and
specialised for observability, performance analysis, networking or security.
Their value lies in placing purpose-built logic close to the relevant kernel
operation while retaining a defined execution model and a verification step
\cite{gbadamosi2024ebpf,linux2026ebpfverifier}.

\subsection{Execution Model, Verifier and JIT Compilation}
\label{subsec:ebpf-execution-verifier-jit}

An eBPF program is compiled into instructions for the \gls{bpf} virtual machine and
submitted to the kernel through the \gls{bpf} user-space interface. The instruction
set defines general-purpose registers, a bounded stack, arithmetic and branch
instructions, memory operations, and calls to kernel-provided functions. The
program does not execute as unrestricted kernel code: its available context,
memory accesses, and callable functions depend on its program type
\cite{rfc9669_bpf_isa,linux_bpf_helpers}.

Code running in the kernel can affect the stability and security of the whole
system, even when it was loaded from user space. The eBPF verifier is the kernel
component that decides whether a submitted program may run. It analyses the
program during loading and rejects it if the required safety conditions cannot
be established.

The verifier performs a path-sensitive static analysis of the program's control
flow. It follows the possible execution paths while tracking the state of
registers and stack locations, distinguishing scalar values from different
classes of pointers, checking memory bounds and alignment, and validating the
arguments supplied to helper functions. Paths that may access invalid memory,
use uninitialised values, or leave kernel-managed resources unreleased are
rejected. To avoid analysing equivalent situations repeatedly, the verifier
uses state pruning: when a previously accepted verifier state already covers a
new state reached at the same instruction, the redundant path does not need to
be explored again \cite{linux2026ebpfverifier,gershuni2019prevail}.

Verification establishes a set of safety properties, not the correctness of
the monitoring logic. An accepted program may still read the wrong field, emit
an incomplete event or disagree with its user-space decoder. Conversely, valid
source-level logic may be rejected when a particular kernel cannot prove its
safety. Verifier behaviour is thus both a security boundary and a compatibility
constraint
\cite{linux2026ebpfverifier,linux_bpf_design_qa}.

After verification, an architecture-specific \gls{jit} compiler may translate
the eBPF bytecode into native instructions. The kernel can then execute that
code directly whenever the program is invoked instead of interpreting each
eBPF instruction in turn
\cite{linux_bpf_execution_modes,linux_bpf_jit_sysctl}.

\subsection{Object Files, Loading and Attachment Lifecycle}
\label{subsec:ebpf-object-loading-attachment}

The source code of an eBPF application is not passed directly to the kernel.
Clang first compiles it into \gls{bpf} instructions stored in an \gls{elf} object.
The object groups programs into named sections and also carries map
declarations, licence information, symbols, BTF metadata and relocation
records. Section names help a loader infer the program type and expected
attachment family, while BTF and relocation information describe references
that must be adapted before the program can be accepted by the target kernel
\cite{linux_libbpf_program_types,linux_btf,linux_bpf_llvm_relocations}.

A user-space loader, commonly built on \texttt{libbpf}, opens this object and
turns its declarations into kernel objects. It creates or reuses maps, resolves
relocations and submits each enabled program through the \gls{bpf} system-call
interface, after which the kernel verifier examines every program. A valid
object can still fail to load if the host lacks a required program type, helper
or symbol, or if its verifier handles the program differently
\cite{linux_bpf_syscall,linux_libbpf_overview,linux2026ebpfverifier}.

Loading and attachment are separate operations. A successfully loaded program
exists as a kernel object referenced from user space, but it does not run until
it is connected to a compatible hook. Depending on the program and hook type,
this connection may be represented by a \gls{bpf} link or by tracing-specific
infrastructure such as a perf event. The attachment owns the relationship
between the program and its trigger and can be removed independently from the
program itself. This separation allows one object file to contain several
programs, only a subset of which may be loaded and attached for a particular
monitoring configuration
\cite{linux_libbpf_program_types,linux_libbpf_overview}.

Programs, maps and links are configured and released through file descriptors.
Closing the final reference normally allows the kernel object to be destroyed;
pinning instead assigns it a persistent name in the \gls{bpf} filesystem, so it
can outlive the process that created it. Cleanup is therefore part of runtime
ownership rather than a minor loader concern: stale attachments and pinned
objects may continue to consume kernel resources
\cite{linux_bpf_syscall,linux_libbpf_overview}.

\subsection{Hook Selection and Event Semantics}
\label{subsec:ebpf-hook-selection-event-semantics}

An eBPF program type defines the execution contract enforced by the kernel,
including the expected context, available helpers, and permitted return
semantics. The hook instead identifies the event or kernel execution point
that triggers the program, while the attachment mechanism binds the loaded
program to a compatible hook. These concepts are related, but they are not
interchangeable
\cite{linux_libbpf_program_types,linux_bpf_helpers}.

The selected observation point determines not only when an eBPF program runs,
but also the meaning of the resulting event. A system-call entry hook captures
the operation requested by a process and its original arguments. A later
tracepoint, dynamic probe, or LSM-related hook may expose kernel-resolved
objects or the security mediation stage of the operation. An exit or
return-side observation can instead reveal whether the operation completed
successfully
\cite{linux_tracepoints,linux_kprobes,linux_lsm_development}.

These observations belong to different stages of one kernel execution path.
No single hook necessarily exposes the original request, resolved kernel
context and final result, so a monitor may need to correlate records from
several sources through process identity and time.

Compatibility also affects hook selection. Tracepoints provide structured
interfaces where the target kernel exports a suitable event. Dynamic probes
allow more flexible placement but depend more heavily on symbols, signatures
and calling conventions. The required security evidence must be balanced
against the capabilities and stability of the deployment kernel
\cite{linux_tracepoints,linux_kprobes,redhat2025backporting}.

\subsection{Maps, Helpers and Kernel-to-Userspace Transport}
\label{subsec:ebpf-maps-helpers-transport}

An eBPF invocation is constrained and usually short-lived, whereas monitoring
often needs state to survive between invocations and eventually reach user
space. Maps provide kernel-managed storage, helpers expose selected kernel
services and event buffers carry records to the user-space runtime
\cite{linux_bpf_maps,linux_bpf_helpers,linux_perf_ring_buffer,
linux_bpf_ringbuf}.

Maps are typed kernel objects that allow eBPF programs to preserve state across
invocations and exchange data with user space. Each map type defines its own
access and concurrency semantics, while its structure and capacity are
established at creation time. By moving persistent configuration and temporary
state outside the constrained \gls{bpf} stack, maps extend the information that a
program can retain between executions. Accesses performed by eBPF code remain
subject to verifier validation and to the rules imposed by the selected map
type \cite{linux_bpf_maps,linux_bpf_syscall}.

Map organisation reflects how the stored state is owned and accessed. Arrays
offer fixed indexed storage for configuration or bounded workspaces. Hash maps
use dynamic keys and can retain entry arguments until a later hook completes
an operation. Per-CPU maps give each processor an independent value, reducing
contention on frequently updated state or counters, although user space must
combine those values to obtain a system-wide result. A shared map instead
requires explicit consideration of concurrent access and update atomicity
\cite{linux_bpf_maps}.

The same maps also carry configuration in the opposite direction. User space
can populate selection or lookup data before monitoring starts and update
supported values while programs remain loaded. Kernel programs can consult
this state without encoding every operational choice in their instructions,
leaving interpretation and configuration under user-space control
\cite{linux_bpf_maps,linux_bpf_syscall}.

Helpers expose selected kernel services without granting programs unrestricted
access to kernel internals. The verifier checks their arguments and the data
passed to them. Availability depends on both program type and target-kernel
capabilities; a helper documented for eBPF in general is not necessarily valid
in every context. For the Rocky Linux target used here, helper support must be
checked against the deployed kernel rather than inferred from current upstream
documentation \cite{linux_bpf_helpers,linux2026ebpfverifier}.

Event transport carries records produced during eBPF execution to user space,
where they can be decoded and processed without extending the work performed
inside the kernel. The \gls{bpf} ring buffer provides a shared
multi-producer, single-consumer channel designed to use buffer capacity across
CPUs and preserve the order in which records are reserved. Perf-event
transport follows a different model: a
\texttt{BPF\_MAP\_TYPE\_PERF\_EVENT\_ARRAY} directs records to per-CPU perf
ring buffers, which are consumed independently and can report lost events.

Both mechanisms have finite capacity. If kernel-side producers outpace the
consumer, submission may fail or records may be lost. Transport is therefore
part of the monitor's correctness model rather than a transparent channel
\cite{linux_bpf_ringbuf,linux_perf_ring_buffer,linux_bpf_helpers}.

\subsection{BTF and CO-RE Portability}
\label{subsec:ebpf-btf-core}

Kernel data structures can change layout between versions and distribution
builds. An eBPF program compiled against one set of headers may therefore use
field offsets or types that do not match the target. BTF and CO-RE preserve the
meaning of compatible accesses by describing types and relocating them for the
deployed kernel.

\gls{btf} is a compact representation of types and related metadata understood
by the kernel and \gls{bpf} tooling. It can describe C types and strings as well
as function, line and relocation information. When the kernel exports BTF,
loaders and debugging tools need not rely solely on headers copied from one
build
\cite{linux_btf}.

\gls{core} uses BTF information to adapt an eBPF program to the kernel on
which it is loaded. During compilation, Clang stores relocation records that
describe the kernel types and fields accessed by the program. At load time,
\texttt{libbpf} reads the BTF information of the running kernel and updates the
relevant eBPF instructions so that they use the actual layout of those
structures. The same object can consequently remain usable when a compatible
kernel places a field at a different offset, without being recompiled on the
monitored system
\cite{linux_btf,linux_bpf_llvm_relocations,linux_libbpf_overview}.

For this prototype, CO-RE adapts accesses to the layouts exposed by Rocky Linux
8.10 with kernel
\texttt{4.18.0-553.137.1.el8\_10.x86\_64}. However, CO-RE only adapts
compatible differences in type and data-structure layout. It cannot make a
missing hook, helper, program type, or attachment mechanism available, and it
does not ensure that the target verifier will accept the program. These
capabilities still need to be checked on the deployed kernel, especially
on enterprise distributions whose backports can differ from what the upstream
version number suggests
\cite{linux_bpf_design_qa,redhat2025backporting}.

\section{Related eBPF Runtime Security Tools}
\label{sec:related-runtime-security-tools}

Runtime security tools differ in where they select events, interpret evidence
and act on a match. The comparison here uses Tracee, Falco and Tetragon to mark
three relevant positions in that design space: an event-oriented pipeline, a
declarative alerting engine and a hook-centred system with optional response
\cite{her2025ebpfsecuritytools}.

\subsection{Tracee}
\label{subsec:tracee}

Tracee is the closest architectural reference for the proposed system because
it separates eBPF collection from event processing, policy selection,
detection and output. In the pipeline shown in
Figure~\ref{fig:tracee-architecture}, kernel and networking hooks produce
observations that become events before higher-level analysis and delivery
\cite{aquasecurity_tracee,aquasecurity_tracee_architecture,
her2025ebpfsecuritytools}.

The figure uses the signature-oriented terminology of the release in which it
was published. Current documentation keeps the same broad pipeline but favours
detectors for new threat detections and derived events. A common event
abstraction represents both hook observations and detector results, keeping
policies, detectors and output independent of physical attachment details
\cite{aquasecurity_tracee_events,aquasecurity_tracee_custom_events,
aquasecurity_tracee_detectors}.

Tracee policies combine workload scope with rules that select events and may
constrain their data. Policy rules can also select detectors through threat
metadata. Detectors consume declared inputs, may retain state and produce
derived events with provenance. Monitoring scope and security interpretation
are thus separate, without forming a general-purpose temporal language
\cite{aquasecurity_tracee_policies,
aquasecurity_tracee_policy_rules,aquasecurity_tracee_detector_api}.

Output remains independent from event production and detection, supporting
human-readable and structured destinations together with additional process and
container context. Tracee also provides routing and forensic capabilities that
extend beyond the prototype developed in this thesis
\cite{aquasecurity_tracee_output,aquasecurity_tracee_overview}.

Tracee faces portability and trust boundaries as well. BTF, symbols, backports
and individual hooks must be verified on enterprise kernels even when the
general kernel line is supported. It also assumes that the kernel is trustworthy
when monitoring starts; a kernel-level adversary may interfere with observation
\cite{aquasecurity_tracee_requirements,
aquasecurity_tracee_security_model}.

The proposed system adopts this separation between collection, policy
selection, detection and output, but not Tracee's breadth. Its scope is a
selected process and host-security event domain on one Rocky Linux environment,
using deterministic point conditions and bounded local sequences. The
comparison establishes prior art and architectural influence, not functional
equivalence.

\subsection{Other Relevant eBPF Security Tools}
\label{subsec:other-ebpf-security-tools}

Falco is a runtime security engine organised around rules evaluated over event
sources. Kernel system-call activity can be captured through its driver
architecture, while plugins provide additional sources. Falco rules are
declarative \gls{yaml} objects containing a condition, output description, priority,
and optional reusable lists, macros, tags, and exceptions. A matching rule
produces an alert that can be routed to configured outputs
\cite{falcosecurity_falco_kernel_architecture,falcosecurity_falco_rules,
falcosecurity_falco_outputs}.

Falco shows how readable rules, reusable expressions and explicit exceptions
can support an alert-oriented interface. It also maintains process and
container context for event enrichment. Its documented conditions evaluate an
incoming event, however, and separate sources are processed independently; the
core rule language is not presented as a temporal sequence language across
heterogeneous sources \cite{falcosecurity_falco_event_sources,
falcosecurity_falco_rule_conditions}.

Tetragon combines eBPF-based observability with optional runtime enforcement.
Its tracing policies specify kernel hooks, captured arguments or return values,
and selectors that can match process, namespace, capability, workload, and
argument attributes. Supported actions can include emitting an event,
delivering a signal, or overriding a return value where the hook and kernel
support that operation \cite{cilium_tetragon_tracing_policy,
cilium_tetragon_selectors,cilium_tetragon_enforcement}.

Tetragon places more selection and potential response near the hook than a
design centred on user-space detectors. It preserves
process-lifecycle context and emits structured events through its own
interfaces, but its documented tracing-policy model is principally
hook-centred rather than a general language for arbitrary temporal sequences
\cite{cilium_tetragon_events,cilium_tetragon_tracing_policy}. Its current
installation requirements also illustrate the dependence of advanced eBPF
functionality on kernel capabilities and BTF availability
\cite{cilium_tetragon_requirements}.

\section{Positioning of the Proposed Work}
\label{sec:positioning-proposed-work}

The proposed work covers a bounded part of Linux runtime security: process and
host-security monitoring on Rocky Linux 8.10 with kernel
\texttt{4.18.0-553.137.1.el8\_10.x86\_64}. Because this environment combines
an older upstream kernel base with vendor backports, compatibility cannot be
inferred from the version number alone. The available hooks, helpers, data
layouts, and verifier behaviour must instead be established on the deployed
system
\cite{redhat2025backporting}.

Within this environment, eBPF programs collect selected observations and send
them to a Go runtime through an explicit event contract. The records form a
typed event stream in user space. Chapter~3 explains how policies scope that
stream and detectors interpret it.

The prototype does not claim these mechanisms as novel in isolation. Tracee establishes
the event-oriented separation of collection, policy selection, detection and
output; Falco provides a mature example of declarative event rules and alerts;
and Tetragon illustrates a more kernel-centred design with enforcement support
\cite{aquasecurity_tracee_policies,aquasecurity_tracee_detectors,
falcosecurity_falco_rules,cilium_tetragon_tracing_policy}.

This thesis integrates those established ideas in a compact prototype tailored
to the selected enterprise kernel. The work concentrates on compatibility,
complementary observation points and the contract that turns kernel records
into typed user-space events. Chapter~3 develops the corresponding system
design.
