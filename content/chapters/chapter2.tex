\section{Linux Kernel Observability}
\label{sec:linux-kernel-observability}

Runtime monitoring requires evidence about operations while they are being
executed. Application logs describe domain-specific actions, but their content
depends on what each application chooses to record. The Linux kernel offers a
complementary observation layer because it mediates process creation,
credential changes, file access, memory management, inter-process
communication, and other security-relevant operations. Kernel observability is
therefore useful when behaviour crosses application boundaries or is not
represented consistently in application logs
\cite{linux_tracing_index,gbadamosi2024ebpf}.

Linux does not expose all runtime activity through one universal event source.
Instead, it provides instrumentation points at different layers of kernel
execution. Each mechanism determines when monitoring code runs, which context
is available, and how strongly the observation depends on kernel internals.

\medskip
\noindent\textbf{System-call observation.}
A system call is the controlled interface through which a user-space process
requests a service from the kernel. It is not itself an instrumentation
mechanism. Monitoring systems commonly observe this boundary through
system-call tracepoints, such as entry and exit events. An entry event exposes
the requested operation and its original arguments, whereas an exit event
exposes the returned result. Correlating the two can distinguish an attempted
operation from one that completed successfully. This view is broad and
process-oriented, but it remains close to the user-space request: one system
call may traverse several internal functions, and its original arguments may
not identify the final kernel object or security decision
\cite{linux_tracepoints,linux_tracing_index}.

\medskip
\noindent\textbf{Tracepoints and raw tracepoints.}
A tracepoint is a static observation point deliberately inserted into the
kernel source by kernel developers. It has a name, belongs to an event
category, and defines the data made available when that point is reached. A
tracepoint remains inactive until a tracing component is attached to it. In an
eBPF-based monitor, this component is an eBPF program loaded from user space
and attached to the selected tracepoint. Each time kernel execution reaches
that point, the kernel invokes the attached program and provides a
tracepoint-specific context containing the declared event fields.

A regular tracepoint gives the eBPF program a structured event context whose
layout follows the format exported for that tracepoint. A raw tracepoint refers
to the same underlying kernel instrumentation site, but exposes the original
arguments passed by the kernel to that site with less intermediate
transformation. This reduces preparation performed before the eBPF program
runs, while requiring the program to know how each raw argument must be
interpreted. Tracepoints are therefore explicit and comparatively stable
observation points, whereas raw tracepoints trade some of that abstraction for
more direct access to the underlying arguments. Both mechanisms are limited to
the tracepoints actually provided by the target kernel
\cite{linux_tracepoints,linux_libbpf_program_types}.

\medskip
\noindent\textbf{Kprobes and kretprobes.}
A kprobe is a dynamic probe placed at a selected kernel instruction at run
time. Monitoring tools usually identify that instruction through the symbol of
a kernel function and place the probe at its entry. Unlike a tracepoint, the
observation point does not need to have been prepared explicitly by the kernel
developer. When execution reaches the probed instruction, the kernel
temporarily transfers control to the probing infrastructure, which invokes the
attached eBPF program before normal execution continues. The program receives
a snapshot of the processor-register state. Function arguments are not
presented as a tracepoint-specific event structure; they must be recovered from
the appropriate registers according to the architecture and calling
convention.

A kretprobe observes the corresponding function-return path. It causes an
attached program to run when an invocation of the probed function finishes and
makes the return value available through the register context. A kprobe can
therefore describe the operation requested at function entry, while a
kretprobe can reveal the result produced at function exit. Entry and return
records are separate observations: when both the original arguments and the
result are required in one logical event, the monitoring system must save the
entry data and correlate it with the return observation, commonly by using the
current thread identity.

Kprobes and kretprobes provide access to functions for which no tracepoint
exists, but this flexibility increases coupling to kernel implementation
details. A renamed or inlined function, a changed signature, a different
calling convention, or an unavailable symbol can invalidate the attachment or
the argument-decoding logic. They are therefore powerful dynamic mechanisms,
but generally require more target-specific validation than tracepoints
\cite{linux_kprobes}.

\medskip
\noindent\textbf{Linux Security Module hooks.}
The \gls{lsm} framework inserts security mediation points into kernel
operations involving files, credentials, processes, sockets, and other
protected objects. At these points, registered security modules can inspect an
operation and, for hooks with authorisation semantics, permit or reject it.
Observing an LSM-related function can therefore expose a resolved kernel object
and the security-relevant stage of an operation, rather than only the original
system-call request. Two concepts should not be confused: an LSM hook is the
kernel mediation point, while an eBPF LSM program is one possible program type
for attaching logic to supported hooks. On kernels where that program type is
unavailable or unsuitable, monitoring tools may instead observe the
corresponding security function through a kprobe. An entry-side observation
still does not necessarily reveal the final outcome; when the result matters,
it must be obtained from a compatible return-side observation
\cite{linux_lsm_development,linux_libbpf_program_types,linux_kprobes}.

\medskip
\noindent\textbf{The role of eBPF.}
eBPF is the execution facility attached to an observation point, not a
replacement name for the observation point itself. The selected hook causes an
eBPF program to run and determines the context received by that program. The
program can then extract selected fields, apply an early filter, update maps,
or submit an event to user space. Consequently, ``tracepoint'', ``kprobe'',
``LSM hook'', and ``eBPF program'' describe different parts of the same
monitoring path \cite{linux2024ebpfuserspaceapi,linux_libbpf_program_types}.

These mechanisms are complementary. System-call observations describe requests
and results at the user--kernel boundary; general tracepoints expose
kernel-defined events; kprobes and kretprobes provide dynamic access to
function entry and return; and LSM-related hooks expose security mediation
points. A runtime monitor combines them according to the required semantics,
available target-kernel features, and acceptable coupling to kernel internals.
The engineering objective is to select observation points that provide sufficient and
reliable evidence for the intended security analysis
\cite{linux_tracing_index,her2025ebpfsecuritytools}.

\section{eBPF Fundamentals}
\label{sec:ebpf-fundamentals}

\gls{ebpf} is a modern technology that makes the Linux kernel programmable at
runtime. It allows small programs to be loaded from user space and executed
inside the kernel when a selected event occurs. Before execution, the kernel
verifies that each program respects the safety constraints associated with its
program type and intended attachment point
\cite{rfc9669_bpf_isa,linux2024ebpfuserspaceapi}.

This approach makes it possible to extend kernel behaviour without modifying
the kernel source or developing a traditional kernel module for each new
functionality. eBPF programs can be loaded, replaced, and specialised for
different purposes, including system observability, performance analysis,
network processing, and security. Its principal benefit is therefore
controlled programmability: functionality can be introduced close to the
kernel operations of interest while remaining subject to verification and
well-defined execution constraints
\cite{gbadamosi2024ebpf,linux2026ebpfverifier}.

\subsection{Execution Model, Verifier and JIT Compilation}
\label{subsec:ebpf-execution-verifier-jit}

An eBPF program is compiled into instructions for the BPF virtual machine and
submitted to the kernel through the BPF user-space interface. The instruction
set defines general-purpose registers, a bounded stack, arithmetic and branch
instructions, memory operations, and calls to kernel-provided functions. The
program does not execute as unrestricted kernel code: its available context,
memory accesses, and callable functions depend on its program type
\cite{rfc9669_bpf_isa,linux_bpf_helpers}.

Because the programs described above are loaded from user space but execute
inside the kernel, they cannot be allowed to run without first establishing
that they respect the kernel's safety constraints. An unsafe memory access or
an invalid operation in this context could affect the stability and security of
the entire system. Linux addresses this requirement through the eBPF verifier,
the kernel component responsible for deciding whether a submitted program can
be accepted for execution. Rather than trusting the program, the verifier
analyses it during the loading process and before permitting its execution; a
program that does not satisfy the required safety conditions is rejected and
never executed.

The verifier performs a path-sensitive static analysis of the program's control
flow. It follows the possible execution paths while tracking the state of
registers and stack locations, distinguishing scalar values from different
classes of pointers, checking memory bounds and alignment, and validating the
arguments supplied to helper functions. Paths that may access invalid memory,
use uninitialised values, or leave kernel-managed resources unreleased are
rejected. To avoid analysing equivalent situations repeatedly, the verifier
uses state pruning: when a previously accepted verifier state already covers a
new state reached at the same instruction, the redundant path does not need to
be explored again \cite{linux2026ebpfverifier,gershuni2019prevail}.

Verification is a necessary safety gate, not a proof that a program implements
the intended monitoring semantics. A verifier-accepted program may still read
the wrong field, emit an incomplete event, or encode data inconsistently with
its user-space decoder. Conversely, semantically reasonable source code may be
rejected because the verifier cannot establish the required safety properties
for a particular kernel. Verifier behaviour is therefore both a security
mechanism and a practical compatibility constraint
\cite{linux2026ebpfverifier,linux_bpf_design_qa}.

Once the verifier accepts a program, the kernel may pass its eBPF instructions
to an architecture-specific \gls{jit} compiler. The compiler translates the
verified eBPF bytecode into native machine instructions for the host
architecture. The resulting native code can then be executed directly whenever
the program is invoked, avoiding the overhead of processing the eBPF
instructions individually at each execution
\cite{linux_bpf_execution_modes,linux_bpf_jit_sysctl}.

JIT compilation does not alter the functionality authorised by the verifier.
The translation is performed only after verification and preserves the
semantics of the accepted eBPF program. Its availability depends on the host
architecture, the kernel build configuration, and the runtime JIT settings.

This completes the basic eBPF execution path considered here. A program is
compiled into eBPF instructions, submitted to the kernel, analysed by the
verifier and, if accepted, translated into native machine code and executed
whenever its associated hook or execution context is invoked
\cite{gbadamosi2024ebpf}.

\subsection{Object Files, Loading and Attachment Lifecycle}
\label{subsec:ebpf-object-loading-attachment}

The source code of an eBPF application is not passed directly to the kernel.
Clang first compiles it into BPF instructions stored in an \gls{elf} object.
The object groups programs into named sections and also carries map
declarations, licence information, symbols, BTF metadata and relocation
records. Section names help a loader infer the program type and expected
attachment family, while BTF and relocation information describe references
that must be adapted before the program can be accepted by the target kernel
\cite{linux_libbpf_program_types,linux_btf,linux_bpf_llvm_relocations}.

A user-space loader, commonly built on \texttt{libbpf}, opens this object and
turns its declarations into kernel objects. It creates or reuses the required
maps, resolves relocations and submits each enabled program through the BPF
system-call interface. The kernel then applies the verifier to every submitted
program. Loading is therefore an active compatibility boundary: a syntactically
valid object may still fail because a required program type, helper, kernel
symbol or verifier behaviour is unavailable on the host
\cite{linux_bpf_syscall,linux_libbpf_overview,linux2026ebpfverifier}.

Loading and attachment are separate operations. A successfully loaded program
exists as a kernel object referenced from user space, but it does not run until
it is connected to a compatible hook. Depending on the program and hook type,
this connection may be represented by a BPF link or by tracing-specific
infrastructure such as a perf event. The attachment owns the relationship
between the program and its trigger and can be removed independently from the
program itself. This separation allows one object file to contain several
programs, only a subset of which may be loaded and attached for a particular
monitoring configuration
\cite{linux_libbpf_program_types,linux_libbpf_overview}.

File descriptors provide the user-space references through which programs,
maps and links are configured and eventually released. Closing the final
reference normally permits the corresponding kernel object to be destroyed,
whereas pinning can give an object a persistent name in the BPF filesystem and
allow it to outlive the process that created it. Runtime ownership and cleanup
are consequently part of the operational model, not merely loader
housekeeping: stale attachments or pinned objects may continue consuming
kernel resources after the original control path has ended
\cite{linux_bpf_syscall,linux_libbpf_overview}.

\subsection{Hook Selection and Event Semantics}
\label{subsec:ebpf-hook-selection-event-semantics}

An eBPF program type defines the execution contract enforced by the kernel,
including the expected context, available helpers, and permitted return
semantics. The hook instead identifies the event or kernel execution point
that triggers the program, while the attachment mechanism binds the loaded
program to a compatible hook. These concepts are related, but they are not
interchangeable
\cite{linux_libbpf_program_types,linux_bpf_helpers}.

The selected observation point determines not only when an eBPF program runs,
but also the meaning of the resulting event. A system-call entry hook captures
the operation requested by a process and its original arguments. A later
tracepoint, dynamic probe, or LSM-related hook may expose kernel-resolved
objects or the security mediation stage of the operation. An exit or
return-side observation can instead reveal whether the operation completed
successfully
\cite{linux_tracepoints,linux_kprobes,linux_lsm_development}.

These observations represent different stages of the same kernel execution
path and should therefore be considered complementary rather than
interchangeable. No single hook necessarily exposes the original request,
the resolved kernel context, and the final result. A runtime monitor may
consequently combine multiple event sources and correlate their records
through process identity and temporal proximity.

Hook selection also introduces a compatibility trade-off. Explicit
tracepoints provide structured interfaces when the target kernel exports a
suitable event, whereas dynamic probes offer broader placement flexibility
but depend more strongly on kernel symbols, function signatures, and calling
conventions. The appropriate observation point must therefore balance the
required security semantics with the capabilities and stability of the
deployment kernel
\cite{linux_tracepoints,linux_kprobes,redhat2025backporting}.

\subsection{Maps, Helpers and Kernel-to-Userspace Transport}
\label{subsec:ebpf-maps-helpers-transport}

The execution of an eBPF program is intentionally constrained and usually
short-lived. Runtime monitoring, however, requires information to persist
beyond a single invocation and eventually reach user space, where more complex
processing can be performed. Linux supports this interaction through
kernel-managed state and a controlled communication path between eBPF programs
and the user-space runtime. Maps, helpers, and event buffers form the main
building blocks of this path
\cite{linux_bpf_maps,linux_bpf_helpers,linux_perf_ring_buffer,
linux_bpf_ringbuf}.

Maps are typed kernel objects that allow eBPF programs to preserve state across
invocations and exchange data with user space. Each map type defines its own
access and concurrency semantics, while its structure and capacity are
established at creation time. By moving persistent configuration and temporary
state outside the constrained BPF stack, maps extend the information that a
program can retain between executions. Accesses performed by eBPF code remain
subject to verifier validation and to the rules imposed by the selected map
type \cite{linux_bpf_maps,linux_bpf_syscall}.

Different map organisations serve different ownership patterns. Array maps
provide fixed indexed storage and are suitable for configuration or bounded
workspaces. Hash maps associate dynamically selected keys with values and can
retain state such as entry arguments until a later hook completes an
operation. Per-CPU variants allocate an independent value for each processor,
reducing contention when programs update temporary state or counters on a hot
path. Their values must, however, be combined explicitly when user space needs
a system-wide result. Shared maps instead require the application to consider
concurrent access from several CPUs and the atomicity of each update
\cite{linux_bpf_maps}.

Maps also form a control channel in the opposite direction. User space can
populate configuration, selection or lookup data before monitoring begins and
update supported values while programs are loaded. An eBPF program can then
consult that state without embedding every operational choice in its
instructions. This division is central to configurable monitoring: the kernel
program remains bounded, while user space controls which state it exposes and
how map contents are interpreted
\cite{linux_bpf_maps,linux_bpf_syscall}.

Helpers are kernel-provided functions that extend what an eBPF program can do
without granting unrestricted access to kernel internals. They expose selected
services through a controlled interface, allowing the kernel to validate how
those services are invoked and what data is passed to them. The set of
available helpers is determined by the program type and by the capabilities of
the target kernel, so support documented for eBPF in general does not imply
that the same helper can be used in every execution context. This constraint is
particularly relevant to this work, which targets Rocky Linux 8.10 with kernel
\texttt{4.18.0-553.109.1.el8\_10.x86\_64}: helper selection must therefore be
validated against the capabilities of the deployed kernel and the program type
used by each probe, rather than inferred solely from current upstream
documentation \cite{linux_bpf_helpers,linux2026ebpfverifier}.

Event transport carries records produced during eBPF execution to user space,
where they can be decoded and processed without extending the work performed
inside the kernel. The BPF ring buffer provides a shared
multi-producer, single-consumer channel designed to use buffer capacity across
CPUs and preserve the order in which records are reserved. Perf-event
transport follows a different model: a
\texttt{BPF\_MAP\_TYPE\_PERF\_EVENT\_ARRAY} directs records to per-CPU perf
ring buffers, which are consumed independently and can report lost events.

Both mechanisms rely on finite buffer capacity. When kernel-side producers
generate data faster than user space can consume it, a submission may fail or
a record may be lost. Event transport must therefore be treated as part of the
monitor's correctness model rather than as a transparent delivery channel
\cite{linux_bpf_ringbuf,linux_perf_ring_buffer,linux_bpf_helpers}.

\subsection{BTF and CO-RE Portability}
\label{subsec:ebpf-btf-core}

An eBPF program often interacts with kernel data structures whose layout may
change across kernel versions and distribution builds. A program compiled
against one specific set of kernel headers may therefore rely on field offsets
or type definitions that do not match the target system. Portability requires
a way to preserve the meaning of those accesses while adapting them to the
types exposed by the deployed kernel. BTF and CO-RE provide the metadata and
relocation mechanisms used to address this problem.

\gls{btf} represents types and related metadata in a compact format understood
by the kernel and BPF tooling. BTF may describe C types and strings and can also
carry function, line, and relocation information. When kernel BTF is available,
loaders and debugging tools can reason about kernel data structures without
depending solely on a set of headers copied from one kernel build
\cite{linux_btf}.

\gls{core} uses BTF information to adapt an eBPF program to the kernel on
which it is loaded. During compilation, Clang stores relocation records that
describe the kernel types and fields accessed by the program. At load time,
\texttt{libbpf} reads the BTF information of the running kernel and updates the
relevant eBPF instructions so that they use the actual layout of those
structures. As a result, the same compiled object can continue to work when
compatible kernel versions place a field at a different offset, without
requiring the program to be recompiled on the monitored system
\cite{linux_btf,linux_bpf_llvm_relocations,linux_libbpf_overview}.

In this thesis, this mechanism helps the eBPF programs access kernel structures
according to the layout exposed by Rocky Linux 8.10 with kernel
\texttt{4.18.0-553.109.1.el8\_10.x86\_64}. However, CO-RE only adapts
compatible differences in type and data-structure layout. It cannot make a
missing hook, helper, program type, or attachment mechanism available, and it
does not ensure that the target verifier will accept the program. These
capabilities must therefore be checked directly on the deployed kernel. This
is especially important for enterprise distributions, where backported
features may make the effective kernel capabilities differ from those suggested
by the upstream version number alone
\cite{linux_bpf_design_qa,redhat2025backporting}.

\section{Related eBPF Runtime Security Tools}
\label{sec:related-runtime-security-tools}

Existing eBPF-based runtime security tools share the objective of interpreting
kernel-derived activity, but they place event selection, detection, and
response at different points of the monitoring pipeline. Tracee, Falco, and
Tetragon are considered here because they represent three relevant design
approaches for positioning the proposed system. Tracee provides the closest
architectural reference through its separation of event collection, policies,
detectors, and output. Falco centres its design on declarative rules and alert
generation, while Tetragon moves filtering and optional response closer to the
monitored kernel hook \cite{her2025ebpfsecuritytools}.

\subsection{Tracee}
\label{subsec:tracee}

Among the systems considered in this section, Tracee is the closest reference
for the tool developed in this work. Both systems separate kernel-level event
collection from the analysis performed in user space. This shared structure,
rather than a direct feature-by-feature correspondence, makes Tracee the main
architectural reference for the proposed system
\cite{aquasecurity_tracee,aquasecurity_tracee_overview,
her2025ebpfsecuritytools}.

\subsubsection{Architecture and Event Pipeline}
\label{subsubsec:tracee-architecture}

The official architecture overview reproduced in
Figure~\ref{fig:tracee-architecture} presents Tracee as a sequence of connected
stages. eBPF programs attached to kernel and networking hooks generate runtime
events, which are transferred to user space for collection and enrichment.
The resulting observations are then evaluated by the detection layer and made
available to external consumers. The diagram therefore illustrates an
important architectural property of Tracee: kernel instrumentation is only the
first stage of a broader processing pipeline
\cite{aquasecurity_tracee_architecture}.

The terminology used in the figure reflects the Tracee version for which it
was published. In particular, the detection stage is represented through the
signature-based model used by that release. The current development
documentation retains the same broad separation between collection,
interpretation, and output, but identifies detectors as the preferred mechanism
for implementing new threat detections and derived events. The figure should
therefore be read as a high-level architectural overview.
\cite{aquasecurity_tracee_overview,aquasecurity_tracee_custom_events,
aquasecurity_tracee_detectors}.

This evolution does not alter the principal architectural idea illustrated by
the diagram. Runtime observations originate from different kernel sources but
are converted into events before higher-level processing takes place. Detection
logic operates on this event representation rather than interacting directly
with each underlying probe, while later components determine how the resulting
events are enriched, selected, and delivered.

\subsubsection{Unified Event Model}
\label{subsubsec:tracee-event-model}

The processing stages shown in Figure~\ref{fig:tracee-architecture} are connected
through Tracee's event abstraction. Observations may originate from system
calls, process lifecycle hooks, file and network activity, Linux Security
Module instrumentation, or container-related sources, but they are presented
to the remainder of the system through a common representation. Policies,
detectors, and output components can consequently operate on events without
having to manage the attachment semantics of each underlying kernel source
\cite{aquasecurity_tracee_events,aquasecurity_tracee_overview}.

The same abstraction also represents information derived after the original
kernel observation has reached user space. Security detections and other
derived results become events of their own and can participate in the same
processing infrastructure. This reduces the distinction between raw telemetry
and higher-level results at the pipeline level, while preserving their
different semantic roles
\cite{aquasecurity_tracee_overview,aquasecurity_tracee_detectors,
aquasecurity_tracee_detector_api}.

Events can be selected individually or through sets that group related event
types. The event catalogue therefore acts both as the interface exposed to
users and as the vocabulary shared by the principal user-space components
\cite{aquasecurity_tracee_events}.

\subsubsection{Policies and Event Selection}
\label{subsubsec:tracee-policies}

Tracee policies determine which part of the available event domain is relevant
to a monitoring scenario. A policy combines a scope, which identifies the
workloads or execution contexts to which it applies, with rules that select
events and optionally constrain their data. The same policy model can be
expressed through a plain YAML or JSON document or through a Kubernetes custom
resource, allowing the monitoring intent to remain consistent across local and
orchestrated deployments
\cite{aquasecurity_tracee_policies}.

This abstraction separates the decision to observe an event from the logic
that interprets its security significance. Policies can restrict collection to
the processes, containers, or event families of interest without embedding
every selection rule inside a detector. Where the necessary information is
available during kernel-side processing, filtering can prevent irrelevant
records from entering the user-space pipeline. Conditions that require richer
context can instead be completed after the event has been collected and
normalised
\cite{aquasecurity_tracee_policies}.

In the current development model, policy rules can refer not only to ordinary
runtime events but also to detectors through their threat metadata. A policy
may therefore select detections according to properties such as severity or
MITRE ATT\&CK classification without naming every detector individually. This
selection is resolved when Tracee starts, so detectors that do not satisfy the
configured criteria do not need to participate in runtime dispatch
\cite{aquasecurity_tracee_policy_rules}.

The policy layer consequently provides more than a final output filter. It
defines the portion of the event and detector domain that Tracee prepares for a
particular monitoring objective, while leaving the interpretation of matching
observations to the detector layer.

\subsubsection{Detectors and Derived Events}
\label{subsubsec:tracee-detectors}

The signature block shown in Figure~\ref{fig:tracee-architecture} represents the
detection model used when that architecture was documented. Tracee's current
development version introduces detectors as the preferred mechanism for new
threat detections and derived events, while retaining the earlier signature
system for backward compatibility
\cite{aquasecurity_tracee_custom_events}.

A detector declares the input events required by its logic and receives
matching observations from the event pipeline. It can then evaluate those
observations and produce a derived event when its condition is satisfied.
Detectors may be implemented in Go when programmatic control and access to
runtime state are required, or described through YAML when the desired
condition can be expressed declaratively
\cite{aquasecurity_tracee_detectors,aquasecurity_tracee_detector_api}.

Because detector results are represented as events, they are not restricted to
a terminal notification channel. They can be selected by policies, routed
through the output infrastructure, or consumed by other detectors. Provenance
information can preserve the relationship between a derived result and the
observations from which it originated
\cite{aquasecurity_tracee_detector_api}.

The detector API permits implementations to consume several event types and
retain internal state. This makes stateful detection possible, but it should
not be interpreted as a predefined general-purpose temporal language. The API
provides the mechanisms through which a detector may combine evidence, while
the meaning and limits of that correlation remain part of the detector
implementation.

\subsubsection{Output and Operational Context}
\label{subsubsec:tracee-output}

Once events have passed through collection, selection, and detection, Tracee's
output subsystem determines how they are presented and delivered. Output
configuration is independent from the detector that produced an event. The
same observation can therefore be rendered for interactive inspection or
serialised for machine processing without changing its detection logic
\cite{aquasecurity_tracee_output}.

Tracee supports human-readable tables, structured JSON records, and custom
templates. Events can be written to local destinations, forwarded to external
logging infrastructure, or delivered through webhooks. Output streams provide
an additional routing layer by allowing different portions of the event domain
to be sent to independent destinations
\cite{aquasecurity_tracee_output}.

The event stream may also be enriched with information maintained outside the
original kernel record. Process ancestry and container context can provide the
operator with a clearer account of the workload responsible for an
observation, while provenance information connects a derived detection to the
event from which it originated. This enrichment illustrates why Tracee keeps
event collection distinct from the later interpretation and presentation
stages: the eBPF program captures the information available at the hook, while
user space can relate that record to broader runtime state
\cite{aquasecurity_tracee_detector_api,aquasecurity_tracee_output}.

Tracee additionally includes forensic capabilities that extend beyond alert
generation. Runtime events can guide the collection of artefacts for later
investigation, giving the system a broader operational scope than a monitor
whose output is limited to telemetry and detector alerts
\cite{aquasecurity_tracee_overview}.

\subsubsection{Portability and Security Boundaries}
\label{subsubsec:tracee-boundaries}

Tracee's breadth depends on capabilities exposed by the monitored Linux
kernel. Its current installation guidance identifies BTF information and
kernel-symbol availability as important prerequisites and explicitly
recognises the enterprise Linux 4.18 kernel used by Red Hat Enterprise Linux 8
as a supported exception to its general upstream-version guidance. Individual
events may nevertheless depend on additional kernel configuration or
attachment support, so the presence of the minimum kernel version does not
imply that every Tracee capability is available
\cite{aquasecurity_tracee_requirements}.

This compatibility model is particularly relevant to the target considered in
this thesis. It demonstrates that a long-lived enterprise kernel cannot be
evaluated solely through its nominal upstream version. BTF availability,
vendor backports, accessible symbols, verifier behaviour, and supported hooks
must be examined on the deployed system.

Tracee also states an explicit trust assumption: the kernel is expected to be
trustworthy when monitoring begins. Once a kernel-level adversary controls the
system, it may interfere with eBPF execution, suppress observations, or disable
the monitoring infrastructure. Tracee can attempt to identify known forms of
kernel manipulation after startup, but such detection remains best effort
rather than a guarantee against a compromised kernel
\cite{aquasecurity_tracee_security_model}.

This boundary is important when interpreting kernel-derived telemetry. Running
the collection programs inside the kernel protects them from ordinary
application behaviour, but it does not make the monitoring system independent
from the integrity of the kernel on which those programs execute.

\subsubsection{Relationship to the Proposed Work}
\label{subsubsec:tracee-relationship}

Tracee influenced the proposed system primarily through its separation of
event collection, policy-based selection, detector evaluation, and output.
The tool developed in this work adopts the same general division of
responsibilities: heterogeneous kernel observations are converted into a
normalised user-space representation, policies define the monitored event
domain, and detectors interpret selected observations without placing all
security logic inside the eBPF programs.

The relationship is architectural rather than one of functional equivalence.
Tracee provides a broad event catalogue, extensive process and workload
context, configurable routing, detector chaining, and forensic capabilities.
The prototype developed in this thesis instead concentrates on a selected set
of process and host-security events on the specified Rocky Linux kernel. Its
detector model is deliberately bounded around deterministic conditions over
individual events and short locally correlated sequences.

Tracee therefore serves both as a design reference and as a point of comparison
for the contribution of this work. It shows that the main architectural choices
on which the proposed system relies are already established in runtime security
tooling. The contribution of the thesis lies instead in bringing these ideas
together within an independently developed prototype tailored to the selected
enterprise environment, where its compatibility, internal event contract,
collective detection model, and runtime behaviour can be examined directly.

\subsection{Other Relevant eBPF Security Tools}
\label{subsec:other-ebpf-security-tools}

Falco is a runtime security engine organised around rules evaluated over event
sources. Kernel system-call activity can be captured through its driver
architecture, while plugins provide additional sources. Falco rules are
declarative YAML objects containing a condition, output description, priority,
and optional reusable lists, macros, tags, and exceptions. A matching rule
produces an alert that can be routed to configured outputs
\cite{falcosecurity_falco_kernel_architecture,falcosecurity_falco_rules,
falcosecurity_falco_outputs}.

This model demonstrates the operational value of readable rules, reusable
expressions, explicit exceptions, and an alert-oriented interface. Falco also
maintains process and container context used to enrich individual events.
However, its documented rule conditions are evaluated against an incoming
event, and separate event sources are processed independently; the core rule
language is not presented as a general temporal sequence language across
heterogeneous sources \cite{falcosecurity_falco_event_sources,
falcosecurity_falco_rule_conditions}.

Tetragon combines eBPF-based observability with optional runtime enforcement.
Its tracing policies specify kernel hooks, captured arguments or return values,
and selectors that can match process, namespace, capability, workload, and
argument attributes. Supported actions can include emitting an event,
delivering a signal, or overriding a return value where the hook and kernel
support that operation \cite{cilium_tetragon_tracing_policy,
cilium_tetragon_selectors,cilium_tetragon_enforcement}.

Tetragon therefore moves more selection and potential response close to the
hook than an architecture centred on user-space detectors. It preserves
process-lifecycle context and emits structured events through its own
interfaces, but its documented tracing-policy model is principally
hook-centred rather than a general language for arbitrary temporal sequences
\cite{cilium_tetragon_events,cilium_tetragon_tracing_policy}. Its current
installation requirements also illustrate the dependence of advanced eBPF
functionality on kernel capabilities and BTF availability
\cite{cilium_tetragon_requirements}.

\subsection{Comparative Summary}
\label{subsec:runtime-tools-comparison}

The systems examined in this section represent different approaches to runtime
security. Tracee provides the closest architectural reference because it
separates kernel-level collection from the analysis performed in user space.
Falco instead places declarative rule evaluation and alert generation at the
centre of its design, while Tetragon moves a greater part of event selection
and optional response closer to the kernel hook.

These approaches are not directly interchangeable, but they provide useful
reference points for the proposed system. Tracee illustrates the event-oriented

\section{Positioning of the Proposed Work}
\label{sec:positioning-proposed-work}

The proposed work occupies a deliberately bounded part of the Linux runtime
security design space. It focuses on process and host-security monitoring on
Rocky Linux 8.10 with kernel
\texttt{4.18.0-553.109.1.el8\_10.x86\_64}. Because this environment combines
an older upstream kernel base with vendor backports, compatibility cannot be
inferred from the version number alone. The available hooks, helpers, data
layouts, and verifier behaviour must instead be established on the deployed
system
\cite{redhat2025backporting}.

Within this environment, eBPF programs collect selected kernel observations
and transfer them to a Go runtime through an explicit event contract. The
resulting records become a typed user-space event stream. Chapter~3 defines how
that stream is scoped through policies and interpreted by detectors; the
present chapter is concerned with the eBPF collection model and the prior-art
systems against which the complete architecture is positioned.

The individual mechanisms used by the prototype have clear precedents in
existing runtime security systems. Tracee provides the closest architectural
reference through its event-oriented separation of collection, policy
selection, detection, and output. Falco demonstrates the maturity of
declarative event rules and alert generation, while Tetragon illustrates a
more kernel-centred design that also supports enforcement
\cite{aquasecurity_tracee_policies,aquasecurity_tracee_detectors,
falcosecurity_falco_rules,cilium_tetragon_tracing_policy}.

The contribution of this thesis therefore lies in the independent integration
of these ideas within a compact prototype tailored to the selected enterprise
kernel. Particular attention is given to the compatibility decisions required
by that environment, the selection of complementary observation points and the
contract through which kernel records become typed user-space events. The
policy and detection architecture built on that contract is developed in
Chapter~3 rather than repeated here.
