\chapter{Experimental Evaluation}
\label{ch:experimental-evaluation}

Chapter \ref{ch:user-space-implementation} completed the implementation account at the point where decoded
events are admitted, evaluated and rendered. This chapter evaluates that
pipeline in a controlled containerised scenario. A vulnerable service, an
exploit client and the monitor run in three separate Pods on one Minikube node.
The experiment asks whether the node-level monitor can observe activity in the
target Pod, whether the configured collective detector preserves the expected
evidence, and whether exact kernel-side UID admission keeps the monitor's
measured CPU demand below the project's 5\% threshold.

The evaluation is deliberately bounded. It is not a measurement of general
detection accuracy, cross-node visibility or total system overhead. Instead,
it combines a functional campaign of three benign and three exploit runs with
a performance campaign of nine runs in rotated profile order. Application
outcome, detector outcome, operational health and resource consumption are
treated as separate observations throughout.

\section{Evaluation Objectives and Experimental Protocol}
\label{sec:evaluation-objectives-protocol}

The experimental protocol addresses three objectives.

\begin{itemize}
    \item First, it tests node-local, cross-Pod visibility: the monitor must receive target events even though the monitor, target and trigger have different Pod identities, network addresses and cgroups.
    \item Second, it tests the scenario-specific collective detector. The exploit should produce one alert containing four ordered events, whereas the selected benign interaction should not complete that sequence.
    \item Third, it compares the monitor's resource use with exact UID admission enabled and disabled while retaining the same exploit workload and detector outcome.
\end{itemize}

These objectives require independent evidence oracles. Application success is
established by the benign response or by recovery of the synthetic flag.
Detector success requires one alert with the complete ordered evidence.
Operational health is assessed from Pod restart deltas and perf-event loss
diagnostics emitted during each retained interval. The exploit client also
performs its own output validation, but this is a harness check rather than a
substitute for either the application or detector oracle. This distinction is
important because two retained exploit runs recovered the flag despite a
defective client-side pattern check.

For the functional campaign, the independent variable is the interaction
class, benign or exploit. The dependent observations are the application
result, client result, alert count and completeness, reported loss diagnostics
and restart delta. Three runs of each class were retained without replacement.
For the performance campaign, the independent variable is the monitor profile:
\textbf{exact UID-filtered, unfiltered, or no monitor}. The primary dependent metric is
monitor-container cgroup CPU consumption; cgroup memory, cgroup
\texttt{total\_rss}, target CPU and node CPU provide additional context. Each
profile was repeated three times
in the rotated orders F--U--N, U--N--F and N--F--U to reduce simple ordering
bias.

Each run was assigned an identifier. Before the interaction began, workload
readiness and Pod state were verified; after completion, the corresponding
trigger output, monitor and target logs, restart counts and, where applicable,
resource samples were retained under the same identifier. Effective manifests 
and the complete command history were preserved with the experimental artefacts. 
This organisation supports repeatability within the laboratory, although three 
repetitions per condition are not sufficient for population-level accuracy or overhead claims.

\section{Kubernetes and Minikube as the Evaluation Platform}
\label{sec:evaluation-kubernetes-minikube}

The evaluation uses Kubernetes to deploy and coordinate the containerised
components involved in the experiment. Kubernetes manages applications through
declarative resources that describe their desired execution state. Its basic
execution unit is the Pod, which groups one or more containers that share
selected namespaces and resources. Containers placed in separate Pods instead
retain distinct workload identities and, unless explicitly configured
otherwise, separate process and network contexts
\cite{kubernetes_pods,kubernetes_process_namespace}.

This model is relevant to the evaluation because the monitoring prototype and
the application under observation can run as independent workloads while still
executing on the same node. The application does not need to include the
monitoring executable or expose an application-specific telemetry interface.
The monitor obtains visibility from the node kernel, whereas Kubernetes
controls the placement, isolation and lifecycle of the corresponding
containers.

The monitor is deployed through a DaemonSet, a controller intended for node-local services
such as monitoring and logging agents. In a multi-node environment, this model
can maintain one monitor instance on each eligible node; in the present
evaluation, it produces one instance because the cluster contains a single
node \cite{kubernetes_daemonset}.

Communication with the target is provided by a Kubernetes Service. Pods are
ephemeral and may receive different addresses when recreated, whereas a
Service provides a stable logical endpoint and selects the Pods that implement
the application. The experimental client can therefore address the service
without depending on the current IP address of the target Pod
\cite{kubernetes_service}.

The Kubernetes environment is instantiated locally through Minikube. Minikube
provisions a Kubernetes cluster on one machine and supports several drivers for
creating its node environment. The experiment uses the Docker driver, under
which the Minikube node is hosted through Docker rather than through a
dedicated virtual machine \cite{minikube_local_cluster,minikube_docker_driver}.
The resulting arrangement preserves the Kubernetes resource and networking
model while keeping the testbed reproducible on the selected Rocky Linux host.

Minikube is used here as a controlled evaluation platform. It makes it possible to deploy the
monitor, target and experiment client through Kubernetes manifests, inspect
their runtime state with \texttt{kubectl}, and repeat the scenario without
requiring external cluster infrastructure. The concrete software versions,
node resources, workload identities and security settings used in the
experiment are reported in
Section~\ref{sec:evaluation-cross-pod-testbed}.

\section{AES-beta Workload and Controlled Attack Scenario}
\label{sec:evaluation-aes-beta-scenario}

AES-beta is a public \gls{ctf} challenge from openECSC-2024
\cite{openecsc2024_aes_beta}. The experiment used a fixed local copy, adapted
only where required for repeatable execution in the laboratory. The original
competition secret was replaced by the synthetic value mounted into the target
Pod.

The benign client submits a valid key and plaintext, receives the transformed
message and compares it with the expected result. It exercises the network
service without requesting the flag. The exploit first leaks the information
needed to locate the library and reconstructs the stack canary by testing the
unknown bytes. Its final worker supplies a payload that invokes
\texttt{system("cat flag")}. The resulting target-side behaviour installs
\path{/bin/sh}, then \path{/bin/cat}, and accesses the flag at
\path{/opt/aes-beta/flag}. Each retained exploit reported 1,793 workers and
recovered the synthetic flag.

The monitor is not a network intrusion detector and does not inspect the
payload, leak or canary search. Its experimental policy admits the selected
target events and, in the filtered profile, applies exact effective UID 10001
admission in kernel space. The collective detector requires four observations
within five seconds: execution of \path{/bin/sh}; execution of
\path{/bin/cat}; an LSM \texttt{security\_file\_open} observation resolving
\path{/opt/aes-beta/flag}; and an \texttt{open} event for caller pathname
\texttt{flag} with a non-negative returned file descriptor. The
\texttt{process\_tree} strategy relates those observations locally.

\section{Functional Evaluation}
\label{sec:evaluation-functional}

\subsection{Collective Detector Validation}
\label{subsec:evaluation-collective-detector}

All three exploit runs recovered the synthetic flag and generated exactly one
alert. Each alert retained four records in the required order: a
\texttt{sched\_process\_}\allowbreak\texttt{exec} event for \path{/bin/sh}, another for
\path{/bin/cat}, a \texttt{security\_file\_open} record resolving the mounted
flag, and an \texttt{open} record. The final \texttt{open} event completed the 
evidence by recording the syscall return value. In the retained alert, the value was 
2: a non-negative result indicating success and identifying the file descriptor assigned by the kernel.

Within each alert, all four records carried UID 10001 and the same stable host
process identity. The experiment therefore exercised the same-process branch
of \texttt{process\_tree} correlation.

The first two records confirm the successful executable transitions to
\path{/bin/sh} and \path{/bin/cat}. The third identifies the resolved flag file
at the LSM mediation point, while the fourth records the successful result of
the corresponding \texttt{open} syscall. The repeated host PID and UID in the

target process. Internally, the detector's \texttt{process\_tree} strategy also
uses the task start time to avoid correlating different process lifetimes that
reuse the same numeric PID.

The application and detector oracles agreed in all three exploit runs, but they
measure different outcomes. Recovering the synthetic flag demonstrates that the
attack reached its intended application effect. The alert instead demonstrates
that the four configured kernel observations were received and correlated in
the expected order. Successful exploitation does not by itself guarantee alert
generation, and an alert does not replace verification of the application
outcome. This distinction is particularly relevant to the client-side
validation discrepancy discussed below.

\section{Performance Evaluation}
\label{sec:evaluation-performance}

\subsection{Metrics, Sampling and Benchmark Profiles}
\label{subsec:evaluation-metrics-profiles}

The performance campaign reused the exploit workload because it provided a
repeatable high-activity interval and an independent functional oracle. Three
profiles were evaluated.

\begin{itemize}
    \item The \textbf{filtered} profile enabled exact UID 10001 admission
    in the common eBPF path.
    \item The \textbf{unfiltered} profile retained the same event, policy,
    detector and output configuration but disabled that early admission.
    \item The \textbf{no-monitor} profile removed the monitoring workload and was
    retained only as descriptive context.
\end{itemize}

After each profile change, the setup allowed a ten-second warm-up before the
official run. A nominal 75-second sampler recorded one-second observations,
but statistics were calculated only from samples whose host timestamps fell
within the actual exploit start and end markers.
The primary CPU metric was derived from the monitor container's cgroup-v1
\texttt{cpuacct.usage} counter. For each sampling interval, the increase in
accumulated CPU time was divided by the elapsed wall-clock time and expressed as
a percentage of one CPU core. A value of 100\% therefore represents the
equivalent of one fully utilised core, while the project's 5\% threshold
corresponds to an average demand of 0.05 core.

Memory was observed through two counters belonging to the same container
cgroup. The \texttt{memory.usage\_in\_bytes} value represents the overall memory
accounted to the cgroup, whereas \texttt{total\_rss} from
\texttt{memory.stat} represents its resident-memory component, including
descendant cgroups. The latter is a container-cgroup measurement and should not
be interpreted as the RSS reported for the monitor process alone through
\texttt{/proc}.

Each profile was run once in each of three rounds. The order changed across
rounds to F--U--N, U--N--F and N--F--U. Every monitored run also retained the 
flag, alert, loss-diagnostic and restart checks so that a low resource value 
could not be accepted after a failed workload.

\subsection{Monitor CPU and Memory Consumption}
\label{subsec:evaluation-monitor-resources}

unfiltered configuration. Across the three filtered runs, mean consumption
ranged from 0.44\% to 0.47\% of one CPU core. The aggregate mean was 0.46\%,
with an \gls{sd} of 0.02 percentage points. In the unfiltered runs, the
corresponding values ranged from 5.28\% to 6.43\%, producing an aggregate mean

\subsection{Effect of Kernel-Side UID Filtering}
\label{subsec:evaluation-uid-filter-effect}

The project acceptance gate applies to the monitor's mean CPU consumption and
requires the filtered profile to remain below 5\% of one core. All three
filtered run means satisfied the gate, and their aggregate mean was 0.46\%.
The corresponding unfiltered mean was 5.73\%, above the threshold. The profiles
differed by the exact kernel-side UID admission setting while retaining the
same scenario and functional checks. The observed difference is therefore
consistent with early rejection of non-target activity before event transport
and user-space processing, although the sequential laboratory design does not
isolate that setting from every source of run-to-run variation.

Using the unrounded run data, the filtered mean was approximately 92.0\% lower
than the unfiltered mean. This percentage compares monitor-container cgroup CPU
and uses the unfiltered mean as its denominator. It is not the total cost of
eBPF execution, the total node overhead, or a production capacity estimate.
The preservation of three flag recoveries and three complete alerts in each
monitored profile shows that the
configured admission rule retained the evidence required by this scenario.

\section{Discussion of Results}
\label{sec:evaluation-discussion}

The functional and performance observations answer complementary questions.
The cross-Pod campaign shows that the monitor does not need to share a Pod,
network namespace or process namespace with the target to observe its
node-kernel activity. The four-stage alert also demonstrates that request,
mediation and successful syscall evidence can be preserved together across the
implemented pipeline. The result is stronger than observing a single hook, but
it remains tied to one known sequence and one same-process correlation path.

The profile comparison shows why admission placement matters. Without exact UID
filtering, events from unrelated node activity reached transport and user-space
processing even though later policy and detector logic did not need them. The
filtered profile rejected that activity in the shared eBPF initialisation path
and was associated with lower measured monitor-container cgroup CPU while
retaining the required alert. This result is consistent with the architectural
decision to combine configurable user-space analysis with a narrow optional
kernel-side control.

The experiment does not establish that UID filtering is universally suitable.
A UID is not a stable Kubernetes workload identity, and two workloads may use
the same numeric identity. Broader monitoring policies may also need evidence
from several UIDs. The conclusion is therefore conditional: when the monitored
subject has a known effective UID and the selected detector requires only that
subject's events, exact early admission can materially reduce the monitor's
user-space demand.

\section{Threats to Validity and Current Limitations}
\label{sec:evaluation-threats-validity}

\noindent\textbf{Internal validity.}
The experiment ran sequentially on one busy two-core node, and unmeasured
background activity could influence CPU samples. Rotating profile order reduces
but does not remove this risk. Resource limits were absent, so monitor, target
and cluster services could contend. The B1 connection anomaly and the E1/E2
client defects were retained and interpreted through independent oracles rather
than silently discarded. No-monitor termination timing was not independently
captured, which prevents a clean baseline subtraction.

\medskip
\noindent\textbf{Construct validity.}
Monitor-container cgroup CPU measures work charged to that cgroup; it does not
include all kernel execution induced by eBPF programs and is therefore not
total overhead. Cgroup memory and cgroup \texttt{total\_rss} capture different
memory views.
No matching perf-loss message is evidence only about diagnosed loss, not proof
of complete transport. Detector completion measures conformance with one
predefined sequence, while three benign controls cannot establish a general
false-positive rate or detection accuracy.

\medskip
\noindent\textbf{External validity.}
The study uses one Rocky Linux kernel, one Docker-backed Minikube node, one CTF
service and one scenario-specific detector. Results may differ with other
kernels, attachment availability, container runtimes, workload rates and node
sizes. All components were co-located, so neither cross-node observation nor
cluster-wide correlation was evaluated. The exact UID key was controlled for
this workload and should not be generalised to workload identity.

\medskip
\noindent\textbf{Conclusion validity.}
Three runs per profile permit a transparent descriptive comparison but do not
support strong inferential statistics. High node utilisation and unresolved
no-monitor timing make duration and target-CPU differences unsuitable for
causal conclusions. The approximately 92.0\% value is consequently reported
only for the filtered-versus-unfiltered monitor-container cgroup CPU means.
The monitor was privileged
and observational; least-privilege deployment, enforcement and production
readiness remain outside the evaluated claims.

\section{Evaluation Summary}
\label{sec:evaluation-summary}

The experiment met its three scoped objectives. A privileged monitor Pod
observed target activity generated through a Service from a separate trigger
Pod on the same node. The selected benign interaction completed three times
without an alert, while all three exploit runs recovered the synthetic flag
and produced one complete four-event alert. Finally, the exact UID-filtered
profile consumed a mean of 0.46\% of one CPU core in the monitor-container
cgroup, below the 5\% project gate and approximately 92.0\% lower than the
unfiltered profile in this campaign.

These findings support the prototype's node-local collection, deterministic
collective detection and early-admission design under the evaluated conditions.
They do not establish cross-node visibility, total overhead, general detection
accuracy, loss-free transport or production privilege requirements.
Chapter~7 draws the overall conclusions from these bounded results and places
the remaining limitations within the future development of the system.
