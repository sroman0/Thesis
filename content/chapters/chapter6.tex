\chapter{Experimental Evaluation}
\label{ch:experimental-evaluation}

Chapters~4 and~5 described the kernel-space collectors and the user-space
runtime separately. This chapter evaluates the complete monitoring path in a
cross-Pod Kubernetes scenario. A vulnerable service, an attack client and the
monitor run in three independent Pods on one Minikube node. The experiment
therefore tests whether a privileged monitoring Pod can observe and correlate
activity generated by another Pod through their shared node kernel.

The evaluation is functional rather than a general benchmark. It establishes
the deployment preconditions, verifies node-local visibility, and compares
three benign interactions with three executions of a controlled exploit.
Application outcome, detector outcome and runtime diagnostics are reported as
separate observations. Resource overhead and cross-node visibility are outside
the experimental protocol.

\section{Evaluation Objectives and Protocol}
\label{sec:evaluation-objectives-protocol}

The experiment assesses three properties of the implemented system:

\begin{itemize}
    \item whether the monitor can receive target events while the monitor,
    target and client have independent Pod identities, network addresses and
    cgroups;
    \item whether the client can reach the target through a Kubernetes Service
    and the resulting target activity remains visible to the node-level eBPF
    programs;
    \item whether the collective detector remains silent during the selected
    benign interaction and produces the expected ordered evidence during the
    AES-beta exploit.
\end{itemize}

The protocol was divided into precondition checks and functional runs. The
precondition checks established Pod separation, Service routing, target-event
visibility and the behaviour of the exact kernel-side \gls{uid} filter. The
functional campaign then executed three benign runs followed by three exploit
runs. Every run had a distinct identifier and retained its client output,
target and monitor log interval, Pod state, restart counts and diagnostic
messages. Failed validations and anomalous timings were preserved rather than
replaced by later runs.

Three result classes were considered independently. Application success meant
that the benign client obtained the expected ciphertext or that the exploit
recovered the synthetic flag. Detection success required one alert containing
the complete ordered event sequence. Runtime health was assessed from Pod
restart counts and the absence or presence of perf-event loss diagnostics.
This distinction prevents a client-side validation defect from being
misclassified as a detector failure, and prevents an alert from being treated
as proof that the client received the flag.

The complete command history, effective manifests and raw run artefacts were
stored in a timestamped evidence directory. The results below are descriptive:
three repetitions can demonstrate repeatability in this controlled scenario,
but do not provide an estimate of general detection accuracy.

endpoint for a selected backend \cite{kubernetes_pod_networking}.

All Pods retained \texttt{hostPID: false}, \texttt{hostNetwork: false} and
\texttt{shareProcessNamespace: false}. The target and trigger consequently did
not gain host process visibility merely to support the experiment. The monitor
remained privileged and mounted the host interfaces required to load and run
the eBPF programs. This is a prototype configuration rather than a demonstrated
least-privilege profile \cite{kubernetes_privileged_containers}.

The synthetic flag was provided through a Kubernetes Secret mounted only in
the target at \path{/opt/aes-beta/flag}. Neither the monitor nor the trigger
received that volume. The effective manifests, image identities and cgroup
records were retained with the evidence so that the final topology could be
distinguished from its planned configuration.

\section{Controlled AES-beta Workload and Detection Oracle}
\label{sec:evaluation-workload}

AES-beta is a public \gls{ctf} challenge used here as a controlled source of
process and file activity \cite{openecsc2024_aes_beta}. In the benign scenario,
the client sent a key and plaintext to the service, received the transformed
message and checked it against the expected XOR result. This path exercised the
network service without requesting the flag.

The exploit scenario recovered the stack canary by testing 256 candidates for
each of seven unknown bytes. The client therefore created 1,792 candidate
workers and one final worker that executed the payload, for 1,793 reported
workers in each run. Successful exploitation caused the target process to
invoke a shell, execute \texttt{cat} and open the mounted flag. The synthetic
flag value made application success directly observable without using a real
competition secret.

The monitor selected only the three logical events required by the scenario
and applied the exact UID 10001 filter before transport. The collective
detector required four ordered observations within five seconds:

\begin{enumerate}
    \item a successful \texttt{sched\_process\_exec} transition to
    \path{/bin/sh};
    \item a successful \texttt{sched\_process\_exec} transition to
    \path{/bin/cat};
    \item a \texttt{security\_file\_open} observation whose resolved path was
    \path{/opt/aes-beta/flag};
    \item an \texttt{open} event for caller pathname \texttt{flag} with a
    non-negative returned file descriptor.
\end{enumerate}

The LSM event identifies the resolved filesystem object under security
mediation, while the final syscall event supplies the success evidence that the
entry-stage hook cannot provide. The sequence used \texttt{process\_tree}
correlation and required UID 10001. Its ATT\&CK metadata classified the
observations as Execution and Collection through TA0002, TA0009, T1059.004 and
T1005 \cite{strom2020attack}. These identifiers communicate the intended
security meaning of the alert; the experimental oracle remained the explicit
four-event sequence.

\section{Isolation and Visibility Validation}
\label{sec:evaluation-preconditions}

Before executing the functional campaign, Kubernetes metadata and container
\path{/proc} data were inspected to verify the assumptions of the topology.
Target and trigger had different Pod UIDs, Pod IPs, container identities and
Pod cgroups. The Service had ClusterIP \texttt{10.102.19.49} and selected the
target endpoint \texttt{10.244.0.3:1337}. A connection from the trigger reached
the target with source address \texttt{10.244.0.4}, confirming that the active
path was cross-Pod Service communication rather than loopback.

A controlled \texttt{/bin/cat /proc/self/status} operation was then executed in
the target. The monitor recorded eight UID 10001 events in the bounded interval,
including executable transition, resolved file access and successful
\texttt{open} evidence. Comparable harmless activity generated under trigger
UID 10002 produced no monitor records in its interval. This establishes a
target-visibility and UID-filter sanity check for the selected event set. It
does not prove that every possible event from other UIDs would be absent under
all workloads.

The preconditions therefore established that the target was observable without
sharing a Pod or process namespace with the monitor. The observation remained
node-local: all components used the same Linux kernel, and no event was expected
to cross a node boundary.

Every alert contained, in order, execution of \path{/bin/sh}, execution of
\path{/bin/cat}, resolved access to \path{/opt/aes-beta/flag}, and a successful
relative \texttt{open} of \texttt{flag}. All four records carried UID 10001 and
the same host \gls{pid} within each run. The selected scenario therefore
exercised the same-process branch of \texttt{process\_tree} correlation; it did
not test arbitrary ancestry reconstruction.

The first two clients returned a failure status even though both recovered the
flag. The reused client initially expected a \texttt{THESIS\{...\}} value,
whereas the mounted synthetic flag used an \texttt{openECSC\{...\}} prefix. The
first attempted correction was then malformed by shell parameter expansion.
After the pattern was assigned literally and tested, the third client returned
success. The raw outputs preserve both failed checks. Application exploitation
was consequently successful in 3/3 runs, while the client's own final
validation passed in 1/3; detector completion was independently observed in
3/3.

Across all six functional intervals, no matching perf-event loss diagnostic
was found and every Pod retained a zero restart count. Absence of a diagnostic
is weaker than an independent transport-loss measurement, but it provides no
evidence of reported loss during these runs.

\section{Discussion and Threats to Validity}
\label{sec:evaluation-discussion}

The results support the experimental question within the stated boundary. A
monitor in its own Pod observed target activity generated through a Service
from a third Pod and completed the configured collective detector in every
exploit run. The successful path depended on node co-location and the shared
kernel, not on a shared Pod network or process namespace. The benign controls
also show that ordinary use of the challenge service did not satisfy this
specific four-stage detector sequence.

The result is strengthened by separating application and detector evidence.
The first two exploit runs demonstrate that client-side status can be wrong
after the relevant host operations have already occurred. Conversely, an alert
proves only that the configured kernel events matched; it does not by itself
prove delivery of the file contents to the client.

\noindent\textbf{Internal validity.}
The target accepts one challenge session at a time, and the connectivity check
delayed B1 until its timeout. This anomaly was retained and excluded from
latency interpretation. The client-pattern defects in E1 and E2 were also
retained, with flag recovery used as the independent application result. The
runs were sequential and not randomised, so unmeasured node-state changes may
remain.

\medskip
\noindent\textbf{Construct validity.}
The UID-filter check covered controlled activity for UIDs 10001 and 10002; it
was not an exhaustive proof for all event types. No textual loss diagnostic was
observed, but transport loss was not measured through an independent counter.
The detector oracle was defined from a known exploit sequence, and zero alerts
in three benign interactions does not establish a false-positive rate.

\medskip
\noindent\textbf{External validity.}
The experiment used one Rocky Linux host, one Docker-backed Minikube node, one
public challenge and one scenario-specific detector. It does not establish
cross-node or cluster-wide collection, behaviour under a heterogeneous cluster,
or coverage of unrelated attacks. UID 10001 is an experimental admission key,
not a general Kubernetes workload identity.

\medskip
\noindent\textbf{Operational limitations.}
The monitor ran as a privileged container with host kernel-interface mounts;
a production least-privilege profile was not evaluated. The tool observed and
reported activity but did not enforce a decision. CPU and memory overhead were
not measured by this protocol, so the functional results do not support a
performance claim.

\section{Evaluation Summary}
\label{sec:evaluation-summary}

The cross-Pod experiment met its functional acceptance criteria. Kubernetes
metadata and cgroup evidence established three independent Pods on one node,
Service routing connected the trigger to the target, and a controlled target
operation was visible to the monitor. All three benign runs completed without
an AES-beta alert, while all three exploit runs recovered the synthetic flag
and produced one alert containing the complete ordered sequence. No matching
loss diagnostic or Pod restart was observed.

The supported conclusion is deliberately node-local: in this single-node
Minikube configuration, detection did not require the monitor, target and
trigger to share a Pod. The experiment does not establish cross-node
observation, production privilege requirements, general detector accuracy,
enforcement or resource overhead. Chapter~7 uses these bounded results to draw
the thesis conclusions and identify future work.
