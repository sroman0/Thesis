\chapter{Experimental Evaluation}
\label{ch:experimental-evaluation}

Chapters~4 and~5 described the kernel-space collection path and the
user-space runtime as separate implementation concerns. This chapter evaluates
their integrated behaviour in a controlled container environment. The
experiment follows one scenario from workload execution to the evidence
observed by the monitor, the alert produced by the collective detector and the
resources charged to the monitored containers. The purpose is to determine
whether the implemented pipeline behaves as intended under a reproducible
node-local workload.

\section{Evaluation Objectives and Experimental Protocol}
\label{sec:evaluation-objectives-protocol}

The evaluation addresses three questions. 
\begin{itemize}
    \item Can the monitoring agent observe security-relevant activity generated inside 
    another container when the Pod does not share its process namespace with the host?
    \item Can the configured collective detector assemble the expected sequence of process and
    file events while leaving a controlled benign interaction without an alert?
    \item How does exact kernel-side \gls{uid} filtering affect the resources
    charged to the monitor container during the attack workload?
\end{itemize}

Two campaigns were conducted. The functional campaign comprised three benign
windows and four exploit windows. Each window had a distinct run identifier and
preserved the trigger output, standard error and time-bounded container logs.
The performance campaign comprised five rounds, each containing a filtered
monitor profile, an unfiltered monitor profile and a profile without the
monitor. The starting profile was shifted between rounds, giving fifteen runs
in a cyclic order. The Pod was recreated and allowed to become ready before
each run.

The performance protocol used a ten-second warm-up and then selected samples
whose endpoint timestamps fell within the externally recorded workload
interval. The sampling period was nominally one second, although reads performed
through the Minikube \gls{ssh} path introduced some interval variation. A project
acceptance gate of 5\% was applied to the mean \gls{cpu} time charged to the monitor cgroup,
expressed as a percentage of one core. This gate is local to the project and is
not a claim about total host overhead. Results are reported descriptively using
the five run means per profile; the sample standard deviation describes
variation among those runs rather than a wider population.

The experimental input was the scenario executed by the trigger together with
the selected monitoring profile. The main dependent observations were the
event evidence and alert count in the functional campaign, and cgroup CPU,
memory, \gls{rss}, PID count, node CPU and workload duration in the performance
campaign. The protocol was designed to hold the host, cluster allocation,
target images, policy, detector and synthetic flag fixed. Run identifiers and
\gls{utc} window boundaries tied
the scenario output to the corresponding monitor log, preventing alerts from
earlier activity in the accumulated container log from being counted in a
later run.

\section{Experimental Testbed}
\label{sec:evaluation-testbed}

Laboratory records identify the host as Rocky Linux 8.10 with kernel
\path{4.18.0-553.137.1.el8_10.x86_64}. This is a later patch-level build in the
same Rocky Linux 8.10 kernel stream as the implementation baseline used during
development. The recorded Minikube v1.38.1 configuration created one node with
the Docker driver, two requested CPUs and 4096~MiB of memory
\cite{minikube_docker_driver}. The archived Kubernetes output independently
confirms server version v1.30.0. No evaluation claim depends on functionality
introduced after the implementation baseline.

The testbed used a single Pod named \texttt{aes-beta-lab} containing three
containers. The target exposed the vulnerable service, the trigger generated
benign or exploit inputs, and the monitor ran the proposed tool. The trigger reached
the target through the Pod-local loopback address on port 1337. The applied Pod
set \texttt{hostPID}, \texttt{hostNetwork} and
\texttt{shareProcessNamespace} to false. The target and trigger consequently
shared the Pod network but did not share one process namespace
\cite{kubernetes_pod_networking,kubernetes_process_namespace}.

The public challenge revision was recorded before image construction, and the
binary, dynamic loader and C library were checked against fixed hashes. The
preparation script verifies these artefacts but does not independently assert
the Git revision of the source checkout. The applied Pod and the policy and
detector documents were preserved with configuration hashes for the functional
campaign, while the running Pod record retained the three image identities. The
flag was a synthetic value created for the thesis experiment rather than a
competition secret. Full hashes, image identifiers, manifests and commands
remain in the reproducibility material rather than in the chapter body.

The Pod specifications declared resource requests but no container limits.
Consequently, the measurements describe actual use under contention on the
two-core Minikube node rather than enforcement at a fixed container ceiling.
The requested node size is preserved by the cluster-start command; a separate
snapshot of realised Kubernetes allocatable capacity was not archived. This
preservation gap is considered again in the validity analysis.

\section{Controlled AES-beta Scenario}
\label{sec:evaluation-workload}

AES-beta is a public Capture the Flag challenge adapted here as a controlled
process-monitoring workload. The target service receives requests over the
Pod-local connection. A benign run exercises the service without attempting to
read the mounted flag. An exploit run drives the vulnerable service until the
target process invokes a shell, executes \texttt{cat} and attempts to read the
flag at \path{/opt/aes-beta/flag}. The exploit implementation and payload
construction are not evaluation variables; the relevant input is the resulting
host behaviour \cite{openecsc2024_aes_beta}.

The policy admitted only the three logical events required by the experiment.
The detector then required four ordered observations for UID 10001 within a
five-second window. The first two were successful executable transitions to
\path{/bin/sh} and \path{/bin/cat}. The third was
\texttt{security\_file\_open} for the resolved flag path. This event shows that
the resolved file reached the Linux security mediation stage, but it does not
by itself establish that access succeeded. The fourth was an \texttt{open}
event for the caller pathname \texttt{flag} with a non-negative return value,
which supplied the syscall-boundary success evidence.

The sequence used the local \texttt{process\_tree} correlation strategy. In the
observed alerts, all four records shared one host \gls{pid}; the experiment
therefore exercised the same-process branch of that strategy. It did not
independently test correlation from a parent process to its immediate child.
The resulting alert carried high severity and the ATT\&CK identifiers TA0002,
TA0009, T1059.004 and T1005. These identifiers classify the intended meaning of
the observed sequence in the standard \gls{attack} vocabulary
\cite{strom2020attack}; they are not evidence of detector correctness or
technique coverage.

This scenario creates an interpretable boundary between controlled application
input and observable host effects. Unlike direct invocation of the monitored
commands, it requires the evidence to originate from the vulnerable target
service rather than from the trigger container. The challenge artefacts and
runtime dependencies were fixed for the experiment, and the success condition
used a synthetic value whose disclosure has no operational consequence.

\section{Functional Evaluation}
\label{sec:evaluation-functional}

\subsection{Cross-Container Event Visibility}
\label{subsec:evaluation-cross-container-visibility}

The initial visibility test captured a wider stream of 7,289 records and then
isolated the nine records whose process UID was 10001. Those records described
a directly invoked \texttt{cat} operation in the target container, including
the executable transition, resolved flag object and successful file-open
result. The process had container PID 327 and host PID 3016236. The monitor
therefore retained both the namespace-relative identity reported inside the
target and the host identity needed for node-local correlation.

This result demonstrates that the privileged monitor observed target-container
activity despite \texttt{hostPID: false} and without a shared Pod process
namespace. The scope is deliberately narrow: all containers ran on one
Minikube node and shared its kernel. The result does not establish visibility
across nodes or cluster-wide correlation.

\subsection{Collective Detector Validation}
\label{subsec:evaluation-collective-detector}

Every exploit window produced one alert containing the configured four-event
sequence. In the first run, the two executable transitions identified
\path{/bin/sh} and \path{/bin/cat}; the mediation event then identified the
resolved flag object, and the final \texttt{open} event returned descriptor 2.
The latter supplied the syscall-boundary success evidence that the LSM event
alone could not provide.

The first and last event timestamps were separated by 0.941, 0.625, 0.650 and
0.725~ms in the four exploit windows. These intervals show that the four
observations fell well inside the configured five-second sequence window. They
must not be interpreted as detector latency or end-to-end alert-delivery time,
because they measure only the span between kernel event timestamps. Each alert
also retained a single unique host PID across its evidence, confirming the
local same-process correlation used in this scenario.

The monitor and the exploit client observed related but distinct outcomes. The
alert demonstrates that the shell and \texttt{cat} transitions occurred and
that the flag file was successfully opened. It does not demonstrate that the
file contents were returned through the service and received by the trigger.
This distinction became visible in the third exploit run, where the detector
completed the same four-event sequence but the client received an empty flag
value and exited with status 1.

\section{Performance Evaluation}
\label{sec:evaluation-performance}

\subsection{Metrics, Sampling and Benchmark Profiles}
\label{subsec:evaluation-performance-method}

The filtered profile ran the monitor with the exact UID 10001 kernel filter.
The unfiltered profile used the same policy, detector, alert mode and workload
without that filter. The no-monitor profile removed the monitor container and
served only as context for the target workload. Before every run, the Pod was
deleted, recreated under the selected profile and allowed to reach readiness.
The order was rotated over five rounds rather than randomised.

The filtered and unfiltered profiles preserved the same event policy, detector,
alert-only output and exploit workload. Their intended independent variable was
therefore the exact kernel-side UID admission setting. The no-monitor profile
changed a broader part of the Pod by removing the monitor container and its host
mounts. It was retained to show the scale and variability of the target
workload, not as an otherwise identical control for causal overhead estimation.

Container CPU was calculated from cgroup-v1 \texttt{cpuacct.usage} deltas,
which report accumulated cgroup CPU time in nanoseconds, divided by wall-clock
deltas \cite{linux_cgroup_v1_cpuacct}. A value of 100\% represents one fully used core.
Node CPU was derived from \path{/proc/stat} and used the complete two-core node
as its 0--100\% scale. Cgroup memory usage and resident set size (\gls{rss}) were
collected separately because they describe different boundaries: cgroup memory
can include charged pages beyond the resident process set. PID counts and the
workload's internal duration were also preserved.

For filtered and unfiltered runs, the primary cgroup belonged to the monitor
and the target was sampled as a secondary container. In the no-monitor profile,
the primary cgroup necessarily belonged to the target. Its CPU and memory
columns therefore cannot be compared directly with the monitor columns or
subtracted as a baseline for monitor overhead.

The maximum cgroup memory attributed to the monitor was 100.51~MiB when
filtered and 112.16~MiB when unfiltered; maximum \gls{rss} was 39.36 and 46.02~MiB.
These maxima describe the resources observed in this campaign rather than a
steady-state requirement. The no-monitor memory values belong to the target and
are included only to characterise the workload context.

Mean node CPU remained close to saturation in every profile: 94.70\% for
filtered, 95.11\% for unfiltered and 94.89\% without the monitor. Workload
duration also varied among repetitions. Although the filtered mean duration was
shorter than the unfiltered mean, the small sample, changing workload cost and
high node utilisation prevent a causal interpretation. The experiment therefore
does not use duration differences to estimate monitor overhead.

\subsection{Observed Difference with Kernel-Side UID Filtering}
\label{subsec:evaluation-uid-filter}

All five filtered monitor run means fell below the project-defined 5\% gate,
ranging from 0.36\% to 0.41\% of one core. The five unfiltered means ranged from
4.73\% to 4.98\%. Under the scripted profiles, enabling exact UID admission was
associated with a reduction from 4.87\% to 0.39\% of one core, or approximately
92.0\% relative to the unfiltered mean. Both profiles were repeated in every
round, but the evidence archive does not retain the rendered monitor
configuration and image identity for each individual replica. The comparison
therefore supports a strong association under the intended profiles rather than
proving that the filter was the sole cause of the difference.

The result remains narrower than a total-overhead statement. Work executed by
eBPF programs in kernel context is not fully represented by the monitor
container's cgroup charge, and the experiment did not isolate host-level kernel
cost. The 5\% result therefore applies to measured monitor-cgroup CPU in the
filtered profile, not to the complete system cost of monitoring.

The functional path remained active in the performance campaign. Each of the
ten monitored runs produced exactly one alert, and none contained a matching
textual perf-loss diagnostic. This supports the claim that filtering preserved
the configured scenario evidence in the observed runs. It does not demonstrate
loss-free transport, because absence of a diagnostic is not an independent
accounting mechanism for every generated record.

\section{Discussion of Results}
\label{sec:evaluation-discussion}

The functional and performance campaigns support three complementary findings.
First, the monitor observed process and file activity produced in the target
container while host PID sharing was disabled at the Pod level. Host process
identity allowed the evidence to be related locally without presenting the
container PID as a global identity. Second, the detector retained the semantic
distinction between executable-transition evidence, file-security mediation and
the successful file-open result. This produced one ordered alert in every
exploit window and avoided interpreting the LSM observation alone as a completed
access.

Third, the scripted profile with early UID admission was associated with
substantially less work charged to the monitor cgroup. The approximately 92.0\%
difference is consistent with the intended benefit of rejecting unrelated
events before transport and user-space processing. However, incomplete per-run
configuration provenance and near-saturated node utilisation prevent a stronger
causal claim or an extension to total overhead and workload acceleration.

The divergent third exploit run also clarifies the monitor's evidence boundary.
The alert correctly represented the host operations it was designed to observe,
including a successful file descriptor return. The empty client result belonged
to a later application and communication outcome outside the detector sequence.
This is not a contradiction between client and monitor; it demonstrates why
observed kernel evidence and end-to-end application success must be reported
separately.

\section{Threats to Validity and Current Limitations}
\label{sec:evaluation-threats-validity}

\noindent\textbf{Internal validity.}
The performance profiles were rotated cyclically rather than randomly assigned.
Recreating the Pod reduced carry-over of container state, but did not remove
host load, cache effects or variation in exploit execution. Sampling through
the Minikube \gls{ssh} path produced intervals longer than the nominal one second.
Because a sample was selected by its endpoint timestamp while its CPU value
covered the preceding interval, the first selected sample could include some
pre-workload activity and the final partial interval could be omitted. The
node was close to saturation in all profiles. In the functional campaign, E3
also showed that client output could fail despite completion of the monitored
host sequence.

\medskip
\noindent\textbf{Construct validity.}
CPU charged to the monitor cgroup is not equivalent to total monitoring
overhead, and target metrics from the no-monitor profile are not a monitor
baseline. Cgroup memory and \gls{rss} cover different resources. Event timestamp
spans do not measure detector or output latency. Likewise, the absence of a
loss diagnostic does not prove loss-free perf-buffer transport. The functional
interpretation also depends on preserving the difference between an LSM
mediation event and the successful syscall return.

\medskip
\noindent\textbf{External validity.}
The experiment used one Rocky Linux kernel build, one Docker-backed Minikube
node, one Kubernetes version, one public \gls{ctf} challenge and one detector tailored
to that challenge. The benign interaction represented only a narrow control.
No alternative kernels, long-duration workloads, multi-node deployments or
production workload mixtures were evaluated. The results therefore describe
the tested node-local scenario and should not be generalised to arbitrary
container environments.

\medskip
\noindent\textbf{Conclusion validity.}
Five repetitions per performance profile and seven functional windows support
descriptive comparisons, not inferential statistics or accuracy rates. The
approximately 92.0\% profile difference applies to the selected event scope,
UID and workload on the observed node. The per-run performance archive does not
retain every rendered monitor configuration and image identity, so it cannot
independently establish that the UID filter was the only realised difference.
Differences in target CPU, memory or duration likewise do not establish a
causal performance effect. ATT\&CK metadata provides alert classification and
does not validate detector coverage.

\section{Evaluation Summary}
\label{sec:evaluation-summary}

The experiment demonstrated node-local observation of target-container process
and file activity, completion of the configured four-event collective sequence
in four controlled exploit windows, and no alert in three selected benign
windows. Under the scripted performance profiles, exact UID filtering was
associated with an approximately 92.0\% lower mean CPU charge than the
unfiltered profile, with all five filtered run means below the local 5\% gate.
These findings validate the intended workflow within the stated environment
while leaving total overhead, broad detection accuracy and multi-node behaviour
outside the supported claims.
Chapter~7 uses these bounded results to draw the final conclusions and identify
future work.
