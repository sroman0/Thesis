\chapter{Requirements and System Design}
\label{ch:requirements-system-design}

The previous chapter established the technical basis for the work and
positioned the proposed system within the runtime security landscape. Building
on that foundation, this chapter defines the requirements that guide the
system and develops the architecture chosen to satisfy them. The discussion
focuses on the constraints imposed by the target environment and on the
division of responsibility between kernel space and user space.

The design is guided by a simple principle: work that depends directly on the
observed kernel operation should remain small and bounded, whereas
higher-level interpretation should take place in user space, where it can
evolve without increasing verifier-sensitive kernel logic. An explicit event
contract connects the two domains. Once an observation crosses this boundary,
policies determine whether it belongs to the monitored scope, while
independently configured detectors evaluate individual events or short ordered
sequences. These choices are presented here at the architectural level, leaving
their concrete implementation to Chapter 4 and their experimental assessment
to Chapter 5.

\section{Design Goals and Constraints}
\label{sec:design-goals-constraints}

The system is designed to provide focused visibility into security-relevant
host activity rather than an exhaustive account of kernel execution. Its event
domain therefore centres on process execution and on operations that affect the
security state of the monitored host. The architecture must allow this domain
to be selected according to the monitoring objective, while presenting the
resulting observations through a consistent typed event model. Security
interpretation should then operate on that model without requiring the
detection logic to be embedded in the eBPF programs.

This design is shaped primarily by the characteristics of the target
environment and by the continuous nature of runtime telemetry. Kernel
capabilities must be established on the concrete enterprise system, since its
reported upstream version does not fully describe the available functionality.
At the same time, frequent observations require the system to avoid unnecessary
collection and to limit the state retained for ongoing detections. Any loss or
failure along the event pipeline must also remain observable, so that missing
telemetry is not interpreted as evidence that no relevant activity occurred.

\subsection{Target Environment and Compatibility Assumptions}
\label{subsec:target-environment-assumptions}

The target environment is Rocky Linux 8.10 on x86-64, running the exact kernel
build \path{4.18.0-553.109.1.el8_10.x86_64}. This target belongs to a
long-lived enterprise kernel line in which selected fixes and features are
backported while the reported upstream base version remains stable. The
nominal version therefore cannot be used alone to infer the effective eBPF
capabilities of the host; the functionality required by the monitoring system
must be confirmed on the deployed kernel
\cite{redhat2025backporting}.

The architecture assumes that the monitored host exposes usable kernel
\gls{btf} information and grants the privileges required to load and attach the
selected programs. As discussed in Chapter~2, BTF and \gls{core} can adapt
compatible differences in kernel data-structure layout, but they cannot provide
missing kernel functionality, bypass permissions, or guarantee verifier
acceptance
\cite{linux_btf,linux_bpf_llvm_relocations,linux_libbpf_overview,
linux2026ebpfverifier}. 

This target-aware design deliberately bounds the portability claim. The system
is designed around the identified Rocky Linux environment and is not assumed
to operate unchanged across arbitrary distributions or kernel configurations.
Dynamic probes introduce an additional dependence on the availability of
kernel symbols and compatible function signatures. Loading and attachment
failures must consequently be detected before monitoring begins, rather than
allowing the runtime to continue with an incomplete observation domain.

\section{System Architecture}
\label{sec:overall-system-architecture}

The architecture separates a control path from a data path. The control path
prepares the runtime by validating the configuration and rule definitions,
determining which events and detectors are admitted, and resolving each logical
event to the kernel programs required for its observation. The data path starts
when one of these programs is triggered and carries the resulting observation
through transport and user-space processing until it is presented as an event
or, when a detector condition is satisfied, as an alert. Operational
diagnostics accompany both paths but remain separate from the monitoring data
they describe.

\subsection{Kernel-Space and User-Space Responsibilities}
\label{subsec:kernel-userspace-responsibilities}

Figure~\ref{fig:kernel-userspace-architecture} summarises the division of
responsibilities between kernel space and user space, together with the
control, monitoring, and diagnostic interactions that cross this boundary.

Kernel space is responsible for observing the operations selected during
bootstrap and for constructing the corresponding logical events. When an
attached hook is reached, the associated eBPF program extracts bounded process
context and event-specific arguments, applies the optional exact-match
effective-UID guard, and serialises the resulting record according to the
shared binary contract. The completed record is then submitted through the
perf buffer used as the primary kernel-to-user-space transport channel \cite{linux_bpf_helpers}.

Some operations require information that is not available at a single
instrumentation point. In these cases, an entry-side program preserves a
limited amount of temporary state and a later return-side program completes
the event with the operation outcome. This entry/exit model is used only for
event construction. It does not introduce policy evaluation or detection logic
into the kernel.

User space owns the more changeable and semantically rich responsibilities.
During bootstrap, the Go runtime validates the configuration, policies, and
detector definitions, derives the effective event scope, resolves the
dependencies of the selected logical events, and determines which eBPF
programs must be loaded and attached. It manages this lifecycle through
\texttt{libbpf} and its Go bindings, \texttt{libbpfgo}
\cite{aquasecurity_libbpfgo}. In this role, \texttt{libbpf} provides the
user-space facilities required to load eBPF objects and manage programs, maps,
and attachments, while \texttt{libbpfgo} exposes those facilities to the Go
runtime.

During monitoring, the runtime receives binary records from the perf buffer,
decodes their context and indexed arguments, and converts them into normalised
events. The policy predicates that could not be resolved during bootstrap,
including constraints that depend on decoded process information and
suppression rules, are then evaluated in user space. Events admitted by this
gate may be routed to the event output and are also dispatched to the detector
engine constructed from the detector definitions selected during bootstrap. 
Point detectors evaluate individual events, whereas collective
detectors correlate short ordered sequences within bounded temporal and state
limits. Only successful detector evaluations produce alerts, which are routed
through an output path distinct from raw event presentation.

The diagnostic path is implemented through the structured Zap logging library
\cite{uber_zap}, forming a third independent stream. These diagnostics describe 
conditions affecting the control or data path while remaining distinct from both 
monitored events and detector alerts. These records may describe conditions 
affecting either the control path or the data path, but they are not represented 
as monitored events or detector alerts.

The boundary is therefore selective rather than absolute. User space controls
which kernel programs are loaded and may configure the narrow kernel-side UID
guard, while kernel programs may retain short-lived state needed to complete a
record. Higher-level policy interpretation, event normalisation, detection,
and presentation remain in user space. Conversely, user-space processing
depends on the correctness and delivery of the records constructed in kernel
space and cannot recover an observation that was rejected before submission or
lost during transport.

\subsection{End-to-End Event Lifecycle}
\label{subsec:end-to-end-event-lifecycle}

Before collection begins, the configuration, policy rules, and detector
definitions are validated. Where the active policies provide exact event
allowlists, these may narrow the event scope requested through the remaining
configuration. Policies may also restrict the available detector catalogue
before the detector runtime is constructed. The probe registry then resolves
the resulting public logical events into the producer programs and internal
dependencies required to construct them, while unrelated registered programs
are excluded from loading and attachment.

Once monitoring is active, reaching a selected hook invokes its associated
eBPF program. The Go runtime decodes the record according to the event registry 
and converts it into a normalised event. It then evaluates the remaining event 
and process constraints whose application depends on decoded user-space context. 
An admitted event may be routed  independently to event presentation and to the 
relevant detectors selected during  bootstrap. Disabling event presentation 
therefore does not prevent detector evaluation. A successful single-event or 
collective detector evaluation produces an alert that preserves the source 
observations responsible for the match and propagates the available MITRE ATT\&CK metadata.

\section{Kernel-Space Collection Design}
\label{sec:kernel-space-collection-design}

Kernel instrumentation must expose evidence that is both meaningful for the
logical event and obtainable on the target kernel. The design therefore does
not prescribe one universal attachment mechanism. It combines available
observation points while maintaining a stable event abstraction above them.

\subsection{Hook Selection and Logical Events}
\label{subsec:hook-selection-logical-events}

Hook selection begins with the semantics required from the observation. The
chosen point must expose the relevant stage of the operation, which may be the
initial request, a resolved kernel object, a state transition, or a security
mediation decision. An entry-side observation is sufficient when the attempted
operation is itself meaningful. When the distinction between success and
failure affects the interpretation of the event, a compatible return-side
observation is also required.

The choice is further constrained by the observation points available on the
concrete target and by their expected cost and robustness. An explicit
tracepoint is preferable when it exposes the required semantics, whereas a
dynamic probe may extend coverage where no suitable tracepoint exists, at the
cost of stronger dependence on kernel symbols, function signatures, and
calling conventions. Similarly, a dedicated observation point is preferred
over a high-frequency generic hook when it provides equivalent evidence more
selectively. These are design-time decisions derived from the properties of
the kernel mechanisms discussed in Chapter~2, rather than choices made
automatically while the system is running.

used to describe instrumentation and event production.

The relationships between these concepts are not necessarily one-to-one. A
logical event may require an entry probe to preserve request information and a
return probe to complete the record with the operation outcome. Different
operation variants may also converge on the same logical event. Conversely,
selecting one public event may activate support probes that maintain required
context but do not produce independently decodable records. Separating these
attachment units from the public event abstraction prevents target-specific
probe mechanics from becoming part of the user-facing event contract.

\subsection{Early Event Selection and Kernel-Side Filtering}
\label{subsec:early-event-selection-filtering}

The public event abstraction introduced in the previous subsection also
defines the unit of early selection. Rather than requiring the operator to
identify individual eBPF programs, the architecture starts from the logical
events that the monitoring scenario is expected to produce. For each selected
event, the probe registry determines the producer probes responsible for its
construction and any support probes on which those producers depend.

The resulting dependency set determines which registered programs enter the
loading lifecycle. Programs that cannot contribute to the selected event
domain are excluded before they are submitted to the kernel for verification
and loading, and are consequently not attached to their hooks. This approach
reduces the active observation surface while preserving the internal probes
needed to construct each requested event. It also keeps the public selection
interface independent from the particular arrangement of hooks and programs
used on the target kernel.

Selective loading applies only to programs represented by the probe registry.
It is not a general removal of every unused section contained in the compiled
eBPF object, and its correctness depends on the registry describing producers
and support dependencies completely. An omitted dependency could leave a
selected event without information required for its construction, whereas an
incorrectly exposed support probe could make an internal mechanism appear as
an independently selectable event.

A further reduction can be applied after an attached program is invoked. The
optional exact-UID guard compares the effective UID of the current task with
one configured value and rejects non-matching observations before complete
context enrichment, record serialisation, and transport. The guard therefore
avoids part of the kernel-side and transport work associated with observations
known to be outside that narrow scope.

The guard is intentionally limited to a single equality condition and serves
as a representative form of inexpensive kernel-side pre-filtering. Additional
predicates over values such as process or local cgroup identity could be
introduced where they are available reliably and provide a measurable
reduction in unnecessary collection. More expressive conditions remain in
user space, where they can be evaluated over the complete normalised event
without increasing verifier-sensitive kernel logic.

\section{Event Contract and Transport Design}
\label{sec:event-contract-transport-design}

Kernel-side producers and the user-space consumer require a common
representation that remains consistent across heterogeneous event sources.
The design combines a bounded binary transport contract with an explicit
registry for semantic interpretation. These elements must evolve together:
omitting repeated schema metadata from each record reduces transport
redundancy, but also means that identifiers, encodings, and registry
definitions must remain aligned.

\subsection{Stable Binary Event Contract}
\label{subsec:stable-binary-event-contract}

Each public record contains a common event context followed by indexed,
typed arguments. The context carries the identity and provenance information
shared across event families, including process, host, namespace, and
execution context. Event-specific arguments describe the observed operation,
while their indices associate the encoded values with the schema maintained by
the user-space event registry.

The representation is intentionally not fully self-describing. The kernel
producer emits an event identifier and the encoded argument values, whereas
the event registry supplies the corresponding public name, argument types, and
expected ordering. This avoids transporting the same semantic metadata with
every observation, but creates an explicit compatibility obligation between
the kernel definitions, the Go protocol representation, the decoder, and the
event registry.

The contract remains valid only while the producer and consumer agree on the
common context layout and each public event identifier resolves to a single
compatible schema. The indices, types, and encodings of the supplied arguments
must also agree with that schema. A record with an unknown identifier or an
inconsistent structure is therefore reported and discarded before it reaches
policy evaluation, detector processing, or presentation. The runtime does not
convert such a record into a partially trusted event.

Decoding and normalisation are related but distinct stages. The decoder first
validates the common record structure and resolves the event identifier through
the registry. It can then interpret each indexed argument according to the
registered schema and verify that the delivered payload is structurally
consistent. Only a successfully decoded record is converted into the common
normalised representation consumed by policies, detectors, and output
components.

The probe registry does not define the binary schema, but it must remain
consistent with the same logical interface. Every probe that produces a public
event must refer to an event identifier for which the user-space registry
provides a valid decoding contract. The implementation mechanisms that realise 
and preserve these relationships are discussed in Chapter~4.

\subsection{Perf-Buffer Transport and Failure Boundaries}
\label{subsec:perf-buffer-failure-boundaries}

The operational event path uses perf-event transport, in which records are
delivered through per-CPU perf ring buffers ( \texttt{BPF\_MAP\_TYPE\_PERF\_EVENT\_ARRAY}). 
This mechanism should not be confused with the BPF ring-buffer facility represented by
\texttt{BPF\_MAP\_TYPE\_RINGBUF}. Although both use circular buffering, the
former maintains separate buffers for individual CPUs, whereas the latter
provides a shared multi-producer ring buffer
\cite{linux_perf_ring_buffer,linux_bpf_ring_buffer}.

Compatibility with the target kernel was the principal reason for selecting
perf-event transport. The perf-event interface is available on the deployed
Rocky Linux environment, whereas the BPF ring buffer belongs to a later
upstream kernel generation and cannot be assumed to be present through a
vendor backport. The transport used by every event was therefore based on the
interface verified on the concrete target.

The BPF ring buffer offers advantages on compatible kernels, including shared
capacity across CPUs and stronger ordering between records submitted to the
same buffer. Perf-event transport instead uses per-CPU buffers, which may use
memory less efficiently under uneven load and do not provide a total ordering
across CPUs. These properties were accepted in favour of target compatibility
and a simpler operational design.

The choice was also influenced by the evolution of the prototype. An
intermediate version maintained both perf-buffer and BPF ring-buffer readers,
even though their records eventually entered the same decoding pipeline.
Converging on perf-event transport removed duplicated lifecycle and
failure-handling paths and ensured that the transport no longer depended on
which probe produced the event. This decision does not demonstrate that perf
buffers are generally faster, since no controlled comparison between the two
mechanisms was performed.

Perf-event delivery remains asynchronous and finite. Records may be lost when
a per-CPU buffer cannot be consumed quickly enough, and the resulting loss
notification does not allow the missing observations to be reconstructed. A
delivered record may instead fail during decoding if it violates the active
binary contract. Transport loss and decoding failure are therefore separate
conditions, neither of which implies that the corresponding kernel operation
did not occur.

The per-CPU organisation also limits ordering guarantees. Collective
detectors evaluate sequences according to the order in which records reach the
user-space engine, since the architecture does not reconstruct a total causal
order across CPUs. The effects of transport pressure, loss, and concurrent
delivery are assessed in Chapter~5.

\section{User-Space Runtime Design}
\label{sec:user-space-runtime-design}

The Go runtime coordinates kernel-facing resources with the higher-level event
pipeline. Its components form a controlled runtime lifecycle in which resources
are acquired only after validation and remain under clear ownership, while
failures affecting individual events are contained without disrupting the main
processing loop.

\subsection{Decoding, Normalisation and Event Registration}
\label{subsec:decoding-normalisation-registration}

The decoder forms the user-space validation boundary for records received from
the perf buffer. It first verifies that the common event context and each
encountered argument payload can be read within the delivered record. The event
identifier is then resolved through the event registry, and argument indexes
are interpreted according to the registered schema. This process produces a
typed \texttt{bufferdecoder.Event} containing the common context, the logical
event name, and the decoded arguments.

Only a record with a decodable context, a known event identifier, and argument
records that can be interpreted using the registered schema enters the policy
and detector pipeline. The decoder rejects records that cannot be safely reconciled 
with the registered schema and configured bounds, for example when the payload is truncated, 
the event identifier is unknown, or an encoded string exceeds the permitted size. It does
not, however, require every schema argument to be present, reject duplicate
argument indexes, or require the complete payload to be consumed. The decoding
contract therefore establishes bounded and typed interpretation rather than
strict canonical encoding.

The event registry and the probe registry describe separate aspects of the
same logical interface. The event registry is authoritative for public event
identifiers, names, and argument schemas used by decoding and configuration
validation. The probe registry instead defines the attachable eBPF programs,
their kernel hooks and attachment methods, and any support dependencies needed
to produce a logical event.

The separation between the two registries preserves distinct architectural
responsibilities: the event registry defines the decoding contract, whereas
the probe registry defines how the corresponding observations are produced.
Their alignment is enforced through consistency checks that verify that public
logical events have a valid decoder definition and that internal support probes
remain outside the public event-selection interface. The relationships between
physical probes and logical events are already discussed in
Section~\ref{subsec:hook-selection-logical-events}.

The decoded event provides the typed representation passed to subsequent
user-space stages, while its use by policies, detectors, and presentation
components is discussed in Sections~\ref{sec:policy-detection-architecture}
and~\ref{subsec:event-alert-logging}. Records that cannot be
decoded are instead reported and discarded at this boundary, preventing
unknown or partially interpreted data from entering the normalised event
stream while allowing later valid records to continue through the monitoring
loop.

\subsection{Event Output, Alert Output and Operational Logging}
\label{subsec:event-alert-logging}

The output architecture preserves three semantically distinct result classes:
monitored events, detector alerts, and operational diagnostics. This separation
is not merely presentational. Event output exposes telemetry admitted by the
active policy scope, alert output exposes security results derived from
detector matches, and operational logging describes the state of the monitoring
infrastructure itself.

Each class follows an independent output contract. Event presentation is a
terminal consumer of the normalised event stream and may be disabled without
removing the corresponding observations from policy evaluation or detector
dispatch. Alert presentation is similarly separated from detector evaluation:
changing its representation does not alter the matching condition or the
structured evidence retained by the alert. Presentation decisions therefore
do not affect collection and detection semantics.

Operational diagnostics remain outside both security-data paths. The runtime
uses the Uber Zap library to provide structured logging for lifecycle state,
libbpf messages, transport loss, decoding and detector failures, presentation
errors, and cleanup conditions. Zap is used only for diagnostic reporting; it
does not serialise monitored events or detector alerts. Events and alerts are
handled by their respective output components and retain formats suited to
interactive or machine-oriented consumption \cite{uber_zap}.

This separation prevents infrastructure conditions from being interpreted as
monitored behaviour. For example, a decoding failure is reported through Zap
rather than being converted into an event, while a detector failure is not
represented as a security alert. Diagnostic verbosity and encoding can
therefore be adapted to the deployment environment without changing the event
or alert interfaces exposed to downstream consumers.

The three paths also define separate failure boundaries. A presentation or
diagnostic failure must not invalidate a successfully decoded event, alter
detector evaluation, or prevent the remaining paths from progressing. Some
startup failures occur before the Zap logger is constructed and are returned
directly to the process entry point. This is an outer lifecycle boundary rather
than an additional output class; once the managed runtime has been created,
Zap provides the structured diagnostic path shown in
Figures~\ref{fig:kernel-userspace-architecture} and~\ref{fig:binary-event-contract}.

\section{Policy and Detection Architecture}
\label{sec:policy-detection-architecture}

Policies and detectors are separate, configuration-driven stages over the
normalised event stream. This separation follows an established runtime
security pattern rather than constituting novelty by itself. Its role in the
prototype is to keep collection scope, detector selection, security
interpretation, and presentation independently configurable within a bounded
host-local design.

\subsection{Policy-Based Event Scope}
\label{subsec:policy-based-event-scope}

A policy defines the portion of the monitored domain that is relevant to a
particular runtime configuration. Its event rules determine whether a
normalised event is admitted according to its identity and selected process
attributes. Suppression rules take precedence over non-suppressive matches,
while the absence of configured policies leaves the decoded event stream
unrestricted by this layer.

Part of this scope can be resolved before monitoring begins. When the active
non-suppressive rules provide explicit event allowlists, their combined event
domain can narrow the selection passed to the probe registry. An event scope
also supplied through the remaining configuration is combined with this result
before the required producer and support probes are resolved. Constraints that
depend on decoded process information, together with suppression decisions,
remain in the user-space path. Policy handling is therefore divided between an
optional bootstrap-time reduction of the observation domain and an
authoritative admission decision over decoded events; it is not implemented as
a complete kernel-side policy engine.

Policies may also restrict the configured detector catalogue during bootstrap.
Detector selectors can refer to explicit detector identifiers or to metadata
such as severity, MITRE ATT\&CK classification, tags, and whether a detector
retains state. Values within the same selector category are combined as
alternatives, while constraints from different categories must be satisfied
together. Exclusions take precedence over inclusions, and the selections
produced by multiple non-suppressive policies are combined before the detector
engine is constructed.

This detector selection remains separate from event admission. It determines
which configured detector definitions are instantiated and therefore avoids
allocating runtime or correlation state for excluded detectors, but it does not
create distinct detector pipelines for individual policies. Policy mode and
intent metadata do not alter the execution model, and matched policy names are
not automatically propagated into detector alerts. These boundaries distinguish
the implemented scope model from the broader policy capabilities reviewed in
Chapter~2.

\subsection{Point and Collective Detectors}
\label{subsec:point-collective-detectors}

Detector definitions are loaded independently from policies. Their event
references and conditions are validated before the runtime begins, and the
dispatcher indexes them by the events they consume. This avoids evaluating
every detector for every event and isolates a detector-local error from the
remaining detector set.

A point detector evaluates deterministic predicates over one normalised event.
When the predicates match, it creates an alert containing that source event.
A collective detector instead defines an ordered sequence of event conditions.
It retains a partial match until a later admitted event advances the sequence,
the sequence completes, or its local state is discarded. Neither model learns
a behavioural baseline or calculates a statistical anomaly score.

Detector event declarations are consumer requirements, not attachment
instructions. They are checked against the event registry, but they do not
automatically enlarge the collection scope. An operator must select compatible
events through the monitoring configuration or policies. A valid detector may
otherwise remain inactive because one of its required observations is not
produced.

Sequence order is the order in which events arrive at the user-space detector
engine. The design does not search backwards, reorder observations, or infer a
causal graph. This bounded model supports the short collective patterns defined
for the prototype while avoiding a claim of general complex-event processing
\cite{cugola2012processing,agrawal2008eventstreams}.

\subsection{Bounded Local Correlation}
\label{subsec:bounded-local-correlation}

Each collective detector defines how the events in its ordered sequence must
be related. The available local relationships distinguish a stable process, an
immediate parent-to-child transition, the same file resource, the same local
cgroup, or a conjunction of these dimensions. A partial match is retained only
within a short configurable interval and a bounded number of correlation keys.
When the sequence completes, the alert preserves the ordered events that
satisfied it; otherwise, the incomplete state expires, is replaced for the
same key, or is evicted.

Stable process correlation distinguishes separate process lifetimes even when
the operating system later reuses the same numeric process identifier.
Process-tree correlation remains deliberately shallow: a sequence may stay
within one process or move from a parent observation to its immediate child,
but it does not traverse arbitrary ancestry or construct a persistent process
graph.

Resource correlation identifies the same local file object rather than relying
on a pathname string. This permits related activity from different processes
to be joined while avoiding the assumption that an equal path always denotes
the same object. Cgroup correlation can similarly connect processes sharing a
local kernel cgroup identity. It does not attribute events to a Kubernetes pod,
workload, tenant, or cluster-wide identity.

A composite relationship requires every configured dimension to agree; it is
a conjunction rather than a fallback among alternative keys. User-session
correlation is rejected because the normalised event model does not expose a
stable session identity, and UID alone would merge unrelated activity.

Only one partial sequence is retained for a detector and correlation key. A
new first step for that key can replace the existing incomplete sequence.
State is bounded by time and by a per-detector key limit, although total memory
also depends on detector count, sequence length, and retained event payloads.
Expired state is reclaimed during relevant detector activity or an explicit
flush, not by a general periodic scheduler in the main runtime.

\subsection{Alert Evidence and MITRE ATT\&CK Metadata}
\label{subsec:alert-evidence-attack}

An alert is a derived detector result rather than an operational log message.
A point alert preserves the source event that satisfied its predicates, while
a collective alert preserves the ordered sequence accumulated by the detector.
This evidence makes the result traceable to the runtime observations on which
it is based and allows machine-oriented output to retain more detail than a
compact interactive summary.

Detector definitions may associate this evidence with MITRE ATT\&CK tactics,
techniques, data sources, and data components. The metadata is copied into the
resulting alert, providing a shared vocabulary through which the intended
security meaning can be communicated and organised
\cite{strom2020attack}. The mapping is part of detector configuration rather
than policy selection.

Validation establishes that configured tactic and technique identifiers follow
the expected syntactic form. It does not consult an authoritative ATT\&CK
catalogue at runtime, verify the semantic correctness of the mapping, or
demonstrate complete coverage. These limitations do not remove the value of
the metadata: preserving the mapping alongside the evidence supports
interpretation, traceability, and later coverage analysis. The final assessment
of representative detector mappings belongs to Chapter~5.

\section{Design Decisions and Scope Boundaries}
\label{sec:design-decisions-boundaries}

The architecture follows a series of deliberate trade-offs. Bounded
kernel-space collection is preferred to embedding complex, verifier-sensitive
analysis in each probe. The Go runtime owns policy and detector semantics so
that those definitions can evolve without recompiling the kernel programs.
Selective loading and attachment are preferred to activating every registered
probe, and an explicit shared event contract is preferred to ad hoc payload
interpretation.

Perf buffers are used because they are supported by the reference environment
and runtime stack; BPF ring-buffer transport remains a non-implemented
alternative. Policy scope is kept separate from detector logic, and detector
results are kept separate from operational logging. Collective detection uses
short, local, evidence-preserving sequences rather than persistent graphs or a
general-purpose event-processing system.

These decisions define the limits of the prototype. It does not implement
enforcement, prevention, machine-learning anomaly discovery, user-session
correlation, arbitrary process ancestry, cluster-wide correlation, or
Kubernetes workload attribution. It does not claim complete Linux event or
MITRE ATT\&CK coverage, universal kernel portability, or universal compliance
with the performance objective.

Container packaging supports later operational use but is an implementation
concern described in Chapter~4. A wider platform may eventually aggregate
alerts from several monitored hosts and add deployment context, but that
external capability is neither implemented nor evaluated as part of this
thesis. Within its stated boundary, the proposed system provides a coherent
path from selected kernel observations to normalised telemetry and
evidence-preserving local detections on the identified enterprise kernel.
