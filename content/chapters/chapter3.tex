\chapter{Requirements and System Design}
\label{ch:requirements-system-design}

Chapter~2 introduced the kernel mechanisms on which the monitoring system is
built. This chapter turns those foundations into concrete requirements and an
overall system design. Particular attention is given to the constraints of the
target environment and to the boundary between kernel-space collection and
user-space processing.

Code that runs in the kernel is kept small and bounded. Interpretation takes
place in user space, where it can change without adding verifier-sensitive
logic to every eBPF program. A shared event contract links the two sides.
Policies use the resulting events to define the monitored scope, and detectors
look for configured conditions in individual observations or short ordered
sequences. This chapter describes those choices as architecture; Chapters~4
and~5 cover their kernel- and user-space implementations, and Chapter~6
evaluates the resulting system.

\section{Design Goals and Constraints}
\label{sec:design-goals-constraints}

The system targets security-relevant host activity, with an emphasis on
process execution and operations that can alter the host security state. It is
not intended to reproduce every kernel action. Operators must be able to choose
the required event domain, while all selected observations retain a consistent
typed representation. Detection logic then works on this representation rather
than being embedded in the collection programs.

Runtime telemetry is continuous, so unnecessary collection and unbounded
detection state would steadily consume resources. Losses and processing
failures must also be reported explicitly, since silence alone cannot show that
no relevant operation took place. Compatibility constraints are defined for the
target environment below.

\subsection{Target Environment and Compatibility Assumptions}
\label{subsec:target-environment-assumptions}

The target environment is Rocky Linux 8.10 on x86-64, running the exact kernel
build \path{4.18.0-553.137.1.el8_10.x86_64}. This target belongs to a
long-lived enterprise kernel line in which selected fixes and features are
backported while the reported upstream base version remains stable. The
nominal version therefore cannot be used alone to infer the effective eBPF
capabilities of the host; the functionality required by the monitoring system
must be confirmed on the deployed kernel
\cite{redhat2025backporting}.

The architecture assumes that the monitored host exposes usable kernel
\gls{btf} information and grants the privileges required to load and attach the
selected programs. As discussed in Chapter~2, BTF and \gls{core} can adapt
compatible differences in kernel data-structure layout, but they cannot provide
missing kernel functionality, bypass permissions, or guarantee verifier
acceptance
\cite{linux_btf,linux_bpf_llvm_relocations,linux_libbpf_overview,
linux2026ebpfverifier}. 

Portability is therefore limited to compatible systems and not assumed for
all Linux distributions and kernel configurations. Dynamic probes also depend
on available symbols and compatible function signatures. The runtime must
detect loading or attachment failures before monitoring starts, otherwise the
active event coverage could differ silently from the requested one.

\section{System Architecture}
\label{sec:overall-system-architecture}

The architecture has a control path and a data path. The control path validates
configuration and rule definitions, selects events and detectors, and maps each
logical event to the kernel programs needed to observe it. The data path begins
when one of those programs runs. It carries the captured record through
transport and user-space processing, producing an event or, after a detector
match, an alert. Operational diagnostics report problems in either path without
becoming monitoring data themselves.

\subsection{Kernel-Space and User-Space Responsibilities}
\label{subsec:kernel-userspace-responsibilities}

Figure~\ref{fig:kernel-userspace-architecture} shows the responsibilities on
either side of the kernel--user-space boundary and the interactions between
them.

In kernel space, selected eBPF programs collect process context and
operation-specific evidence, construct bounded records and submit them through
the perf-event channel. Some events require short-lived state to combine an
entry observation with its return. An optional exact effective-\gls{uid} filter
can reject a record before submission. Policy evaluation and security
classification are not performed at this stage.

User space manages configuration and the parts expected to change more often.
The Go runtime determines the event scope, translates logical events into a
probe set, loads and attaches programs through \texttt{libbpfgo}, decodes
records and runs policies and detectors \cite{aquasecurity_libbpfgo}. Events,
alerts and operational diagnostics use separate output paths because they
represent different kinds of information.

This division keeps kernel work constrained and lets the interpretation layer
change independently. It also exposes an important limitation: user space
cannot recover a record rejected in kernel space or lost before decoding.

\subsection{End-to-End Event Lifecycle}
\label{subsec:end-to-end-event-lifecycle}

Before collection begins, the validated configuration, policies and detector
definitions establish the logical event scope. The probe registry expands it
into public producers and any required support probes; unrelated programs stay
disabled. During monitoring, a hook produces a binary record, which is
transported and decoded against the event registry. User-space policy
constraints then admit or reject the event. Admitted events can be presented
and evaluated by detectors. A successful point or sequence match produces an
alert containing the source evidence and available MITRE ATT\&CK metadata.
Operational diagnostics remain outside this data path: they report runtime
conditions without becoming monitored events or detector evidence. The event
lifecycle also does not establish a total order across observations.
Perf-event transport uses per-CPU buffers, so collective detectors use the
order in which records reach the user-space engine.
Section~\ref{subsec:perf-buffer-failure-boundaries} discusses this ordering
constraint together with transport loss.

\section{Kernel-Space Collection Design}
\label{sec:kernel-space-collection-design}

Kernel instrumentation must provide evidence that is meaningful for the
logical event and available on the target kernel. No single attachment
mechanism meets both needs in every case, so the design combines several kinds
of observation point behind one stable event abstraction.

\subsection{Hook Selection and Logical Events}
\label{subsec:hook-selection-logical-events}

Chapter~2 established how the observation point determines event semantics.
At design time, the system therefore selects the smallest practical set of
hooks that provides the evidence required by each event. The choice must also
be available on the target kernel and avoid unnecessarily frequent attachment
points. Stable, dedicated hooks are preferred when they expose sufficient
information; dynamic probes are used where the exported interfaces leave a
coverage gap.

These concepts do not have a one-to-one relationship. A logical event may have
several producers and may depend on support probes that retain intermediate
context without emitting a record. The public event contract therefore remains
independent of the physical arrangement used to construct it.

\subsection{Early Event Selection and Kernel-Side Filtering}
\label{subsec:early-event-selection-filtering}

Early selection operates on logical events, so operators do not need to name
individual eBPF programs. For each requested event, the probe registry finds
its producers and any support probes they require.

This dependency set determines which registered programs enter the loading
lifecycle. Programs outside it are disabled before kernel verification and are
not attached. The active observation surface is reduced without dropping the
internal programs needed to construct a selected event.

Selective loading covers programs represented in the probe registry, not every
section that could exist in the compiled object. Correctness depends on a
complete description of producers and dependencies. A missing dependency can
leave a selected event incomplete; exposing a support probe incorrectly can
turn an internal mechanism into an apparent public event.

An optional exact \gls{uid} guard provides a second reduction after a program
has been invoked. It compares the task's effective \gls{uid} with one configured
value and rejects a mismatch before full context enrichment, serialisation and
transport. This avoids work for observations known to be outside that narrow
scope.

The guard deliberately supports only one equality condition. Other cheap
predicates, such as process or local cgroup identity, could be added if their
inputs are reliable and the reduction is measurable. Richer conditions stay in
user space, where the complete normalised event is available.

\section{Event Contract and Transport Design}
\label{sec:event-contract-transport-design}

Kernel producers and the user-space consumer share one representation across
all event sources. It combines a bounded binary record with a registry that
supplies its meaning. Because records omit repeated schema metadata, event
identifiers, encodings and registry definitions must evolve together.

\subsection{Stable Binary Event Contract}
\label{subsec:stable-binary-event-contract}

Each public record begins with a common event context and continues with
indexed arguments. The context carries shared identity and provenance data for
the process, host, namespaces and execution environment. Event-specific
arguments describe the observed operation; their indices refer to entries in
the user-space schema.

The record is not fully self-describing. A kernel producer writes the event
identifier and encoded values; the registry supplies the public name, argument
types and ordering. This saves repeated metadata, at the cost of requiring the
kernel definitions, Go protocol, decoder and registry to agree.

Unknown or structurally inconsistent records are discarded before policies,
detectors or output components can use them. The probe registry does not define
the wire schema, but every public producer must refer to an event known by the
event registry. Chapter~4 covers record production and Chapter~5 covers the
receiving registries and admission path.

\subsection{Perf-Buffer Transport and Failure Boundaries}
\label{subsec:perf-buffer-failure-boundaries}

The event path uses perf-event transport through a
\texttt{\gls{bpf}\_MAP\_TYPE\_PERF\_EVENT\_ARRAY}. It was selected because it is
available on the target kernel; the alternative transport models were compared
in Chapter~2. This choice gives each CPU an independent finite buffer and does
not establish a total order across CPUs \cite{linux_perf_ring_buffer}.

Perf-event delivery is asynchronous and finite. If user space cannot drain a
per-CPU buffer quickly enough, records may be lost and cannot be reconstructed
from the loss notification. A record that arrives can still fail decoding if
it violates the binary contract. These are separate failures, and neither
shows that the corresponding kernel operation did not occur.

Collective detectors consequently use arrival order rather than a reconstructed
causal order across CPUs. Chapter~6 reports the perf-loss diagnostics observed
under the experimental workload but does not independently measure transport
loss.

\label{sec:user-space-runtime-design}

The Go runtime connects kernel collection to analysis. Lifecycle management,
record interpretation and presentation have separate responsibilities, giving
each resource and failure a clear owner. Their implementation is described in
Chapter~5.

\subsection{Decoding, Normalisation and Event Registration}
\label{subsec:decoding-normalisation-registration}

The decoder is the boundary between transported bytes and the typed events
shared by policies, detectors and output. The event registry defines their
public identifiers and argument schemas, while the separate probe registry
maps them to producer and support programs. Records without a valid schema are
rejected before reaching downstream components. Chapter~5 describes the
decoder and the consistency checks between these registries.

\subsection{Event Output, Alert Output and Operational Logging}
\label{subsec:event-alert-logging}

The architecture distinguishes admitted events, detector alerts and operational
diagnostics. Suppressing ordinary event output does not disable detector
evaluation, and runtime failures are never represented as monitored activity.
Chapter~5 covers their formats and error handling.

\section{Policy and Detection Architecture}
\label{sec:policy-detection-architecture}

The analytical subsystem is prepared before monitoring begins. Policy and
detector documents are validated and compiled into a plan that later admits
events and evaluates matches without changing the active kernel
instrumentation.

\subsection{Policy-Based Event Scope}
\label{subsec:policy-based-event-scope}

Policies define which observations belong to a monitoring scenario. A finite
event scope can reduce collection before the eBPF object is loaded; an
open-ended scope retains the broader plan. Policies may also narrow the detector
catalogue through metadata. Conditions that require decoded values are applied
in user space, and a rejected event reaches neither output nor detectors. With
no policy, this admission boundary is permissive.

All active policies contribute to one effective monitoring plan, not separate
pipelines. Policies choose relevant observations and detectors; detectors
decide whether admitted evidence should produce an alert. Chapter~5 describes
how both are implemented.

\subsection{Point and Collective Detectors}
\label{subsec:point-collective-detectors}

The terms \emph{point} and \emph{collective} refer to the amount of evidence a
detector needs. A point detector considers one observation. A collective
detector looks for an explicitly configured local sequence. Both are
deterministic and rule based; no baseline is learned and no anomaly score is
calculated.

Both receive the same normalised events used by policies. Point matches can
produce an alert immediately. Collective evaluation retains bounded partial
state until a sequence completes or expires. The two forms share the same
pipeline.

Detector definitions declare their input events but do not attach probes. Those
events must already be present in the monitoring plan when the detector engine
is built, so event-time matching cannot alter kernel instrumentation.

\subsection{Bounded Local Correlation}
\label{subsec:bounded-local-correlation}

Collective detectors relate observations through configured local identities.
A process key combines the host process identifier with its start time, and a
parent relation covers only the immediate parent. Files use a device--inode
pair; cgroups use their node-local kernel identifier. Composite strategies
require every configured dimension to match. None of these keys represents a
persistent process graph, arbitrary ancestry or Kubernetes workload identity.

Partial sequences have finite lifetimes and a per-detector capacity. If the
event model cannot provide a requested correlation dimension, configuration is
rejected rather than approximated with weaker evidence. This supports short
local sequences without introducing a general-purpose complex-event processing
engine \cite{cugola2012processing,agrawal2008eventstreams}. Exact transitions,
limits and pruning behaviour belong to Chapter~5.

\subsection{Alert Evidence and MITRE ATT\&CK Metadata}
\label{subsec:alert-evidence-attack}

An alert preserves detector identity, severity and the evidence that completed
the match: one event for a point detector or an ordered set for a collective
detector. It does not have to be reconstructed from presentation output.

Detector metadata may include MITRE ATT\&CK tactics and techniques. Policies can
use these fields to select definitions, and matching alerts retain them for
classification and downstream organisation \cite{strom2020attack}. The mapping
supplements the detector evidence; Chapter~5 describes how it is validated and
propagated.

\section{Design Decisions and Scope Boundaries}
\label{sec:design-decisions-boundaries}

The design favours reliable observation on the target host over the broadest
possible event catalogue. Selective loading and explicit probe dependencies
limit collection to the event surface supported by that host.

Early filtering is used only where it stays small and verifier compatible.
Policies and detector semantics remain in Go, where they can change without
recompiling the collection layer. The shared event contract supports this
division, and perf-event transport reflects the facilities available on the
reference kernel.

Detection state is similarly constrained. Point detectors and bounded local
sequences add interpretation to raw telemetry without maintaining persistent
graphs, learning statistical models or retaining unbounded correlation state.
The prototype observes and detects; it does not enforce decisions or provide a
general-purpose event-processing service. Chapter~6 evaluates node-local event
visibility, the configured collective detector and monitor-cgroup resource
consumption under the selected profiles.

Alert aggregation across hosts and the addition of external deployment context
are left to a wider platform and are neither implemented nor evaluated here.
The system considered in this thesis ends at node-local, evidence-preserving
detection.
