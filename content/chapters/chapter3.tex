\chapter{Requirements and System Design}
\label{ch:requirements-system-design}

Chapter \ref{ch:ebpf-architecture} introduced the kernel mechanisms on which the monitoring system is
built. This chapter turns those foundations into concrete requirements and an
overall system design. Particular attention is given to the constraints of the
target environment and to the boundary between kernel-space collection and
user-space processing.

Code that runs in the kernel is kept small and bounded. Interpretation takes
place in user space, where it can change without adding verifier-sensitive
logic to every eBPF program. A shared event contract links the two sides.
Policies use the resulting events to define the monitored scope, and detectors
look for configured conditions in individual observations or short ordered
sequences. This chapter describes those choices as architecture; Chapters \ref{ch:kernel-space-implementation}
and \ref{ch:user-space-implementation} cover their kernel- and user-space implementations, and Chapter \ref{ch:experimental-evaluation}
evaluates the resulting system.

\section{Design Goals and Constraints}
\label{sec:design-goals-constraints}

The system targets security-relevant host activity, with an emphasis on
process execution and operations that can alter the host security state. It is
not intended to reproduce every kernel action. Operators must be able to choose
the required event domain, while all selected observations retain a consistent
typed representation. Detection logic then works on this representation rather
than being embedded in the collection programs.

Runtime telemetry is continuous, so unnecessary collection and unbounded
detection state would steadily consume resources. Losses and processing
failures must also be reported explicitly, since silence alone cannot show that
no relevant operation took place. Compatibility constraints are defined for the
target environment below.

\subsection{Target Environment and Compatibility Assumptions}
\label{subsec:target-environment-assumptions}

The target environment is Rocky Linux 8.10 on x86-64, running the exact kernel
build \path{4.18.0-553.137.1.el8_10.x86_64}. This target belongs to a
long-lived enterprise kernel line in which selected fixes and features are
backported while the reported upstream base version remains stable. The
nominal version therefore cannot be used alone to infer the effective eBPF
capabilities of the host; the functionality required by the monitoring system
must be confirmed on the deployed kernel
\cite{redhat2025backporting}.

The architecture assumes that the monitored host exposes usable kernel
\gls{btf} information and grants the privileges required to load and attach the
selected programs. As discussed in Chapter~2, BTF and \gls{core} can adapt
compatible differences in kernel data-structure layout, but they cannot provide
missing kernel functionality, bypass permissions, or guarantee verifier
acceptance
\cite{linux_btf,linux_bpf_llvm_relocations,linux_libbpf_overview,
linux2026ebpfverifier}. 

Portability is therefore limited to compatible systems and not assumed for
all Linux distributions and kernel configurations. Dynamic probes also depend
on available symbols and compatible function signatures. The runtime must
detect loading or attachment failures before monitoring starts, otherwise the
active event coverage could differ silently from the requested one.

  components. Each event must identify the observed operation and expose its
  available context such as the process involved, the accessed
  resource or the returned result. The system must preserve the meaning of
  these fields.

  FR-03 lets operators narrow monitoring to a particular scenario without
  changing the software. Configuration files called policies can select or
  exclude activity using event names, process names, user identifiers and
  operation details. For example, a policy may retain file-access events
  involving a particular path. Policies can also restrict the active security

  their sequence order where applicable. It must also report the configured
  severity and any supplied security classification metadata.

  FR-06 supports both direct inspection and further processing of results.
  Text output allows terminal use, while JSON allows other software to read
  the observations and alerts. Operational messages, such as collection or
  processing errors, must be distinguishable from the monitored activity.

  FR-07 supports controlled operation of the monitor. Invalid configuration
  must be reported before collection begins, and failures that prevent startup
  must be visible to the operator. When monitoring is stopped, or startup fails
  after resources have been acquired, those resources must be released.

\section{System Architecture}
\label{sec:overall-system-architecture}

The architecture has a control path and a data path. The control path validates
configuration and rule definitions, selects events and detectors, and maps each
logical event to the kernel programs needed to observe it. The data path begins
when one of those programs runs. It carries the captured record through
transport and user-space processing, producing an event or, after a detector
match, an alert. Operational diagnostics report problems in either path without
becoming monitoring data themselves.

\label{subsec:kernel-userspace-responsibilities}

Figure~\ref{fig:kernel-userspace-architecture} shows the responsibilities on
either side of the kernel--user-space boundary and the interactions between
them.

In kernel space, selected eBPF programs collect process context and
operation-specific evidence, construct bounded records and submit them through
the perf-event channel. Some events require short-lived state to combine an
entry observation with its return. An optional exact effective-\gls{uid} filter
can reject a record before submission. Policy evaluation and security
classification are not performed at this stage.

User space manages configuration and the parts expected to change more often.
The Go runtime determines the event scope, translates logical events into a
probe set, loads and attaches programs through \texttt{libbpfgo}, decodes
records and runs policies and detectors \cite{aquasecurity_libbpfgo}. Events,
alerts and operational diagnostics use separate output paths because they
represent different kinds of information.

This division keeps kernel work constrained and lets the interpretation layer
change independently. It also exposes an important limitation: user space
cannot recover a record rejected in kernel space or lost before decoding.

\subsection{End-to-End Event Lifecycle}
\label{subsec:end-to-end-event-lifecycle}

Before collection begins, the validated configuration, policies and detector
definitions establish the logical event scope. The probe registry expands it
into public producers and any required support probes; unrelated programs stay
disabled. During monitoring, a hook produces a binary record, which is
transported and decoded against the event registry. User-space policy
constraints then admit or reject the event. Admitted events can be presented
and evaluated by detectors. A successful point or sequence match produces an
alert containing the source evidence and available MITRE ATT\&CK metadata.
Operational diagnostics remain outside this data path: they report runtime
conditions without becoming monitored events or detector evidence. The event
lifecycle also does not establish a total order across observations.
Perf-event transport uses per-CPU buffers, so collective detectors use the
order in which records reach the user-space engine.
Section~\ref{subsec:perf-buffer-failure-boundaries} discusses this ordering
constraint together with transport loss.

\section{Kernel-Space Collection Design}
\label{sec:kernel-space-collection-design}

Kernel instrumentation must provide evidence that is meaningful for the
logical event and available on the target kernel. No single attachment
mechanism meets both needs in every case, so the design combines several kinds
of observation point behind one stable event abstraction.

\subsection{Hook Selection and Logical Events}
\label{subsec:hook-selection-logical-events}

Hooks are selected according to the information required by each event and
  their availability on the target kernel. The choice also considers how often
  the attached collection program will run. A hook reached by many unrelated
  operations requires repeated checks to discard activity outside the selected
  scope. Where possible, the design therefore uses hooks specific to the
  operation being monitored.

  Dedicated tracepoints are preferred when they expose the required
  information. Dynamic probes provide access to kernel functions when suitable
  tracepoints are unavailable or insufficient. Multiple hooks may be needed
  to observe both the request and the outcome of an operation.

used to describe instrumentation and event production.

The operator selects logical events without having to identify the individual
kernel programs required to collect them. The system maps each selection to
its producer probes and support dependencies. This allows the collection
mechanism to change while preserving the public event name and schema.

\subsection{Early Event Selection and Kernel-Side Filtering}
\label{subsec:early-event-selection-filtering}

Early selection operates on logical events, so operators do not need to name
individual eBPF programs. For each requested event, the probe registry finds
its producers and any support probes they require.

This dependency set determines which registered programs enter the loading
lifecycle. Programs outside it are disabled before kernel verification and are
not attached. The active observation surface is reduced without dropping the
internal programs needed to construct a selected event.

Selective loading covers programs represented in the probe registry, not every
section that could exist in the compiled object. Correctness depends on a
complete description of producers and dependencies. A missing dependency can
leave a selected event incomplete; exposing a support probe incorrectly can
turn an internal mechanism into an apparent public event.

An optional exact \gls{uid} guard provides a second reduction after a program
has been invoked. It compares the task's effective \gls{uid} with one configured
value and rejects a mismatch before full context enrichment, serialisation and
transport. This avoids work for observations known to be outside that narrow
scope.

The guard deliberately supports only one equality condition. Other cheap
predicates, such as process or local cgroup identity, could be added if their
inputs are reliable and the reduction is measurable. Richer conditions stay in
user space, where the complete normalised event is available.

\section{Event Contract and Transport Design}
  \label{sec:event-contract-transport-design}

  The event contract is the agreement between the kernel programs that collect
  observations and the user-space runtime that reads them. It defines how each
  event is identified, which fields it contains and how their values are
  represented. A common format allows observations from different hooks to
  reach the same analysis components.

  \subsection{Stable Binary Event Contract}
  \label{subsec:stable-binary-event-contract}

  Each record contains a common context, an argument count and a sequence of
  event-specific arguments. The context records shared information, including
  the event identifier, timestamp and process identity. The arguments describe
  the operation observed, such as the file accessed or the credentials changed.
  Separating these parts allows events to carry different details while sharing
  the information needed to identify their source.

  Each argument begins with an index followed by its encoded value.
  The event registry associates each event ID with a schema containing
  the argument names and types. The decoder uses the event ID to select
  the schema, then uses each argument index to find the corresponding field.
  Field names and type descriptions are kept in the registry, reducing the
  metadata repeated in transmitted records.

  Figure~\ref{fig:binary-event-contract} illustrates this design through a
  \texttt{security\_file\_open} event. The example shows three selected
  arguments with illustrative values; other arguments are omitted.

  \begin{figure}[H]
      \centering
      \includegraphics[
          width=0.95\textwidth,
          keepaspectratio
      ]{figures/chapter3/Binary_event_contract.drawio.png}
      \caption[Interpretation of an indexed event record]
      {Interpretation of selected \texttt{security\_file\_open} arguments
      using the event registry.}
      \label{fig:binary-event-contract}
  \end{figure}

  The event ID selects the \texttt{security\_file\_open} schema.
  Index 0 identifies \texttt{pathname}, whose value is decoded as a string.
  Indices 1 and 2 identify \texttt{dev} and \texttt{inode}, decoded as
  unsigned 32-bit and 64-bit integers, respectively. The resulting event
  contains these named fields together with the common context.

  Indices also allow individual arguments to be omitted without changing
  the meaning of the remaining fields. Whether a producer continues after
  a collection failure depends on the missing information. For example,
  \texttt{security\_file\_open} stops without submitting a record if it
  cannot obtain the resolved path. When a record is submitted, its argument
  count states how many arguments were written.

  The producer and decoder must agree on identifiers, indices, field widths,
  byte order and variable-length encodings. These definitions are maintained
  separately in C and Go. Registry tests check identifiers and names, while
  decoder tests exercise selected encoded records. Changes to the format
  therefore require review of both the producer and the receiving schema.

  The decoder reports unknown event identifiers, indices outside the selected
  schema and payloads that fail their type-specific checks. Chapter~4 describes 
  record construction, and Chapter~5 covers decoding.

  \subsection{Perf-Buffer Transport and Failure Boundaries}
  \label{subsec:perf-buffer-failure-boundaries}

  Records are transferred through per-CPU perf buffers using a \\
  \texttt{BPF\_MAP\_TYPE\_PERF\_EVENT\_ARRAY} map. This transport was selected
  for its availability on the target kernel. A collection program submits
  a record to the buffer associated with its current CPU, and the user-space
  runtime reads it for processing \cite{linux_perf_ring_buffer}.

  The buffers hold records while collection and processing proceed at
  different rates. Their capacity is finite: if records arrive faster than
  the runtime reads them, a buffer can fill and subsequent records may be
  lost.
  
  The runtime addresses temporary increases in activity by separating reading
  from processing. A dedicated reader retrieves records and places them in
  a queue while the processing loop decodes and analyses earlier events.
  This allows reading to continue during short processing delays, provided
  the queue still has space.

  Selective collection also reduces the incoming workload. Programs unrelated
  to the selected events remain disabled, and the optional UID filter rejects
  observations outside its configured scope before transport. Each submission
  includes only the populated part of the record, reducing buffer use.

  If processing remains slower than collection, the queue eventually fills
  and blocks the reader. The perf buffers may then fill as well.
  The runtime reports loss notifications from the reader as warning messages.
  These contain the number of reported losses, but no information from which
  the missing records can be recovered. Decoding failures are logged separately
  to distinguish them from transport losses.

  Missing observations may prevent a detector from completing a sequence.
  Collection diagnostics therefore help interpret an interval without alerts.
  Chapter~6 reports whether perf-loss warnings appeared in the retained experimental logs.

\subsection{Decoding, Normalisation and Event Registration}
\label{subsec:decoding-normalisation-registration}

The decoder is the boundary between transported bytes and the typed events
shared by policies, detectors and output. The event registry defines their
public identifiers and argument schemas, while the separate probe registry
maps them to producer and support programs. Records without a valid schema are
rejected before reaching downstream components. Chapter~5 describes the
decoder and the consistency checks between these registries.

\subsection{Event Output, Alert Output and Operational Logging}
\label{subsec:event-alert-logging}

The architecture distinguishes admitted events, detector alerts and operational
diagnostics. Suppressing ordinary event output does not disable detector
evaluation, and runtime failures are never represented as monitored activity.
Chapter~5 covers their formats and error handling.

\section{Policy and Detection Architecture}
  \label{sec:policy-detection-architecture}

  Policies select the activity relevant to a monitoring task and the detectors
  to enable. Detectors examine the selected observations and generate alerts
  when their conditions match. Before monitoring begins, the runtime prepares
  a plan containing the events to collect, the filters to apply and the
  detectors to run. These choices remain fixed during the monitoring session.

  \subsection{Policy-Based Event Scope}
  \label{subsec:policy-based-event-scope}

  Policies can filter observations by event name, process command, UID and
  argument values. They can also select detectors by identifier or metadata,
  such as severity and tags.

  The example assumes one active policy and an available detector definition

  The operator initially selects three event types. The policy retains two,
  so the programs used only for \texttt{chmod} are left disabled.
  The UID condition is checked after decoding: events from other UIDs reach
  neither event output nor detectors. This condition does not automatically
  enable the separate kernel UID filter.

  Before monitoring starts, the system compares the events selected
  by the operator with those listed in the policies. When all rules that admit
  activity list the events they need, collection is limited to the event types
  shared by the two selections. If a rule allows any event type, the operator's
  selection is kept. Conditions on process names, UIDs and argument values
  are then checked after the events have been collected and decoded.

  All active policies contribute to one shared plan. An event must match an
  allowing policy, and a matching suppression policy overrides that decision.
  Without policies, events pass this gate. Selecting detectors determines
  which checks run; it does not independently enable additional kernel events.

  \subsection{Point and Collective Detectors}
  \label{subsec:point-collective-detectors}

  A point detector evaluates one event against configured conditions.
  For example, \texttt{file-access-check} could generate an alert when a
  file-opening observation identifies a specified sensitive path.

  A collective detector evaluates an ordered sequence of related events.
  For example, a check may require a credential change followed by program
  execution by the same process. Events are considered in their arrival order.
  A configured time window limits how long the runtime waits for completion,
  starting when it stores the first matching observation.

  Both forms use explicit, deterministic conditions and consume the same
  decoded event model. Chapter~5 explains how their definitions are loaded
  and evaluated.

  \subsection{Bounded Local Correlation}
  \label{subsec:bounded-local-correlation}

  Sequence detection requires a way to identify observations that belong
  together. Several processes can share a UID, so that value alone cannot
  establish that two events came from the same process. Process correlation
  uses the host PID and process start time, distinguishing separate lifetimes
  that reuse the same PID.

  Other supported relationships use the immediate parent process, a file's
  device and inode numbers, or a local cgroup identifier. Several dimensions
  can be combined when all must agree.

  Incomplete sequences are subject to the time and capacity limits stated
  in Section~\ref{subsec:nonfunctional-operational-requirements}.
  Unsupported correlation strategies are rejected during configuration.
  An event that cannot provide a valid correlation key does not advance
  a sequence. Chapter~5 describes how this state is stored and removed.

  \subsection{Alert Evidence and MITRE ATT\&CK Metadata}
  \label{subsec:alert-evidence-attack}

  An alert identifies the detector, reports its configured severity and
  preserves the observations that satisfied its conditions. 
  The analyst can inspect this evidence to understand why the alert was raised.

  Detector definitions may include MITRE ATT\&CK labels describing the attack
  tactics and techniques they are intended to identify \cite{strom2020attack}.
  Policies can use these labels to choose which detectors to enable.

\section{Design Decisions and Scope Boundaries}
\label{sec:design-decisions-boundaries}

The design favours reliable observation on the target host over the broadest
possible event catalogue. Selective loading and explicit probe dependencies
limit collection to the event surface supported by that host.

Early filtering is used only where it stays small and verifier compatible.
Policies and detector semantics remain in Go, where they can change without
recompiling the collection layer. The shared event contract supports this
division, and perf-event transport reflects the facilities available on the
reference kernel.

Detection state is similarly constrained. Point detectors and bounded local
sequences add interpretation to raw telemetry without maintaining persistent
graphs, learning statistical models or retaining unbounded correlation state.
The prototype observes and detects; it does not enforce decisions or provide a
general-purpose event-processing service. Chapter~6 evaluates node-local event
visibility, the configured collective detector and monitor-cgroup resource
consumption under the selected profiles.

Alert aggregation across hosts and the addition of external deployment context
are left to a wider platform and are neither implemented nor evaluated here.
The system considered in this thesis ends at node-local.
