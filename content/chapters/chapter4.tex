\chapter{Kernel-Space Event Collection Implementation}
\label{ch:kernel-space-implementation}

This chapter describes the kernel-space implementation of the design presented
in Chapter \ref{ch:requirements-system-design}. It begins with the build artefacts and common event-construction
code, then examines the implemented hook families, binary record format,
perf-buffer transport, early \gls{uid} admission and compatibility work for the
target Rocky Linux kernel. Chapter \ref{ch:user-space-implementation} takes over at the user-space boundary;
Chapter \ref{ch:experimental-evaluation} evaluates the completed system.

The project combines C sources for kernel collection with a Go application
  for loading, event processing and detection. Figure~\ref{fig:build-toolchain}
  shows how these sources and their dependencies produce the executable.

  The build first compiles the local libbpf sources into a static library
  and prepares their headers and package metadata. Clang then compiles the
  collection sources into an eBPF object, using definitions for the target

  ways. The library is linked to provide kernel-facing operations, while
  the eBPF object is embedded as bytes in the executable. At startup, the
  runtime can retrieve those bytes to load the collection programs.
  The usual deployment therefore requires no separate eBPF object beside
  the executable, although an external object can be supplied for development
  and compatibility testing.

\section{eBPF Program Implementation}
\label{sec:implementation-ebpf-programs}

The eBPF object contains programs for several hook types. Most records follow
one of two construction patterns. A direct producer creates and submits an
event during one invocation. A paired producer saves request arguments at
entry and completes the event when a return hook supplies the result.

Physical hooks and public events are not in one-to-one correspondence. Several
programs may produce one logical schema, while support programs can be attached
without emitting public events.

\subsection{Shared Event-Construction Framework}
\label{subsec:implementation-shared-event-construction}

Both patterns build records in a reusable per-CPU workspace instead of placing
the full event structure on the limited eBPF stack. Other per-CPU maps hold
temporary path and kernel-object data. Task and process maps retain context
that can be reused across invocations.

The common initialiser clears the argument buffer and records basic identity
and timing data. The hook appends its own fields, after which the submission
helper refreshes the full task context and sends the populated record through
the interface described in Section~\ref{sec:implementation-binary-contract}.

Listing~\ref{lst:ebpf-shared-construction} shows the main stages shared by these
helpers. Details related to process-map initialisation and optional stack
capture are omitted because they do not change the event-construction process.

\begin{lstlisting}[
      language=C,
      basicstyle=\ttfamily\footnotesize,
      caption={Shared event construction and submission path.},
      label={lst:ebpf-shared-construction}
  ]
  if (!p->event)
      p->event = bpf_map_lookup_elem(&event_data_map, &zero);
  if (!p->event)
      return 0;

  p->config = bpf_map_lookup_elem(&config_map, &zero);
  if (!p->config)
      return 0;

  reset_event_args_buf(p->event);
  p->event->task = (struct task_struct *) bpf_get_current_task();

  u64 id = bpf_get_current_pid_tgid();
  p->event->context.task.host_tid = id;
  p->event->context.task.host_pid = id >> 32;
  p->event->context.eventid = event_id;

  init_task_context(&p->event->context.task,
                    p->event->task, p->config->options);

  u32 size = sizeof(event_context_t) + sizeof(u8) +
             p->event->args_buf.offset;
  long ret = bpf_perf_event_output(
      p->ctx, &events, BPF_F_CURRENT_CPU, p->event, size);

  update_event_stats(p->event->context.eventid, ret);
  return ret;
  \end{lstlisting}

Submission copies the populated prefix into the perf-event channel, after which
the per-CPU workspace can be reused. Later writes cannot alter the submitted
record. If the workspace, configuration or task context is unavailable, the
invocation ends without producing an event.

The full helper also checks the record size and can update delivery statistics.
Listing~\ref{lst:ebpf-shared-construction} concentrates on the transport
boundary; Section~\ref{sec:implementation-binary-contract} covers the exact
bounds.

Paired producers save argument values at entry and retrieve them when the
return program collects the result. The map key combines the event identifier
with the calling host thread. Saved values may include user-space pointers:
storing a pointer does not copy the data it references. If that data is read
at exit, it may have changed or become unreadable since entry.

\begin{lstlisting}[
      language=C,
      basicstyle=\ttfamily\footnotesize,
      caption={Saving and recovering arguments for paired producers.},
      label={lst:ebpf-entry-state}
  ]
  statfunc u64 get_args_id(u32 event_id)
  {
      return ((u64) event_id << 32) |
             (u32) bpf_get_current_pid_tgid();
  }

  statfunc int save_args(args_t *args, u32 event_id)
  {
      u64 key = get_args_id(event_id);
      bpf_map_update_elem(&args_map, &key, args, BPF_ANY);
      return 0;
  }

  statfunc int load_args(args_t *args, u32 event_id)
  {
      u64 key = get_args_id(event_id);
      args_t *saved = bpf_map_lookup_elem(&args_map, &key);
      if (!saved)
          return -1;

      /* Fixed argument-slot copies are omitted. */
      return 0;
  }
\end{lstlisting}

The seven argument slots are copied explicitly so that each access remains
statically bounded for the verifier. If lookup fails, the return program cannot
reconstruct the request and emits no record.

The return program deletes the entry after copying it and then appends the
result. Entry updates use \texttt{\gls{bpf}\_ANY}, so a later request can replace
state left behind by a missed return. This map is temporary construction state,
not a process history.

The hook families below reuse these patterns, but the meaning of a record still
depends on its observation point. Syscall entry captures a request. A security
hook exposes an operation under mediation, usually without the final decision.
A committed-state hook sees installed state, and a lifecycle tracepoint reports
a completed transition. Exit or return probes add the result visible at that
boundary.

\subsection{Process Lifecycle and Executable Transitions}
\label{subsec:implementation-process-execution-hooks}

Process creation is visible both as a syscall and as a scheduler transition.
The syscall records the requested operation and returned result; scheduler
tracepoints observe tasks after creation, rename or termination. Both views are
kept because they answer different questions.

\subsubsection{Process Creation and Lifecycle}

The \texttt{fork} and \texttt{vfork} events provide the simplest syscall-level
view of process creation. Their schemas contain only the return value, so their
entry probes do not retain any arguments. A positive result identifies the
child returned to the caller, while a negative result records the reported
error.

The \texttt{clone} event monitors task creation, including new threads
that share resources with the caller. The recorded flags describe
which resources are shared, such as memory and file descriptors. The exit probe adds the returned child identifier
or error.

The \texttt{sched\_process\_fork} tracepoint runs after the child task exists and
receives both task structures. It records the host \gls{pid} and \gls{tid} of
parent and child, together with the child's start time. The corresponding
source excerpt is retained in Listing~\ref{lst:sched-process-fork}.

\begin{lstlisting}[
    language=C,
    basicstyle=\ttfamily\scriptsize,
    caption={Parent-child identity collected by
    \texttt{sched\_process\_fork}.},
    label={lst:sched-process-fork}
]
struct task_struct *parent =
    (struct task_struct *) ctx->args[0];
struct task_struct *child =
    (struct task_struct *) ctx->args[1];

u32 parent_pid = get_task_host_tgid(parent);
u32 parent_tid = get_task_host_pid(parent);
u32 child_pid = get_task_host_tgid(child);
u32 child_tid = get_task_host_pid(child);
u64 child_start = get_task_start_time(child);

save_to_submit_buf(&p.event->args_buf,
                   &parent_pid, sizeof(u32), 0);
save_to_submit_buf(&p.event->args_buf,
                   &parent_tid, sizeof(u32), 1);
save_to_submit_buf(&p.event->args_buf,
                   &child_pid, sizeof(u32), 2);
save_to_submit_buf(&p.event->args_buf,
                   &child_tid, sizeof(u32), 3);
save_to_submit_buf(&p.event->args_buf,
                   &child_start, sizeof(u64), 4);
\end{lstlisting}


Because PIDs and TIDs can be reused, the start time lets user space distinguish
separate task lifetimes with the same numeric identifier. The same combination
is used as a process identity for local detector correlation.

Two direct tracepoints cover later lifecycle changes.
\texttt{task\_rename} records the previous and new command names when the task
name changes. This operation is kept separate from executable replacement
because a command-name change does not imply that a new program image was
installed. The \texttt{sched\_process\_exit} event records the task's exit code
and whether the complete thread group is terminating, distinguishing a single
thread exit from the end of the process.

These lifecycle relations are emitted as bounded events; the kernel does not
maintain a persistent process graph. Longer-lived reconstruction, where needed,
belongs in user space.

\subsubsection{Executable Transitions}

Executable-transition monitoring retains the requested program as well as the
outcome. Pathname and arguments are available at syscall entry, but that point
cannot show whether the kernel installed the new image. Separate hooks cover
the request, binary security processing and final result.

\begin{figure}[H]
    \centering
    \includegraphics[
        width=0.85\textwidth,
        keepaspectratio
    ]{figures/chapter4/execution_monitoring.drawio.png}
    \caption[Execution monitoring: attempts and outcomes]
    {Events used to observe execution requests, kernel security processing
    and executable-transition outcomes.}
    \label{fig:execution-monitoring}
\end{figure}

Figure~\ref{fig:execution-monitoring} shows the events used at each stage of the execution process. 
These events do not always form a one-to-one sequence. Binary handlers and
interpreters may invoke the security hooks several times during one execution
request. Moreover, the security hooks describe intermediate processing and do
not report whether execution ultimately succeeded.

The \texttt{execve} and \texttt{execveat} events describe the execution
requested by a process. They record the pathname and up to 38 argument strings,
allowing an analyst to identify the requested program and command line.
\texttt{execveat} also records the directory file descriptor and flags needed
to interpret relative or descriptor-based execution. As entry events, neither
contains a result.

The \texttt{security\_bprm\_check} event identifies the executable file that
the kernel resolved and submitted to its binary security checks. 
The event records the resolved pathname, device, inode, original filename, 
argument count and environment count, tying the request to a resolved kernel object.

\texttt{security\_bprm\_creds\_for\_exec} observes credential preparation for program execution, 
which may change privileges. It captures the same binary identity and adds the file change time. 
Prepared credentials are not necessarily installed; committed transitions are covered
in Section~\ref{subsubsec:implementation-identity-credentials}.

The \texttt{sched\_process\_exec} event confirms successful execution.
It records the execution filename and, where available, the resolved path
and file metadata. It also collects bounded argument and environment data,
their counts, the real UID and identifiers derived from process and thread
lifetimes. These fields help identify the executable and how it was started.

The \texttt{process\_execute\_failed} event instead reports a failed
\texttt{execve} or \texttt{execveat}. It records the operation type,
directory file descriptor, pathname read at syscall exit, flags and
negative return value.

The failure event uses paired entry and exit programs. The entry program
stores the operation, directory file descriptor, flags and pathname pointer.
The exit program retrieves these values, reads the pathname and adds the
syscall result. Listing~\ref{lst:process-execute-failed} shows this processing.

\begin{lstlisting}[
    language=C,
    basicstyle=\ttfamily\scriptsize,
    caption={Return-side emission of failed executable transitions.},
    label={lst:process-execute-failed}
]
args_t args = {};
if (load_args(&args, PROCESS_EXECUTE_FAILED) != 0)
    return 0;
del_args(PROCESS_EXECUTE_FAILED);

if (ret >= 0)
    return 0;

program_data_t p = {};
if (!init_program_data(&p, ctx, PROCESS_EXECUTE_FAILED))
    return 0;

int operation = (int) args.args[0];
int dirfd = (int) args.args[1];
const char *pathname = (const char *) args.args[2];
int flags = (int) args.args[3];

save_to_submit_buf(&p.event->args_buf,
                   &operation, sizeof(int), 0);
save_to_submit_buf(&p.event->args_buf,
                   &dirfd, sizeof(int), 1);
if (pathname)
    save_str_to_buf(&p.event->args_buf, (void *) pathname, 2);
save_to_submit_buf(&p.event->args_buf,
                   &flags, sizeof(int), 3);
save_to_submit_buf(&p.event->args_buf,
                   &ret, sizeof(long), 4);
return events_perf_submit(&p);
\end{lstlisting}

The exit program first removes the temporary state. A successful syscall
produces no failure event, while a negative return value is submitted together
with the saved request. The implementations for \texttt{execve} and
\texttt{execveat} use the same public event schema.

\subsection{Identity, Credentials, Process Control and Limits}
\label{subsec:implementation-identity-control-hooks}

\subsubsection{Identity and Credentials}
\label{subsubsec:implementation-identity-credentials}

A set-ID syscall alone cannot describe every privilege transition. Credentials
may also change during executable loading or through internal kernel paths, and
a security hook sees a proposal before it becomes active. The implementation
therefore records identity requests, mediation, committed credentials and
capability checks at separate points.

\begin{figure}[H]
    \centering
    \makebox[\textwidth][c]{%
        \includegraphics[
            width=0.85\textwidth,
            keepaspectratio
        ]{figures/chapter4/real_effective_saved_uid.png}
    }
    \caption[Real, Effective, Saved and Filesystem UIDs]
    {Real, effective, saved and filesystem UIDs for a process \cite{gazestani2025linuxuids}.}
    \label{fig:real-effective-saved-uid}
\end{figure}

Linux associates each process with several user and group identifiers. The
real ID represents the identity under which the process was started, while the
effective ID is used for most access-control decisions. The saved ID allows a
process to retain an effective identity that may later be restored, supporting
temporary privilege reduction and recovery. Linux also maintains filesystem
IDs, which are used specifically during filesystem permission checks. The same
distinction applies to user and group credentials \cite{gazestani2025linuxuids}.

A process can change its effective or filesystem privileges without changing
its real identity. A saved identity may also allow dropped privileges to be
restored. Monitoring only the real ID would miss these changes in effective
authority \cite{gazestani2025linuxuids}.

Identity requests are captured through the \texttt{setuid},
\texttt{setgid}, \texttt{setreuid}, \texttt{setregid},
\texttt{setresuid}, \texttt{setresgid}, \texttt{setfsuid} and
\texttt{setfsgid} events. Their entry programs retain one, two or three
identifiers according to the syscall interface. This distinguishes single-ID,
real/effective, real/effective/saved and filesystem-specific requests. Exit
programs append the returned value.

Return semantics differ across this family. Most operations report a status,
but \texttt{setfsuid} and \texttt{setfsgid} return the previous filesystem
identity. User space therefore needs the originating event to interpret the
value correctly.

The \texttt{security\_task\_fix\_setuid} hook adds the mediation view. It
records the old and proposed real, effective, saved and filesystem UIDs,
together with a flag that distinguishes the set-ID operation category. The
eBPF program compares the two credential proposals and suppresses the event
when none of the monitored \gls{uid} fields changes. Since the hook is observed
before installation and its result is not captured, the record describes a
transition under examination, not a confirmed change.

No public \texttt{security\_task\_fix\_setgid} event is currently exposed.
Group-ID requests remain visible through the set-group syscall events, while
changes that become active are included in the broader
\texttt{commit\_creds} event.

The \texttt{commit\_creds} hook runs when replacement credentials become active.
It converts the installed and replacement credentials into fixed-width
snapshots containing real, effective, saved and filesystem user and group IDs,
the user-namespace ID, secure bits and the inheritable, permitted, effective,
bounding and ambient capability sets.

Credential installation is frequent, and many invocations do not alter a field
used by the monitor. The two snapshots are compared before submission. Listing
\ref{lst:commit-creds-filter} shows this change-only emission strategy.

\begin{lstlisting}[
    language=C,
    basicstyle=\ttfamily\footnotesize,
    caption={Kernel-side suppression of unchanged credential snapshots
    .},
    label={lst:commit-creds-filter}
]
slim_cred_t old_slim = {};
slim_cred_t new_slim = {};

/* Identifiers, namespace, secure bits and capability
 * sets are copied into the two snapshots. */

if (old_slim.uid == new_slim.uid &&
    old_slim.gid == new_slim.gid &&
    old_slim.euid == new_slim.euid &&
    old_slim.egid == new_slim.egid &&
    /* Remaining monitored fields are compared here. */
    old_slim.cap_ambient == new_slim.cap_ambient)
    return 0;

save_to_submit_buf(&p.event->args_buf,
                   &old_slim, sizeof(slim_cred_t), 0);
save_to_submit_buf(&p.event->args_buf,
                   &new_slim, sizeof(slim_cred_t), 1);

return events_perf_submit(&p);
\end{lstlisting}

Unchanged snapshots never enter the perf-event channel. When a relevant field
differs, the event preserves both states, so analysis does not depend on finding
an earlier credential record.

The \texttt{cap\_capable} event observes checks for individual Linux
privileges, called capabilities. The recorded capability identifies
the privilege being checked, helping the analyst recognise attempts
to perform privileged operations.

\subsubsection{Process Control and Limits}
\label{subsubsec:implementation-process-control-limits}

These events monitor how processes inspect or control other processes,
handle signals and manage resource limits. Security hooks record requests
while the kernel checks them; paired syscall probes also collect the
returned result \cite{linux_lsm_development}.

The \texttt{ptrace} event monitors requests to inspect or control another
process, such as reading its memory or registers and controlling its
execution. These operations support debugging but can also expose or alter
another process's state. The event records the request code, target PID,
address and data arguments, together with the syscall return value.
Arguments are retained as raw values; referenced memory is not copied.

The \texttt{security\_task\_kill} event monitors permission checks for
sending signals to a target task. Signals can request termination, stop
execution or notify a process of an event. The common context identifies
the calling task, while the payload records the signal and the target's
host PID, TID, real UID and command name. Signal zero is also recorded:
it checks existence and permission without delivering a signal.

Listing~\ref{lst:security-task-kill-relation} shows how the monitor reads
the target's identity directly from the task selected by the kernel.
This gives the analyst a command name and user identity alongside the
numeric process identifiers.

\begin{lstlisting}[
    language=C,
    basicstyle=\ttfamily\footnotesize,
    caption={Target evidence collected by
    \texttt{security\_task\_kill} .},
    label={lst:security-task-kill-relation}
]
u32 target_pid = get_task_host_tgid(target);
u32 target_tid = get_task_host_pid(target);
u32 target_uid = 0;
char target_comm[TASK_COMM_LEN] = {};

const struct cred *target_cred =
    get_task_real_cred(target);
if (target_cred)
    target_uid = BPF_CORE_READ(target_cred, uid.val);

if (bpf_probe_read_kernel_str(
        target_comm, sizeof(target_comm),
        target->comm) <= 0)
    return 0;

save_to_submit_buf(&p.event->args_buf,
                   &target_pid, sizeof(u32), 0);
save_to_submit_buf(&p.event->args_buf,
                   &target_tid, sizeof(u32), 1);
save_to_submit_buf(&p.event->args_buf,
                   &target_uid, sizeof(u32), 2);
save_str_to_buf(&p.event->args_buf, target_comm, 3);
save_to_submit_buf(&p.event->args_buf,
                   &sig, sizeof(int), 4);
\end{lstlisting}

The record shows which task was targeted and which signal was requested.
Because collection occurs before the security check returns, it does not
confirm permission, delivery or the target's response.

The \texttt{security\_task\_prctl} event observes requests made through
\texttt{prctl} to query or change process settings, such as its name or
restrictions on gaining privileges. It records the option and four
arguments. Their meaning depends on the option and is left to user space;
the event does not report whether the request succeeded.

The \texttt{do\_sigaction} event monitors queries and proposed changes to
signal handling. A process may install a handler, ignore a signal or
restore its default action. The event records the signal, whether a new
action was supplied and whether the previous action was requested. It
also captures the current and proposed handler settings, including flags
and the first signal-mask word. Collection occurs at function entry,
so a proposed change is not necessarily applied.

Resource limits control quantities such as CPU time, address-space size
and the number of open file descriptors.
\texttt{security\_task\_setrlimit} records proposed changes: the target's
host PID, resource type, soft limit and hard limit. The soft limit is
the enforced threshold; the hard limit restricts how far an unprivileged
process can raise it. This event does not contain the final decision.

The \texttt{prlimit64} event complements this view by recording requests
to read or change resource limits and their syscall result. It retains
the target PID, resource type and addresses of the new and old limit
structures.

Finally, \texttt{security\_settime64} monitors requests to change the
system clock or timezone. It records the supplied time and timezone
fields. These observations can help investigate clock changes that affect
log timestamps, but do not confirm that the requested change took effect.

\subsection{File and Filesystem Security}
\label{subsec:implementation-filesystem-hooks}

Filesystem events distinguish the name supplied by a process from the object
reached by the kernel. A pathname may be relative, use a directory file
descriptor or contain symbolic links; the Virtual File System resolves these
elements before operating on the object \cite{linuxPathnameLookup}.

Syscall probes preserve the original request and returned result. Security
hooks see the object after pathname resolution. Its device and inode numbers
provide a local identity, since an inode is unique only within its filesystem
\cite{linuxInodeIdentifiers}.

The \texttt{open} event provides the syscall view. Entry probes for
\texttt{open} and \texttt{openat} retain the operation variant, directory file
descriptor, requested pathname, flags and creation mode. Exit probes add either
the returned file descriptor or a negative error. The two syscall variants
share one logical schema while retaining their different calling conventions.

The same design is used for filesystem metadata changes. The \texttt{chmod}
event monitors requests to modify permission bits, which determine whether an
object may be read, written or executed. It combines \texttt{chmod},
\texttt{fchmod} and \texttt{fchmodat}, recording the relevant pathname,
descriptor or directory-relative context, the requested mode and the syscall
result.

The \texttt{chown} event monitors requests to replace the user or group ownership
of an object. It combines \texttt{chown}, \texttt{fchown},
\texttt{fchownat} and \texttt{lchown}, retaining the requested owner and group
identifiers, pathname or descriptor context, flags and returned result.
The operation identifier remains important because \texttt{lchown} changes the
ownership of a symbolic link itself rather than following the link to its
target.

Six entry and exit programs produce the single \texttt{chmod} event, and eight
produce \texttt{chown}. An operation field identifies the originating syscall,
avoiding duplicate public schemas.

\texttt{security\_file\_open} complements the syscall view. It runs after the
Virtual File System has resolved the pathname and built a \texttt{struct file}.
Linux Security Modules may use this point to preserve open-time state and
re-evaluate conditions previously checked through \texttt{inode\_permission}
\cite{linuxKernelSecurityFileOpen}. The event exposes the resolved object under
inspection, not the final LSM decision or syscall result.

From the supplied \texttt{struct file}, the program obtains the resolved
pathname, file flags, device number, inode number and change time. When the
originating syscall is recognised, it also attempts to recover the pathname
argument from the current task register state. Listing
\ref{lst:security-file-open-paths} shows the essential separation between these
two forms of evidence.

\begin{lstlisting}[
    language=C,
    basicstyle=\ttfamily\footnotesize,
    caption={Requested and resolved evidence collected by
    \texttt{security\_file\_open}.},
    label={lst:security-file-open-paths}
]
void *resolved = get_path_str(&file->f_path);
dev_t device = get_dev_from_file(file);
unsigned long inode = get_inode_nr_from_file(file);

void *requested = "";
struct pt_regs *regs = get_current_task_pt_regs();

if (p.event->context.syscall == SYSCALL_OPEN)
    requested = get_syscall_arg1(p.event->task, regs, false);
else if (p.event->context.syscall == SYSCALL_OPENAT)
    requested = get_syscall_arg2(p.event->task, regs, false);

save_str_to_buf(&p.event->args_buf, resolved, 0);
save_to_submit_buf(&p.event->args_buf, &device, sizeof(device), 2);
save_to_submit_buf(&p.event->args_buf, &inode, sizeof(inode), 3);
save_str_to_buf(&p.event->args_buf, requested, 5);
\end{lstlisting}

The requested path shows how the process referred to the file; the resolved
path is reconstructed from the kernel object. Symbolic links, relative
traversal and mount topology may make them differ. Requested-path recovery is
best-effort and may be empty when the syscall or register state cannot be
identified. The resolved object remains available from \texttt{struct file}.

Path reconstruction walks kernel dentries backwards and assembles the result in
per-CPU scratch storage. The traversal is limited to 20 components and a
4096-byte working region so that the verifier can prove finite execution and
memory access. Deep or disconnected paths may be partial or explicitly marked
as disconnected; the result is bounded kernel evidence, not an unconditional
canonical path.

A \texttt{device:inode} pair is a more stable local correlation key than a path
string. It can associate observations that use different paths for the same
object. Correlation remains local and time-bounded because inodes can be reused
and layered filesystems may expose different identities for apparently
equivalent paths.

Other file hooks observe checks and control requests on resolved objects.
\texttt{security\_file\_permission} records the pathname,
device-inode identity, change time and permission mask presented during a
read, write or execution check. It shows that the check occurred, but does not
establish whether access was ultimately granted. This is also a high-volume
observation point, making selective event activation particularly important.

The \texttt{security\_file\_ioctl} event monitors file and device-specific
control requests. It records the resolved target identity, ioctl command and
argument value. The argument is intentionally retained as an opaque value:
its interpretation depends on both the command and the target device, and
decoding every possible structure inside eBPF would increase complexity and
verifier cost.

Directory-entry hooks preserve objects at the point where their namespace
representation may change. \texttt{security\_inode\_unlink} records the path,
device, inode and change time of an entry proposed for removal. Capturing this
identity before the unlink operation is valuable because the pathname may no
longer resolve afterwards.

\texttt{security\_inode\_rename} records the old and new paths, rename flags and
source-object identity. Both paths use the same per-CPU scratch buffer, so the
source must be serialised before destination reconstruction overwrites it.

Creation-related hooks retain evidence specific to the new directory entry.
\texttt{security\_inode\_symlink} records the pathname of the symbolic link and
the caller-supplied target string, which may be relative or may not yet identify
an existing object. The \texttt{security\_inode\_mknod} event observes requests to create
filesystem nodes, including device nodes through which processes can
access character or block devices. It records the pathname,
requested mode and device number of a new special node. The mode identifies the
object type and permission bits, while the device number is meaningful for
character and block devices. Both events observe security mediation and do not
contain a final syscall result.

Mount hooks extend monitoring from individual objects to filesystem mounting and unmounting operations.
\texttt{security\_sb\_mount} records the source name, resolved target path,
filesystem type and mount flags. The filesystem-specific data argument is not
copied because its format varies between filesystems and may contain sensitive
configuration. \texttt{security\_sb\_umount} records the resolved mountpoint,
filesystem type and unmount flags. As entry observations of security hooks,
these events show that the requested topology change reached mediation, not
that it completed successfully.

Filesystem records retain three different facts where available: the process
request, the resolved object under mediation and the returned result. Neither a
pathname request nor an LSM entry observation is treated as proof of success.

\subsection{Memory, Namespace and Cgroup Transitions}
\label{subsec:implementation-memory-namespace-hooks}

Memory mappings govern address-space access and permissions. Namespaces shape
the kernel resources visible to a process, and cgroups place it in a resource
control and accounting hierarchy. Their events cover code loading,
cross-process memory access and changes to local isolation boundaries.

not a mandatory sequence. A memory syscall may not reach its security hook, and
a successful namespace syscall need not change every recorded namespace.

The \texttt{memfd\_create} event records creation of an anonymous,
\gls{ram}-backed file. Such an object initially has no conventional filesystem
pathname, but it may later be mapped into memory or used as an executable
image. The event records the requested name and creation flags, followed by
the returned file descriptor or a negative error. This makes successful
anonymous-file creation distinguishable from a failed attempt without
requiring the monitor to inspect its future contents.

The \texttt{mmap} event records requests to create or modify mappings in a
process address space. Its entry probe retains the requested address, length,
protection mask, mapping flags, file descriptor and offset. The exit probe
adds either the address selected by the kernel or a negative error. These
fields distinguish anonymous mappings from file-backed mappings and identify
requests that combine writable and executable permissions.

The \texttt{mprotect} event monitors requests to change the permissions of an
existing memory range. It records the starting address, length, requested
protection mask and returned status. The related
\texttt{pkey\_mprotect} event additionally records the protection key assigned
to the range. Protection-key support is dependent on the target architecture
and kernel configuration, so the returned value remains necessary for
distinguishing an applied request from an unsupported or rejected operation.

Syscall events describe the request but not the kernel objects examined during
security mediation. The
\texttt{security\_mmap\_file} hook complements \texttt{mmap} for file-backed
mappings. It records the resolved pathname, file flags, device, inode, change
time, requested protections and mapping flags. Anonymous mappings are omitted
because no backing \texttt{struct file} is available; they remain visible
through the syscall event.

The \texttt{security\_file\_mprotect} hook observes a protection change through
the virtual memory area supplied by the kernel. It preserves three distinct
protection values: the permissions requested by user space, the permissions
adjusted by the kernel for security evaluation, and the access bits currently
installed on the region. It also records the region start and length. When the
mapping is file-backed, the event adds its resolved pathname and
device-inode identity; anonymous regions retain the protection and address
evidence without file metadata.

This can show that a writable region is being considered for executable access
and whether it belongs to a resolved file. Because the probe runs at security
hook entry, it contains neither the hook decision nor the final syscall result.

The program reads the supplied virtual memory area directly instead of
searching the process memory-management tree again. This keeps collection
bounded and avoids repeating work already done by the kernel.

The \texttt{process\_vm\_readv} and \texttt{process\_vm\_writev}
events monitor requests to read memory from another process or write
into it. These events 
record the target \gls{pid}, addresses and element counts of the local and remote
I/O-vector arrays, operation flags and the number of bytes transferred or the
returned error. The vector elements and transferred memory contents are not
copied. The events retain the transfer relation without collecting potentially
sensitive payload data.

Namespace events monitor changes to the resource views associated with a
process. The \texttt{setns} syscall requests that the caller join an existing
namespace referenced by a file descriptor. Its event records the descriptor,
the requested namespace type and the returned result. A type value of zero
allows the kernel to infer the namespace type from the descriptor.

The \texttt{unshare} syscall requests that selected execution-context
resources cease to be shared with other processes. Its event records the
complete \texttt{CLONE\_*} flag mask and the syscall result. In combination,
the two events distinguish joining an existing namespace from separating an
execution context.

A successful syscall does not expose the identifiers installed in the task.
\texttt{switch\_task\_ns} provides this state view at
\texttt{switch\_task\_namespaces}, where the kernel replaces the namespace
proxy.

The hook compares the old and proposed namespace sets and emits an event only
when at least one monitored identifier changes. The record contains the task
\gls{pid} and only the new identifiers for the changed mount, PID-for-children, \gls{uts},
\gls{ipc}, network or cgroup namespaces. Unchanged fields are omitted from the
indexed argument stream, keeping the record sparse and suppressing no-op
transitions. User namespaces are not part of this namespace-proxy comparison;
credential-related user-namespace changes are observed separately through the
credential hooks.

Cgroup monitoring covers task placement, not namespace replacement. A cgroup
namespace changes how the hierarchy is presented; attachment changes the node
to which the task belongs.

The \texttt{cgroup\_attach\_task} raw tracepoint reports movement of a task to
a destination cgroup. It records the destination cgroup and hierarchy
identifiers, the supplied cgroup path, target command name, host \gls{pid} and \gls{tid},
and whether the operation concerns the complete thread group. This allows the
monitor to observe containment changes even when the task identity itself
remains unchanged.

The \texttt{cgroup\_mkdir} and \texttt{cgroup\_rmdir} events describe the
lifecycle of the local cgroup hierarchy. Both retain the cgroup identifier,
bounded path and hierarchy identifier supplied at creation or removal. Each is
a local lifecycle observation, not a persistent hierarchy.

Cgroup identifier extraction also contains a compatibility decision specific
to the supported kernel range. The layout of the underlying
\texttt{kernfs\_node} identifier differs between older kernels, newer kernels
and the hidden \gls{kabi} representation used by the target \gls{rhel}-derived kernel.
CO-RE field-existence checks select the available layout at load time, allowing
the same helper to obtain the identifier without hard-coding a single
structure version.

Namespace inode numbers and cgroup identifiers are local kernel identities.
They support comparison and detector correlation on one node, but are not pod,
container or cluster-wide workload identifiers. No persistent namespace graph,
cgroup hierarchy or Kubernetes execution model is reconstructed.

\subsection{Kernel Integrity and Kernel-Facing Activity}
\label{subsec:implementation-kernel-activity-hooks}

Kernel modules, eBPF objects and dynamic instrumentation can inspect or change
kernel behaviour. Their interfaces are legitimate but security-sensitive. The
implemented hooks record the operation, object identity and result available at
each observation point; classification is left to detectors.

Kernel-module monitoring separates lifecycle notifications from initialisation
results. The \texttt{module\_load} raw tracepoint records a
module as it enters the kernel module lifecycle, while
\texttt{module\_free} reports its removal. Both events preserve the module
name and, when available, its version and source-version strings. They do not
copy module code, sections or other internal contents.

Lifecycle events do not show whether initialisation succeeded.
\texttt{do\_init\_module} therefore uses a kprobe and kretprobe pair. At entry,
the module object is
retained in per-thread temporary state. At return, the implementation retrieves
that object, extracts the module identity and appends the function result. A
zero value identifies successful initialisation, while a negative value
preserves the reported kernel error.

The tracepoints identify additions and removals;
\texttt{do\_init\_module} provides the initialisation outcome. Seeing a module
during loading is therefore not treated as proof that it became operational.

The eBPF hooks are kprobes on Linux Security Module functions used during
security checks for eBPF commands and objects. They are not \gls{bpf} LSM
enforcement programs and do not change the decision.

The \texttt{security\_bpf} hook monitors operations entering the security path
of the \texttt{\gls{bpf}} syscall. Its purpose is to expose requests such as map
creation, program loading and program attachment. The event records the \gls{bpf}
command and attribute size, but does not copy \texttt{union \gls{bpf}\_attr}, whose
active fields depend on the command.

The \texttt{security\_bpf\_map} hook observes security checks involving an
existing eBPF map. Since maps retain state and exchange data between kernel
programs and user space, identifying access to them provides useful
object-level evidence. The event records the map identifier and bounded name,
without collecting its contents.

The \texttt{security\_bpf\_prog} hook observes security operations involving an
existing eBPF program. It records the program identifier, name and type,
allowing programs intended for kprobes, tracepoints, cgroups and other
execution contexts to be distinguished.

These hooks expose the requested \gls{bpf} operation and the map or program
under security mediation.

Further events cover kernel-facing activity that ordinary process syscalls may
not reveal: dynamic tracing, symbol lookup, procfs creation, kernel-initiated
execution and kernel file consumption.

The \texttt{register\_kprobe} event monitors attempts to install dynamic
kprobes. It records the target symbol, pre- and post-handler addresses, and
registration result. This distinguishes successful installations from rejected
requests, although the symbol may be absent when registration uses a kernel
address directly.

The \texttt{kallsyms\_lookup\_}\allowbreak\texttt{name} event records kernel
symbol resolution. It combines the requested symbol name with the returned
address, where zero indicates that no address was found. It covers this
specific lookup interface rather than every possible source of kernel
addresses.

The \texttt{proc\_create} event records requests to create procfs interfaces.
It records the entry name and proc-operations address, making kernel-created
user-space control or information endpoints visible. It does not include the
parent directory, complete path or creation result.

The \texttt{call\_usermodehelper} event records requests by the kernel to start
a user-space program. It records the executable path, bounded argument and
environment arrays, and wait mode. The arrays contain at most 38 elements and
remain subject to the event-size limit. The event represents the request, not
successful execution or completion of the helper.

The \texttt{security\_kernel\_read\_file} event observes the security stage
before the kernel consumes a file. It records the resolved pathname, device,
inode, change time and read purpose, distinguishing uses such as modules,
firmware, policy data and kexec images.

The later \texttt{security\_kernel\_post\_read\_file} event records the same
file identity and purpose together with the supplied byte size. This size is
not a return value. The two stages are emitted independently: the
implementation does not correlate them automatically, copy file contents or
compute a digest.

The resulting coverage does not inspect handler code, reconstruct every kernel
relationship, prove integrity or enforce a decision. Chapter~5 explains how
these logical events activate their producers and support dependencies.

\section{Binary Event Contract and Kernel Transport}
\label{sec:implementation-binary-contract}

Every event uses the same binary format. A 136-byte context holds common
process, host and event metadata, followed by a one-byte argument count and the
captured arguments. The Go decoder mirrors the C field order and widths. Only
the populated prefix is submitted, not the entire 32,000-byte construction
workspace.

Each argument starts with a one-byte schema index. Fixed-width values follow
directly, while strings and arrays use lengths and counts specific to their
encoding. The Go registry associates each index with an argument name and
decoder, so records do not repeat type information. Arguments can be omitted
without changing the indices of the remaining fields.

Before writing an argument, the eBPF helper must prove to the verifier that the
current offset and the complete payload remain inside the buffer.
Listing~\ref{lst:argument-buffer-bounds} shows the essential checks.

\begin{lstlisting}[
    language=C,
    caption={Checked argument-buffer offset handling.},
    label={lst:argument-buffer-bounds}
]
if (size == 0 || size > MAX_ELEMENT_SIZE || buf->offset >= ARGS_BUF_SIZE)
    return 0;
u32 offset = buf->offset;
update_min(offset, ARGS_BUF_SIZE - 1);
u32 buffer_index_offset = offset + 1;
if (buffer_index_offset > ARGS_BUF_SIZE)
    return 0;
buf->args[offset] = index;
// The omitted block clamps size for the older verifier.
u32 buffer_arg_offset = buffer_index_offset + size;
if (buffer_arg_offset > ARGS_BUF_SIZE)
    return 0;
if (bpf_probe_read(&(buf->args[buffer_index_offset]), size, ptr) < 0)
    return 0;
buf->offset = buffer_arg_offset;
buf->argnum++;
return 1;
\end{lstlisting}

The helper checks the original offset and uses \texttt{update\_min} only to make
its bound visible to the verifier. The stored offset advances after the index
and complete payload have been copied.

Once the event is complete, the submission helper refreshes its task context,
optionally adds a user-space stack identifier and calculates the record size.
It sends the record through
\texttt{\gls{bpf}\_perf\_event\_output} to the perf-event buffer associated with the
current CPU. The Go runtime consumes these per-CPU buffers through a libbpfgo
perf reader; the current implementation does not retain a \gls{bpf} ring-buffer
transport path.

The reader's loss channel reports records dropped by a full per-CPU buffer;
malformed records that arrive are reported by the decoder. These remain
separate conditions. Section~\ref{subsec:perf-buffer-failure-boundaries} covers
the transport's capacity and ordering consequences.

\section{Kernel-Side UID Filtering}
\label{sec:implementation-selection-filtering}

The shared initialiser can filter on one exact real \gls{uid}. When enabled,
it compares the current task's real UID with the configured value. A mismatch
stops collection before argument capture, full context enrichment and
perf-buffer submission. The check applies to every producer that uses the
shared initialiser.

The filter supports a single UID value. It does not support ranges,
exclusion lists or policy expressions. When disabled, it imposes no UID
restriction. If the shared configuration cannot be retrieved, the program
emits no event. More detailed selection is performed in user space.

Before processing begins, the Go runtime writes the enable flag and \gls{uid} to
fixed fields in the shared configuration map. These fields must remain aligned
with the C structure. Chapter~5 covers the update lifecycle; this section is
limited to kernel-side admission.

\section{Compatibility and Verifier Challenges}
\label{sec:implementation-compatibility-verifier}

Running the collector on Rocky Linux 8.10 required changes to how it reads
kernel data and checks buffer boundaries. CO-RE adjusts field accesses using
the target kernel's BTF information, but some differences require explicit
alternatives in the code \cite{linux_btf,linux_libbpf_overview}. The shared
helpers handle these differences when reading process identifiers, start
times, capabilities and inode timestamps. Cgroup identification also accounts
for the internal layout used by the RHEL 8 kernel family.

Helper availability affects how syscall registers are read. The code uses
BTF-aware task helpers when available; otherwise, an x86-64 fallback locates
the registers in the task's kernel stack using the target's stack dimensions.
For compatible 32-bit processes, syscall numbers are translated before event
classification.

The verifier must be able to establish that memory accesses stay within
valid bounds \cite{linux2026ebpfverifier}. Path reconstruction and argument
collection therefore use fixed loop limits, while buffer writes and event
submission include explicit size checks. Some checks needed further changes
to pass verification on the target. The shared syscall-exit path restricts
the return-argument index to values below 16, and selected memory syscalls
use dedicated tracepoints because the generic dispatcher was rejected.

These adaptations were tested on the selected Rocky Linux kernel.
Compatibility with other kernels still requires checking the available hooks,
helpers and attachment mechanisms, as explained in
Section~\ref{subsec:ebpf-btf-core}.
