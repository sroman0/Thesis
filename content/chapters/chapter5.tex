\chapter{User-Space Runtime and Detection Implementation}
\label{ch:user-space-implementation}

Chapter~4 followed an event to the perf-buffer boundary. This chapter continues
in user space, where the Go runtime prepares the selected programs, decodes
their records, applies policies and detectors, and delivers events, alerts and
diagnostics.

\section{Command-Line Configuration and Runtime Bootstrap}

The user-space workflow begins with a Cobra command-line interface
\cite{spf13_cobra}. It parses operator input into one configuration object and
invokes the application entry point. Policy loading, detector evaluation and
eBPF attachment remain outside Cobra.

Defaults provide the host BTF path, JSON event and alert output, console
diagnostics and an informational log level. CLI flags update event selection,
kernel filtering, policy and detector paths, output, logging and eBPF input.
The resulting typed structure is passed through the runtime instead of a loose
set of command-line values.

Configuration is normalised and validated before kernel resources are acquired.
Detector paths enable detector processing, and \texttt{alerts-only} enables
alert generation while suppressing ordinary event output. Unsupported event,
alert or logging formats fail at this stage, before loading or attachment.

The \texttt{list-events} path reads public names from the probe registry and
exits without resolving BTF, opening the eBPF object or attaching programs. A
monitoring invocation resolves the object, creates the runner and hands over
the validated configuration.

Listing~\ref{lst:cobra-runtime-handoff} shows this handoff.

  \begin{lstlisting}[
      language=Go,
      caption={Validated handoff from the Cobra command to the runtime
      (abridged).},
      label={lst:cobra-runtime-handoff}
  ]
  if err := ValidateConfig(&cliCfg); err != nil {
      return err
  }
  if cliCfg.ListEvents {
      printSupportedEvents(cmd.OutOrStdout())
      return nil
  }
  if err := initialize.BPFObject(&cliCfg); err != nil {
      return err
  }
  runner, err := NewProjectRunner(cliCfg)
  if err != nil {
      return err
  }
  return runner.Run(ctx)
  \end{lstlisting}

Static configuration, external-definition and construction errors are reported
before monitoring starts. Failures confined to one record are handled later by
the active event loop.

\section{Loader, Probe Registry and Attachment Lifecycle}
\label{sec:implementation-loader-registry}

After validation, bootstrap resolves the eBPF object and BTF inputs. An object
named by \texttt{PROJECT\_BPF\_OBJECT} takes precedence over the command-line
path; otherwise the embedded object is used. BTF resolution follows the same
environment, command-line and default-host order. Embedding simplifies
distribution but does not remove the need for compatible BTF, kernel features
and privileges.

Policies and detectors are prepared before the eBPF module is opened. A finite
policy scope can narrow the CLI event set; an open-ended rule retains the wider
scope. A disjoint finite policy and CLI selection fails startup, avoiding an
empty set being interpreted as ``all events''. Selecting a detector does not
enable its kernel events independently: its inputs must already be in scope.

The probe registry converts logical events into producer programs and any
support probes needed to retain intermediate information.

Listing~\ref{lst:probe-plan} shows this dependency expansion.

  \begin{lstlisting}[
      language=Go,
      caption={Selection of producer and support probes (abridged).},
      label={lst:probe-plan}
  ]
  for _, probe := range supportedProbes {
      if probeActivation[probe.eventName] {
          selectedProbes = append(selectedProbes, probe)
          continue
      }
      for _, event := range probe.impliedBy {
          if probeActivation[event] {
              selectedProbes = append(selectedProbes, probe)
              break
          }
      }
  }
  \end{lstlisting}

Registry tests verify the expected producers and support probes. Hook
availability can only be established by loading and attaching on the target
system.

Before object loading, autoload is disabled for registered programs outside the
plan. Libbpf then verifies and loads the selected producers and dependencies.
The optimisation covers only programs represented in the registry.

After loading, the runtime updates the required maps, creates the perf-event
reader and attaches each selected program. Monitoring ends when the context is
cancelled, normally by \texttt{SIGINT} or \texttt{SIGTERM}.

\section{User-Space Decoder and Event Registry}
\label{sec:implementation-decoder-registry}

The perf reader receives each kernel record as a byte slice. The decoder checks
its structure and converts it into the typed representation used by the Go
runtime.

Figure~\ref{fig:userspace-decoder-record-layout} shows the regions read by the
decoder: a 136-byte common context, the argument count at byte 136 and the
variable stream of indexed arguments.

  \begin{figure}[H]
      \centering
      \includegraphics[
          width=0.90\textwidth,
          height=0.65\textheight,
          keepaspectratio
      ]{figures/chapter5/userspace-decoder-record-layout.drawio.png}
      \caption[Binary record layout consumed by the user-space decoder]
      {Binary record layout consumed by the user-space decoder.}
      \label{fig:userspace-decoder-record-layout}
  \end{figure}

The fixed context must be complete before any field is read. Header values are
decoded from explicit little-endian offsets rather than copied into a Go
structure, whose compiler-defined padding could differ from the C wire layout.

The resulting context includes timing, process and namespace identities,
command and UTS names, the event identifier, associated syscall and collection
metadata. The event identifier selects an entry in the user-space registry.

Each registry entry associates a public identifier with a logical name and an
ordered argument schema. The schema supplies the name and type omitted from the
wire representation.

An argument begins with a one-byte schema index followed by its payload. The
selected type determines the decoder: scalars have fixed widths; strings, byte
sequences and arrays carry bounded lengths; socket addresses and credentials
use dedicated structured decoders.

  \begin{lstlisting}[
      language=Go,
      basicstyle=\ttfamily\footnotesize,
      caption={Schema-directed decoding of indexed event arguments.},
      label={lst:indexed-argument-decoding}
  ]
  spec, ok := events.GetSpec(eventID)
  if !ok {
      return nil, fmt.Errorf("unknown event id=%d", eventID)
  }

  for seen := 0; seen < argnum && offset < len(rawArgs); seen++ {
      index := int(rawArgs[offset])
      offset++

      if index >= len(spec.Args) {
          return nil, fmt.Errorf("argument index out of range")
      }

      argSpec := spec.Args[index]
      value, consumed, err :=
          decodeArgRecord(rawArgs[offset:], argSpec.DecodeAs)
      if err != nil {
          return nil, err
      }

      offset += consumed
      decoded[index] = Argument{
          Name:  argSpec.Name,
          Type:  argSpec.DecodeAs,
          Value: value,
      }
  }
  \end{lstlisting}

A valid record becomes a \texttt{bufferdecoder.Event} containing the common
context, public event name and typed arguments. Policies, detectors and output
all consume this representation; presentation does not perform another
normalisation step.

\section{User-Space Event Selection and Admission}
\label{sec:userspace-event-selection}

After decoding, three short-circuit gates check the logical event set, an
optional exact command name and the active policies. A policy applies its common
scope before its rules, and matching suppression overrides monitor or detect
rules. Without policies, the last gate admits the event.

Listing~\ref{lst:event-admission} shows the order and consumer fan-out. Optional
socket enrichment and diagnostics are omitted.

\begin{lstlisting}[
    language=Go,
    caption={Decoded-event admission and consumer fan-out (abridged).},
    label={lst:event-admission}
]
event, err := bufferdecoder.DecodeEvent(raw)
if err != nil {
    return
}
if !p.eventEnabled(event.EventName) {
    return
}
if !p.commEnabled(event.Context.CommString()) {
    return
}
if !p.policyEnabled(event) {
    return
}
if !p.cfg.Alerts.Only {
    if err := p.printer.Print(event); err != nil {
        p.logger.Error("print event", zap.Error(err))
    }
}
p.processDetectors(ctx, event)
\end{lstlisting}

Failure at any gate prevents both event output and detector evaluation.

The policy manager does not generate alerts. Monitor and detect modes share the
same admission path; only suppression removes a matching event from later
consumers.

Valid rejections are distinguished from failures. Only the first few filter
drops are logged at debug level, preventing unbounded diagnostics. Decode,
detector and rendering errors are reported separately without stopping the
loop. Component tests cover these paths, although no unit test exercises the
complete admission order end to end.

\section{Policy and Detector Engine}
\label{sec:implementation-policy-detector}

\subsection{YAML Policy and Detector Definitions}
  \label{subsec:implementation-yaml-definitions}

Policies and detectors use separate YAML documents, both validated and
converted into Go models before event processing.

Listing~\ref{lst:policy-yaml-schema} shows the main policy fields.

  \begin{lstlisting}[
      style=thesis-yaml,
      caption={Representative YAML policy structure.},
      label={lst:policy-yaml-schema}
  ]
  name: privileged-file-monitoring
  mode: detect
  intent: threat_hunting

  scope:
    uids: [0]

  rules:
    - name: sensitive-files
      events:
        include: [security_file_open]
      filters: ["args.pathname=/etc/*"]

  detectors:
    include:
      severities: [high, critical]
      techniques: [T1548]
      stateful: true
    exclude:
      tags: [experimental]
  \end{lstlisting}

The \texttt{name}, \texttt{mode} and \texttt{intent} identify the policy and its
purpose. Mode and intent default to \texttt{monitor} and
\texttt{threat\_hunting}. An optional \texttt{scope} applies command or UID
constraints to all rules.

Rules are alternatives; fields within one rule are cumulative constraints.
Event exclusions override inclusions, and an empty include list starts from all
events. Filters written as \texttt{args.<name>} run after decoding because they
need typed arguments.

The optional \texttt{detectors} block selects definitions by identifier,
severity, tags, statefulness or MITRE ATT\&CK metadata. Values in one criterion
are alternatives; populated criteria are combined. Exclusions are then removed
from the catalogue. Suppression policies cannot select detectors.

A detector document defines input events, matching logic, alert fields and
optional ATT\&CK classification. Listing~\ref{lst:detector-yaml-schema} shows a
shortened collective definition.

  \begin{lstlisting}[
      style=thesis-yaml,
      caption={Representative YAML definition of a collective detector.},
      label={lst:detector-yaml-schema}
  ]
  id: privilege-exec-chain
  name: Privilege change followed by execution
  requires:
    - {event: security_task_fix_setuid,
       reason: observes a UID transition}
    - {event: sched_process_exec,
       reason: confirms executable replacement}
  consumes: [security_task_fix_setuid, sched_process_exec]

  stateful: true
  window: 5s
  group_by: [process_tree]
  steps:
    - event: security_task_fix_setuid
      conditions:
        - {field: args.new_euid, operator: eq, value: "0"}
    - event: sched_process_exec
      conditions:
        - {field: uid, operator: eq, value: "0"}

  output:
    title: Privilege change followed by process execution
    severity: high
  threat:
    tactics: [{id: TA0004, name: Privilege Escalation}]
    techniques: [{id: T1548,
                  name: Abuse Elevation Control Mechanism}]
  tags: [process, collective, privilege-escalation]
  \end{lstlisting}

The stable \texttt{id} supports selection and alert attribution.
\texttt{requires} documents event dependencies; \texttt{consumes} defines the
dispatch set and is derived from requirements and steps when omitted.

Stateless predicates appear in top-level \texttt{conditions}. Collective
definitions use ordered \texttt{steps}, a bounded \texttt{window} and
\texttt{group\_by} strategies for process, immediate parent, file resource,
local cgroup or composite identity. Subsection
\ref{subsec:implementation-correlation-deduplication} describes their state.

The \texttt{output} block defines the alert; \texttt{threat} carries optional
MITRE ATT\&CK classification. Conditions, event names, severity, ATT\&CK
identifiers and correlation plans are validated and compiled at startup.

Definitions may be supplied as files or through directories scanned
non-recursively in lexical order.

\subsection{Point and Collective Evaluation Paths}
  \label{subsec:implementation-point-collective}

As introduced in Subsection~\ref{subsec:point-collective-detectors}, point and
collective detectors require different amounts of evidence. Both implement the
same \texttt{Detector} interface and use the event-indexed dispatcher. The
YAML-backed implementation chooses the path when it receives an event.

Listing~\ref{lst:detector-evaluation-path} shows the branch between immediate
matching and sequence processing.

  \begin{lstlisting}[
      language=Go,
      caption={Selection of the point or collective evaluation path.},
      label={lst:detector-evaluation-path}
  ]
  if !d.consumes(event.EventName) {
      return nil, nil
  }

  if d.isStatefulSequence() {
      return d.onStatefulEvent(event)
  }

  matches, err := d.matches(event)
  if err != nil || !matches {
      return nil, err
  }

  return []detectors.Alert{d.newAlert(event)}, nil

  func (d *Detector) isStatefulSequence() bool {
      return d.def.Stateful && len(d.steps) > 1
  }
  \end{lstlisting}

The consumption check remains at the detector boundary even though dispatch has
already narrowed the candidates. The collective path requires both
\texttt{stateful: true} and more than one compiled step; the flag alone does not
create a collective detector.

Collective definitions are delegated to \texttt{onStatefulEvent}, which derives
correlation keys and tests the next expected step. An event can advance or
complete existing state, or start a new sequence by matching its first step.

\subsection{Compiled Correlation State and Alert Deduplication}
  \label{subsec:implementation-correlation-deduplication}

YAML \texttt{group\_by} values are compiled into a correlation plan during
detector construction. Event processing then calls preselected key extractors
without parsing strategy names again.

The supported components produce these internal values:

  \begin{itemize}
      \item \texttt{process} combines the host PID and task start time;
      \item \texttt{process\_tree} can additionally produce the immediate
      parent's host PID and start time when looking up an existing sequence;
      \item \texttt{resource} combines the device and inode arguments;
      \item \texttt{cgroup} uses the local kernel cgroup identifier.
  \end{itemize}

Several components form one composite key, and all must be present. Missing
process, resource or cgroup data stops the transition instead of falling back
to a weaker identity.

Plan construction rejects unknown or duplicate components. Resource
correlation requires \texttt{dev} and \texttt{inode} in every step.
\texttt{user\_session} is unsupported because events do not expose a stable
session identifier; UID is not used as an approximation.

Each collective detector maps correlation keys to partial sequences. An entry
stores the next step, initial time and matched evidence. Listing
\ref{lst:collective-transition} shows how an event advances it.

  \begin{lstlisting}[
      language=Go,
      caption={Advancement of a partial collective sequence (abridged).},
      label={lst:collective-transition}
  ]
  for _, key := range lookupKeys {
      state, ok := d.state[key]
      if !ok {
          continue
      }
      if now.Sub(state.firstSeen) > window {
          delete(d.state, key)
          continue
      }

      matches, err :=
          stepMatches(event, d.steps[state.nextStep])
      if err != nil {
          return nil, err
      }
      if !matches {
          continue
      }

      state.events = append(state.events, event)
      state.nextStep++

      if state.nextStep >= len(d.steps) {
          delete(d.state, key)
          return []detectors.Alert{
              d.newAlertFromEvents(state.events),
          }, nil
      }

      d.state[key] = state
      return nil, nil
  }
  \end{lstlisting}

Process-tree lookup may use both the current process and its immediate parent,
allowing a child event to advance parent state without a persistent process
graph. If no state advances, a first-step match creates an entry under its
initial key. Each key retains at most one partial sequence.

Expired state is removed when addressed or during periodic pruning triggered by
relevant events. The interface exposes \texttt{Flush}, but the production
runtime does not schedule it independently. Idle stale entries may remain until
later traffic or capacity pressure triggers cleanup.

Alert deduplication runs after evaluation and is independent of sequence state.
Its key contains detector identity, title, severity and fields from the first
evidence event, excluding timestamps and thread identifiers. Repeated keys
inside the window are suppressed.

The key is neither the complete collective sequence nor a durable causal
identity. The deduplication map also has no independent capacity limit.

\section{Output and Structured Logging}
\label{sec:implementation-output-logging}

The output package formats the decoded model; it does not normalise it again.
Events become JSON or compact text, while alerts add detector identity,
severity, ordered evidence and optional threat metadata. JSON preserves typed
values and can add readable labels; compact text supports interactive use.

Events and alerts both use standard output but have independent format settings,
so one run can produce a mixed stream. \texttt{alerts-only} suppresses event
presentation without disabling detection. Point alerts contain one source
event; collective alerts preserve ordered evidence in JSON and a bounded
sequence in compact text.

Zap writes operational diagnostics to standard error in console or JSON form
at debug, info, warn or error level \cite{uber_zap}. These include lifecycle and
selected libbpf messages, perf-buffer losses, and decoder, detector or output
failures. Zap never serialises monitored events or alerts, keeping
infrastructure conditions outside the security data stream.

record-local failures are logged and processing continues. Logger

\section{User-Space Implementation Summary}
\label{sec:user-space-implementation-summary}

The Go runtime turns perf-buffer records into typed events, applies admission
gates and routes accepted evidence to output and deterministic detectors.
Policies control scope and suppression; detectors evaluate point conditions or
bounded local sequences and carry ATT\&CK metadata into alerts.

Registry and decoder tests establish structural invariants. Attachment under
workload, alert behaviour, transport loss and resource consumption require
target-environment evidence and are examined in Chapter~6.
