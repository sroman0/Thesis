\chapter{User-Space Runtime and Detection Implementation}
\label{ch:user-space-implementation}

Chapter~4 followed an event to the perf-buffer boundary. This chapter continues
in user space, where the Go runtime prepares the selected programs, decodes
their records, applies policies and detectors, and delivers events, alerts and
diagnostics.

\section{Command-Line Configuration and Runtime Bootstrap}

The user-space workflow begins with a Cobra command-line interface
\cite{spf13_cobra}. It parses operator input into one configuration object and
invokes the application entry point. Policy loading, detector evaluation and
eBPF attachment remain outside Cobra.

Defaults provide the host BTF path, \gls{json} event and alert output, console
diagnostics and an informational log level. \gls{cli} flags update event selection,
kernel filtering, policy and detector paths, output, logging and eBPF input.
The resulting typed structure is passed through the runtime instead of a loose
set of command-line values.

Configuration is normalised and validated before kernel resources are acquired.
Detector paths enable detector processing, and \texttt{alerts-only} enables
alert generation while suppressing ordinary event output. Unsupported event,
alert or logging formats fail at this stage, before loading or attachment.

The \texttt{list-events} path reads public names from the probe registry and
exits without resolving BTF, opening the eBPF object or attaching programs. A
monitoring invocation resolves the object, creates the runner and hands over
the validated configuration.

Listing~\ref{lst:cobra-runtime-handoff} shows this handoff.

  \begin{lstlisting}[
      language=Go,
      caption={Validated handoff from the Cobra command to the runtime
     .},
      label={lst:cobra-runtime-handoff}
  ]
  if err := ValidateConfig(&cliCfg); err != nil {
      return err
  }
  if cliCfg.ListEvents {
      printSupportedEvents(cmd.OutOrStdout())
      return nil
  }
  if err := initialize.BPFObject(&cliCfg); err != nil {
      return err
  }
  runner, err := NewProjectRunner(cliCfg)
  if err != nil {
      return err
  }
  return runner.Run(ctx)
  \end{lstlisting}

Static configuration, external-definition and construction errors are reported
before monitoring starts. Failures confined to one record are handled later by
the active event loop.

\section{Loader, Probe Registry and Attachment Lifecycle}
\label{sec:implementation-loader-registry}

After validation, the bootstrap phase resolves the artefacts required to load
  the eBPF programs. The eBPF object is an ELF file produced by compiling the C
  collector sources.

  The runtime first checks the \texttt{PROJECT\_BPF\_OBJECT} environment
  variable, followed by the path supplied through the command-line interface. If
  neither is specified, it reads \path{dist/project.bpf.o}, which is embedded in
  the Go executable at build time. In every case, the selected object is loaded
  into memory and passed to \texttt{libbpfgo} as a byte buffer.

  The BTF file is resolved separately. The
  \texttt{PROJECT\_BTF\_FILE} environment variable takes precedence over the
  command-line configuration, whose default is
  \path{/sys/kernel/btf/vmlinux}. This file describes the types of the running
  kernel and allows \texttt{libbpf} to apply the CO-RE relocations required by
  the compiled eBPF object.

Policies and detectors are prepared before the eBPF module is opened. A disjoint 
finite policy and \gls{cli} selection fails startup, avoiding an empty set being interpreted
as ``all events''. Selecting a detector does not enable its kernel events independently: 
its inputs must already be in scope.

The probe registry converts logical events into producer programs and any
support probes needed to retain intermediate information.

Listing~\ref{lst:probe-plan} shows this dependency expansion.

  \begin{lstlisting}[
      language=Go,
      caption={Selection of producer and support probes.},
      label={lst:probe-plan}
  ]
  for _, probe := range supportedProbes {
      if probeActivation[probe.eventName] {
          selectedProbes = append(selectedProbes, probe)
          continue
      }
      for _, event := range probe.impliedBy {
          if probeActivation[event] {
              selectedProbes = append(selectedProbes, probe)
              break
          }
      }
  }
  \end{lstlisting}

Registry tests verify the expected producers and support probes. Hook
availability can only be established by loading and attaching on the target
system.

Before object loading, autoload is disabled for registered programs outside the
plan. Libbpf then verifies and loads the selected producers and dependencies.
The optimisation covers only programs represented in the registry.

After loading, the runtime updates the required maps, creates the perf-event
reader and attaches each selected program. Monitoring ends when the context is
cancelled, normally by \texttt{SIGINT} or \texttt{SIGTERM}.

\section{User-Space Decoder and Event Registry}
\label{sec:implementation-decoder-registry}

The perf reader receives each kernel record as a byte slice. The decoder checks
its structure and converts it into the typed representation used by the Go
runtime.

Figure~\ref{fig:userspace-decoder-record-layout} shows the regions read by the
decoder: a 136-byte common context, the argument count at byte 136 and the
variable stream of indexed arguments.

  \begin{figure}[H]
      \centering
      \includegraphics[
          width=0.95\textwidth,
          height=0.75\textheight,
          keepaspectratio
      ]{figures/chapter5/eBPF_Decoding_Schema.drawio.png}
      \caption[Binary record layout consumed by the user-space decoder]
      {Binary record layout consumed by the user-space decoder.}
      \label{fig:userspace-decoder-record-layout}
  \end{figure}

The fixed context must be complete before any field is read. Header values are
decoded from explicit little-endian offsets.

The resulting context includes timing, process and namespace identities,
command and UTS names, the event identifier, associated syscall and collection
metadata. The event identifier selects an entry in the user-space registry.

Each registry entry associates a public identifier with a logical name and an
ordered argument schema. The schema supplies the name and type omitted from the
wire representation.

An argument begins with a one-byte schema index followed by its payload. The
selected type determines the decoder: scalars have fixed widths; strings, byte
sequences and arrays carry bounded lengths; socket addresses and credentials
use dedicated structured decoders.

  \begin{lstlisting}[
      language=Go,
      basicstyle=\ttfamily\footnotesize,
      caption={Schema-directed decoding of indexed event arguments.},
      label={lst:indexed-argument-decoding}
  ]
  spec, ok := events.GetSpec(eventID)
  if !ok {
      return nil, fmt.Errorf("unknown event id=%d", eventID)
  }

  for seen := 0; seen < argnum && offset < len(rawArgs); seen++ {
      index := int(rawArgs[offset])
      offset++

      if index >= len(spec.Args) {
          return nil, fmt.Errorf("argument index out of range")
      }

      argSpec := spec.Args[index]
      value, consumed, err :=
          decodeArgRecord(rawArgs[offset:], argSpec.DecodeAs)
      if err != nil {
          return nil, err
      }

      offset += consumed
      decoded[index] = Argument{
          Name:  argSpec.Name,
          Type:  argSpec.DecodeAs,
          Value: value,
      }
  }
  \end{lstlisting}

A valid record becomes a \texttt{bufferdecoder.Event} containing the common
context, public event name and typed arguments. Policies, detectors and output
all consume this representation; presentation does not perform another
normalisation step.

\section{User-Space Event Selection and Admission}
\label{sec:userspace-event-selection}

After decoding, the runtime applies three filters to decide whether an event
should be shown to the analyst and evaluated by detectors.

The first filter checks whether the event type belongs to the enabled set.
For example, selecting \texttt{sched\_process\_exec} keeps execution events
while excluding other event types.

The second filter, when configured, selects events by the command name of
the process that generated them. Selecting \texttt{cat}, for example, keeps
only events whose \texttt{comm} field is exactly \texttt{cat}. This checks
the task name, not the executable path or its command-line arguments.

The third filter evaluates the active policies. Each policy first checks
its common scope, then its rules, which can constrain process attributes
and event arguments. A matching suppression policy rejects the event even
if another policy allows it. When no policies are configured, this filter
accepts the event.

Processing stops at the first rejection. Only events that pass all three
filters reach event output and detector evaluation. These checks reduce
the work performed after decoding; they do not reduce traffic already
transferred from the kernel.

Listing~\ref{lst:event-admission} shows the filter order and the subsequent
processing. The \texttt{alerts-only} option skips event printing while
keeping detection enabled. Optional socket enrichment and diagnostics are
omitted.

\begin{lstlisting}[
    language=Go,
    caption={Decoded-event admission and consumer fan-out.},
    label={lst:event-admission}
]
event, err := bufferdecoder.DecodeEvent(raw)
if err != nil {
    return
}
if !p.eventEnabled(event.EventName) {
    return
}
if !p.commEnabled(event.Context.CommString()) {
    return
}
if !p.policyEnabled(event) {
    return
}
if !p.cfg.Alerts.Only {
    if err := p.printer.Print(event); err != nil {
        p.logger.Error("print event", zap.Error(err))
    }
}
p.processDetectors(ctx, event)
\end{lstlisting}

Valid rejections are distinguished from failures. Only the first few filter
drops are logged at debug level, preventing unbounded diagnostics. Decode,
detector and rendering errors are reported separately without stopping the
loop. Component tests cover these paths, although no unit test exercises the
complete admission order end to end.

\section{Policy and Detector Engine}
\label{sec:implementation-policy-detector}

\subsection{YAML Policy and Detector Definitions}
  \label{subsec:implementation-yaml-definitions}

Policies and detectors use separate YAML documents, both validated and
converted into Go models before event processing.

Listing~\ref{lst:policy-yaml-schema} shows the main policy fields.

  \begin{lstlisting}[
      style=thesis-yaml,
      caption={Representative YAML policy structure.},
      label={lst:policy-yaml-schema}
  ]
  name: privileged-file-monitoring
  mode: detect
  intent: threat_hunting

  scope:
    uids: [0]

  rules:
    - name: sensitive-files
      events:
        include: [security_file_open]
      filters: ["args.pathname=/etc/*"]

  detectors:
    include:
      severities: [high, critical]
      techniques: [T1548]
      stateful: true
    exclude:
      tags: [experimental]
  \end{lstlisting}

The \texttt{name}, \texttt{mode} and \texttt{intent} identify the policy and its
purpose. Mode and intent default to \texttt{monitor} and
\texttt{threat\_hunting}. An optional \texttt{scope} applies command or UID
constraints to all rules.

Rules are alternatives; fields within one rule are cumulative constraints.
Event exclusions override inclusions, and an empty include list starts from all
events. Filters written as \texttt{args.<name>} run after decoding because they
need typed arguments.

The optional \texttt{detectors} block chooses which detector definitions
to enable. Selection can use identifiers, severity, tags, statefulness
or MITRE ATT\&CK metadata. A detector must satisfy every specified
criterion, but may match any of the values listed within that criterion.
For example, selecting severities \texttt{high} and \texttt{critical}
together with the tag \texttt{filesystem} keeps filesystem detectors
with either severity. Explicit exclusions remove detectors from this
selection.

A detector document defines input events, matching logic, alert fields and
optional ATT\&CK classification. Listing~\ref{lst:detector-yaml-schema} shows a
shortened collective definition.

  \begin{lstlisting}[
      style=thesis-yaml,
      caption={Representative YAML definition of a collective detector.},
      label={lst:detector-yaml-schema}
  ]
  id: privilege-exec-chain
  name: Privilege change followed by execution
  requires:
    - {event: security_task_fix_setuid,
       reason: observes a UID transition}
    - {event: sched_process_exec,
       reason: confirms executable replacement}
  consumes: [security_task_fix_setuid, sched_process_exec]

  stateful: true
  window: 5s
  group_by: [process_tree]
  steps:
    - event: security_task_fix_setuid
      conditions:
        - {field: args.new_euid, operator: eq, value: "0"}
    - event: sched_process_exec
      conditions:
        - {field: uid, operator: eq, value: "0"}

  output:
    title: Privilege change followed by process execution
    severity: high
  threat:
    tactics: [{id: TA0004, name: Privilege Escalation}]
    techniques: [{id: T1548,
                  name: Abuse Elevation Control Mechanism}]
  tags: [process, collective, privilege-escalation]
  \end{lstlisting}

The stable \texttt{id} supports selection and alert attribution.
\texttt{requires} documents event dependencies; \texttt{consumes} defines the
dispatch set and is derived from requirements and steps when omitted.

Stateless predicates appear in top-level \texttt{conditions}. Collective
definitions use ordered \texttt{steps}, a bounded \texttt{window} and
\texttt{group\_by} strategies for process, immediate parent, file resource,
local cgroup or composite identity. Subsection
\ref{subsec:implementation-correlation-deduplication} describes their state.

The \texttt{output} block defines the alert; \texttt{threat} carries optional
MITRE ATT\&CK classification. Conditions, event names, severity, ATT\&CK
identifiers and correlation plans are validated and compiled at startup.

Definitions may be supplied as files or through directories scanned
non-recursively in lexical order.

\subsection{Point and Collective Evaluation Paths}
  \label{subsec:implementation-point-collective}

As introduced in Subsection~\ref{subsec:point-collective-detectors}, point and
collective detectors require different amounts of evidence. Both implement the
same \texttt{Detector} interface and use the event-indexed dispatcher. The
YAML-backed implementation chooses the path when it receives an event.

Listing~\ref{lst:detector-evaluation-path} shows the branch between immediate
matching and sequence processing.

  \begin{lstlisting}[
      language=Go,
      caption={Selection of the point or collective evaluation path.},
      label={lst:detector-evaluation-path}
  ]
  if !d.consumes(event.EventName) {
      return nil, nil
  }

  if d.isStatefulSequence() {
      return d.onStatefulEvent(event)
  }

  matches, err := d.matches(event)
  if err != nil || !matches {
      return nil, err
  }

  return []detectors.Alert{d.newAlert(event)}, nil

  func (d *Detector) isStatefulSequence() bool {
      return d.def.Stateful && len(d.steps) > 1
  }
  \end{lstlisting}

The consumption check remains at the detector boundary even though dispatch has
already narrowed the candidates. The collective path requires both
\texttt{stateful: true} and more than one compiled step; the flag alone does not
create a collective detector.

Collective definitions are delegated to \texttt{onStatefulEvent}, which derives
correlation keys and tests the next expected step. An event can advance or
complete existing state, or start a new sequence by matching its first step.

\subsection{Compiled Correlation State and Alert Deduplication}
\label{subsec:implementation-correlation-deduplication}

A collective detector must identify which events belong to the same
sequence. Its YAML \texttt{group\_by} setting defines the fields used
to make this association. During construction, the detector prepares
the functions that extract these fields, so event processing does not
need to interpret the configuration again.

The supported correlation criteria are:
\begin{itemize}
    \item \texttt{process}: the host PID and task start time;
    \item \texttt{process\_tree}: the process identity, with an additional
    lookup using the immediate parent's identity;
    \item \texttt{resource}: the file's device and inode numbers;
    \item \texttt{cgroup}: the local kernel cgroup identifier.
\end{itemize}

When several criteria are selected, their values form one key and all
are required. An event with missing correlation data cannot advance
a sequence. Unknown or repeated criteria are rejected during detector
construction. Resource correlation also requires every step to expose
\texttt{dev} and \texttt{inode}. The \texttt{user\_session} criterion is
unsupported because the events do not provide a stable session identifier.

Each detector stores at most one incomplete sequence per key. The stored
state contains the matched events, the time of the first match and the
next expected step. Listing~\ref{lst:collective-transition} shows how an
incoming event advances an existing sequence. Completing the final step
generates an alert and removes that state.

\begin{lstlisting}[
    language=Go,
    caption={Advancement of a partial collective sequence.},
    label={lst:collective-transition}
]
for _, key := range lookupKeys {
    state, ok := d.state[key]
    if !ok {
        continue
    }
    if now.Sub(state.firstSeen) > window {
        delete(d.state, key)
        continue
    }

    matches, err :=
        stepMatches(event, d.steps[state.nextStep])
    if err != nil {
        return nil, err
    }
    if !matches {
        continue
    }

state.events = append(state.events, event)
  state.nextStep++

  if state.nextStep >= len(d.steps) {
      delete(d.state, key)
      return []detectors.Alert{
          d.newAlertFromEvents(state.events),
      }, nil
  }

  d.state[key] = state
    return nil, nil
}
\end{lstlisting}

With \texttt{process\_tree}, a child event can
advance a sequence started by its immediate parent. This does not require
a persistent process graph and does not follow arbitrary ancestry.

Each correlation key holds only one incomplete sequence. If an event
does not advance that sequence but matches its first step, it replaces
the stored sequence and restarts the time window. For example, when
looking for A followed by B, receiving A twice under the same key means
that the detector waits for B after the most recent A.

A sequence must complete within its configured time window, which defaults
to two seconds and cannot exceed five seconds. The window starts when the
runtime stores the first matching event. Each detector stores at most 4,096 incomplete sequences.
At capacity, adding a new key removes the oldest incomplete sequence.

Expired sequences cannot advance. They are removed when accessed or during
cleanup checks triggered by incoming events. Without further events,
expired entries may remain in memory until processing resumes.

Alert deduplication is separate from sequence tracking. It suppresses an
alert when the same deduplication key was emitted less than five seconds
earlier. The key combines the detector identity, title and severity with
the first evidence event's name, process PID, UID, command name and argument
values. It does not compare the complete sequence, so alerts with different
later observations may still be treated as duplicates.

\section{Output and Structured Logging}
  \label{sec:implementation-output-logging}

  The output layer formats decoded events and detector alerts as JSON or compact
  text. JSON output writes one object per line, preserving typed argument values
  and adding readable labels where available. Compact text provides a shorter
  representation for terminal use.

  The following examples were collected during a controlled invocation of
  \texttt{cat /etc/passwd}. They show an event, an alert and an operational
  diagnostic from the same monitoring session. The JSON has been indented for
  readability; fields omitted from the event and alert extracts are described below.

  Listing~\ref{lst:output-event-example} retains the event name, selected process
  fields and three arguments. The numeric operation value has the label
  \texttt{openat}, while the returned descriptor has the label \texttt{fd:3}.
  The positive return value confirms successful opening.

  \begin{lstlisting}[language={},
      caption={Selected fields from the recorded file-opening event.},
      label={lst:output-event-example}]
  {
    "event_name": "open",
    "process": {"pid": 3951999, "uid": 1000, "comm": "cat"},
    "args": [
      {"name": "operation", "type": 1, "value": 2, "label": "openat"},
      {"name": "pathname", "type": 11, "value": "/etc/passwd"},
      {"name": "returnValue", "type": 3, "value": 3, "label": "fd:3"}
    ]
  }
  \end{lstlisting}

  The same invocation triggered the configured sensitive-file detector.
  Listing~\ref{lst:output-alert-example} retains its identity, severity, evidence
  count and complete threat metadata. The full alert also contains the source
  event in an \texttt{events} array, together with descriptive and timing fields.
  The source was the \texttt{security\_file\_open} observation for
  \path{/etc/passwd}. This controlled read satisfied the configured rule.

  \begin{lstlisting}[language={},
      caption={Selected alert fields, including the complete threat block.},
      label={lst:output-alert-example}]
  {
    "type": "alert",
    "detector_id": "sensitive-file-open",
    "severity": "medium",
    "event_count": 1,
    "threat": {
      "framework": "MITRE ATT&CK Enterprise",
      "version": "v19.1",
      "tactics": [{"id": "TA0007", "name": "Discovery"}],
      "techniques": [{"id": "T1083", "name": "File and Directory Discovery"}],
      "data_sources": ["File"],
      "data_components": ["File Access"]
    }
  }
  \end{lstlisting}

  Events and alerts are written to standard output with independently configured
  formats. The \texttt{alerts-only} option suppresses event presentation while
  keeping detection and alert output active. Alert evidence uses the same JSON
  event representation as ordinary event output.

  Operational diagnostics are written to standard error through Zap, in console
  or JSON format \cite{uber_zap}. Listing~\ref{lst:output-diagnostic-example}
  shows a complete configuration message. Its fields report the detector
  catalogue prepared for the run.

  \begin{lstlisting}[language={},
      caption={Recorded diagnostic describing detector configuration.},
      label={lst:output-diagnostic-example}]
  {
    "level": "info",
    "ts": "2026-09-09T14:07:42.895Z",
    "msg": "detector layer configured",
    "paths": 1,
    "available_detectors": 1,
    "loaded_detectors": 1,
    "policy_selection": false
  }
  \end{lstlisting}

  Diagnostics also report setup failures, perf-buffer loss notifications and
  decoding, detector or output errors. During monitoring, record-local failures are logged
  and processing continues with subsequent events.
