\chapter{User-Space Runtime and Detection Implementation}
\label{ch:user-space-implementation}

Chapter~4 described how the eBPF programs construct and submit binary event
records through the perf buffer. This chapter starts at the corresponding
user-space boundary. It explains how the Go runtime turns the selected monitoring configuration into
a managed user-space pipeline, from program preparation and record
interpretation to policy-driven analysis, detector evaluation, and the delivery
of monitoring and diagnostic results. The focus is on the implemented ownership and failure
boundaries rather than on eBPF theory, hook catalogues or experimental results.

\section{Loader, Probe Registry and Attachment Lifecycle}
\label{sec:implementation-loader-registry}

The runtime begins with one central configuration object populated by the
command-line interface. Configuration normalisation enables the detector layer
when detector paths are supplied and enables alert output for the
\texttt{alerts-only} mode. Static validation then checks the requested output
and logging formats before the runtime attempts to open an eBPF object or
acquire a kernel-facing resource. The \texttt{list-events} path terminates at
this stage: it obtains names from the probe registry and does not resolve BTF,
open the eBPF object or attach a program.

The object and BTF inputs are resolved independently. For the eBPF object, the
runtime gives precedence to the \texttt{PROJECT\_BPF\_OBJECT} environment
variable, then to an explicit command-line path, and finally to the object
embedded in the executable. BTF follows the analogous
\texttt{PROJECT\_BTF\_FILE}, command-line and default-host-path order. The
embedded object removes the need to place a second object file beside the
executable in the usual path, but it does not remove the target dependence on
kernel BTF, privileges, compatible attachment points and the libraries used by
the CGO-linked runtime. The latter uses \texttt{libbpfgo} as its Go interface to
\texttt{libbpf} \cite{aquasecurity_libbpfgo}.

Policies and detector definitions are prepared before the eBPF module is
opened. Policy files are loaded and checked against the event registry. When
every active non-suppressive rule contains an explicit event include set, the
policy manager computes a finite allowlist and intersects it with the optional
CLI selection. The resulting set can reduce the programs considered for
loading. An open-ended policy rule cannot safely produce such an allowlist, so
the broader user selection is retained. A disjoint exact policy and CLI scope
is rejected during startup rather than being misinterpreted as the empty
selection that means ``all events'' to the probe selector.

Detector files are likewise parsed and validated before instances are created.
Policies may select detector definitions by identifier or metadata, including
severity, tags, statefulness and \gls{attack} tactic or technique identifiers.
This is a bootstrap operation: definitions outside the selected catalogue do
not create detector instances or retain collective state. Detector selection
does not, however, expand the eBPF event plan. A detector whose inputs are
outside a general CLI selection will receive no such event; policy-selected
detectors are checked against the selecting policy's event scope.

The probe registry translates the selected logical event names into physical
programs, hooks and attachment kinds. A public logical event may require
several producers, for example different syscall variants, while an internal
support program may be attached only because another event requires it. The
logical set remains the user-facing selection and admission domain; the
physical slice controls autoload and attachment. Listing~\ref{lst:probe-plan}
shows the dependency expansion used to build the latter.

\begin{lstlisting}[
    language=Go,
    caption={Physical probe-plan construction from selected logical events (abridged).},
    label={lst:probe-plan}
]
selectedProbes := make([]Spec, 0, len(supportedProbes))
for _, probe := range supportedProbes {
    if _, ok := probeActivation[probe.eventName]; ok {
        selectedProbes = append(selectedProbes, probe)
        continue
    }
    for _, trigger := range probe.impliedBy {
        if _, ok := probeActivation[trigger]; ok {
            selectedProbes = append(selectedProbes, probe)
            break
        }
    }
}
\end{lstlisting}

The first branch retains a producer directly selected by its logical event. The
second retains a support program when one of its triggering events is active.
Consequently, internal dependencies are available to the kernel-side
implementation without becoming CLI-visible events or independent decoder
schemas. Cross-registry tests exercise the public event set, dependency
expansion and the many-to-one relation between physical programs and logical
events. They are intended to detect interface drift; they do not establish the
availability of every attachment on a particular target kernel.

Before the module is loaded, the runtime disables autoload for unselected
programs represented in the registry. This ordering means that relocation,
verification and loading apply only to the selected registered subset and its
dependencies. The qualification is important: the registry controls registered
program names; it is not an object-wide discovery mechanism for every program
that might be present in the compiled eBPF object.

After loading, the runtime updates the singleton configuration map used by the
optional exact effective-UID filter described in Chapter~4. It then creates one
libbpfgo perf reader for the \texttt{events} map, with separate channels for
records and reported losses, and attaches each selected program through the
registry's attachment route. Raw tracepoints, typed tracepoints, kprobes,
kretprobes and the conditionally required cgroup attachment each use an
explicit libbpfgo operation. The runtime retains every returned link.

Resource ownership is centralised in the runtime object. A signal-derived
context stops the event loop cooperatively, while a deferred cleanup routine
destroys links in reverse attachment order, releases only a cgroup-v2 mount
created by the runtime, closes the perf reader and closes the module. Setup
and attachment failures abort initialisation. By contrast, record-local
decoding, detector and presentation failures are reported during the active
loop and do not terminate later event processing. Cleanup errors are joined
with an existing runtime error and reported through the diagnostic logger. The
current tests strongly cover selection and configuration behaviour, whereas
object-backed tests for partial initialisation, attachment and cancellation
remain a limitation.

\section{User-Space Decoder and Event Registry}
\label{sec:implementation-decoder-registry}

The perf reader delivers byte slices rather than self-describing event objects.
The decoder is therefore the normalisation boundary for host events. It reads
the fixed 136-byte common context using explicit little-endian offsets, obtains
the declared argument count, resolves the numeric event identifier, and returns
one typed \texttt{bufferdecoder.Event}. This representation contains the
context, the public logical-event name and the decoded arguments; it is the
same representation later used by policy matching and detector dispatch.

Explicit offset decoding avoids relying on Go structure padding. It also makes
the cross-language contract visible: the field order, widths and total size
must remain aligned with the C definition discussed in
Section~\ref{sec:implementation-binary-contract}. The implementation does not
generate this contract from one source or enforce it with a compile-time C/Go
layout assertion, so changes to either side still require review and tests.

Argument interpretation is schema directed. The wire stream contains an index
followed by a payload, but no independent type tag. The event registry maps the
event identifier to a public name and ordered argument specification; the index
then determines the expected name and decoding type. Listing~\ref{lst:schema-decoding}
shows the central part of this procedure.

\begin{lstlisting}[
    language=Go,
    caption={Schema-directed decoding of indexed arguments (abridged).},
    label={lst:schema-decoding}
]
spec, ok := events.GetSpec(eventID)
if !ok {
    return decodeUnknownArguments(rawArgs, eventID, argnum)
}
for seen := 0; seen < argnum && offset < len(rawArgs); seen++ {
    index := int(rawArgs[offset])
    offset++
    if index >= len(spec.Args) {
        return nil, fmt.Errorf("argument index %d out of range", index)
    }
    argSpec := spec.Args[index]
    value, consumed, err := decodeArgRecord(rawArgs[offset:], argSpec.DecodeAs)
    if err != nil {
        return nil, err
    }
    offset += consumed
    decoded[index] = Argument{Name: argSpec.Name, Type: argSpec.DecodeAs, Value: value}
}
\end{lstlisting}

Fixed-width scalar values, length-prefixed strings and byte sequences, bounded
string arrays, compact argument arrays, credentials and socket-address records
use dedicated payload decoders. Strings have terminal NUL bytes removed and
must be valid UTF-8. Missing arguments are intentional: an eBPF producer may
be unable to collect one field while preserving the schema indexes of fields
that follow it. The decoder finally emits present arguments in schema order,
rather than in their incidental order in the delivered record.

Two registries divide responsibility. The event registry is authoritative for
the user-space public event identifiers, names and argument schemas. The probe
registry is authoritative for which physical programs can be selected and
attached. Several probes can converge on one schema, and internal support
probes need not define a public decoded event. Cross-registry tests are used to
detect drift between these domains, while retaining this separation of decoding
and attachment concerns.

Malformed records and transport loss are distinct. A loss notification means
that no record bytes were retained by the perf buffer; a decode error means
that bytes reached user space but could not be safely interpreted. Both are
diagnosed without converting the condition into a monitored event, and later
records continue through the loop.

\section{User-Space Event Selection and Admission}
\label{sec:userspace-event-selection}

After decoding, the runtime applies three short-circuit admission gates. The
first checks whether the decoded logical name belongs to the selected event
set. The second applies an optional exact command-name filter. The third asks
the policy manager whether the event is selected by the active policy set. A
policy evaluates its common scope and then its rules; matching suppress rules
override monitor or detect rules. With no configured policies, this final gate
is permissive.

Listing~\ref{lst:event-admission} shows the admission order and the resulting
fan-out. Diagnostics and optional socket enrichment are omitted because they
do not change the host-event admission contract.

\begin{lstlisting}[
    language=Go,
    caption={Decoded-event admission and consumer fan-out (abridged).},
    label={lst:event-admission}
]
event, err := bufferdecoder.DecodeEvent(raw)
if err != nil {
    return
}
if !p.eventEnabled(event.EventName) {
    return
}
if !p.commEnabled(event.Context.CommString()) {
    return
}
if !p.policyEnabled(event) {
    return
}
if !p.cfg.Alerts.Only {
    if err := p.printer.Print(event); err != nil {
        p.logger.Error("print event", zap.Error(err))
    }
}
p.processDetectors(ctx, event)
\end{lstlisting}

An admission failure prevents both normalised-event presentation and detector
evaluation. The \texttt{alerts-only} option has a narrower role: it suppresses
only normalised-event presentation after admission. It does not bypass policy
matching, disable detector processing or suppress alert presentation. This
keeps collection and analytical semantics independent from whether an operator
wants to see the ordinary event stream.

The policy manager is intentionally not a detector. Policies decide which
observations are relevant to a scenario through event, command, UID and
argument constraints; detectors decide whether one admitted event or a short
sequence produces an alert. The current policy modes record monitor, detect or
suppress intent, but monitor and detect matches share the same admission path.
Suppression is the only mode that removes a matching event from subsequent
consumers.

The active loop distinguishes valid rejections from failures. At debug level,
only the first few filter drops are logged in order to avoid unbounded
diagnostic output. Decode errors, detector errors and rendering errors are
logged separately, while the loop remains active. This behaviour is established
by code inspection and component tests; a direct end-to-end unit test for the
complete admission order is still absent.

\section{Policy and Detector Engine}
\label{sec:implementation-policy-detector}

\subsection{YAML Policy and Detector Definitions}
\label{subsec:implementation-yaml-definitions}

Policies and detectors enter the runtime through separate YAML models. A policy
contains a name, mode, intent, common scope and one or more rules. Empty policy
mode and intent default to \texttt{monitor} and \texttt{threat\_hunting}; an
event selector with no include list means all events except explicit exclusions.
Rules compose as alternatives within a policy, whereas the fields of one rule
compose as constraints. A suppress policy may not select detectors.

Detector documents provide stable identity and descriptive metadata together
with consumed events, conditions, optional ordered steps, output information,
and optional ATT\&CK metadata. The loader reads explicit files or the YAML
files in supplied directories in deterministic lexical order, validates known
event names, and compiles conditions, numeric constants, event sets and
correlation plans before event processing begins. The current YAML decoder is
not strict about unknown fields; a spelling error can therefore be ignored by
the external parser rather than becoming a schema error. This is an
implementation limitation rather than a feature of the rule language.

Policy metadata can reduce the loaded detector catalogue using identifiers,
severity, tags, statefulness, tactics and techniques. Values within one
criterion have alternative semantics, while populated criteria are conjunctive.
Selections from separate policies are combined. The complete detector catalogue
is parsed before this selection, so an invalid unselected definition can still
fail startup. The selection check currently uses the broad event-name set of a
definition, including optional requirements; Chapter~6 should evaluate the
practical consequences of this conservative choice rather than treating it as
a claim of detection coverage.

\subsection{Point and Collective Detection}
\label{subsec:implementation-point-collective}

The detector engine creates a validated registry and an event-name dispatch
index once at bootstrap. The index prevents each decoded event from being
offered to the entire catalogue. Listing~\ref{lst:detector-dispatch} shows the
event-time dispatch loop. It invokes only candidates for the current event and
keeps one detector failure from preventing the remaining candidates from
running.

\begin{lstlisting}[
    language=Go,
    caption={Event-indexed detector dispatch with isolated errors.},
    label={lst:detector-dispatch}
]
for _, detector := range detectors {
    result.Invoked++
    alerts, err := detector.OnEvent(ctx, event)
    if err != nil {
        result.Errors = append(result.Errors, DetectorError{
            DetectorID: detector.Definition().ID,
            Err:        err,
        })
        continue
    }
    if len(alerts) > 0 {
        result.Alerts = append(result.Alerts, alerts...)
    }
}
\end{lstlisting}

A point detector applies its compiled top-level conditions to one admitted
event. If it declares steps, the event must also match a step and its step
conditions. A successful point match immediately creates an alert containing
that source event. Conditions support equality, inequality, containment,
membership, prefix and suffix tests, existence tests, and numeric comparisons.
The implementation therefore performs deterministic rule evaluation; it does
not train on observed activity or calculate an anomaly score.

A collective detector is a stateful detector with more than one ordered step.
It first applies its global conditions, derives local correlation keys, and
attempts to advance the next expected step of a partial sequence. Completion
creates an alert containing the ordered evidence. An event that matches the
first step can start or replace the partial sequence for its key. Events need
not be contiguous in the complete input stream, but they are considered in the
arrival order delivered to the runtime. The engine does not reorder records or
infer cross-CPU causality.

\subsection{Local Correlation Strategies, State Bounds and Alert Deduplication}
\label{subsec:implementation-correlation-deduplication}

Correlation plans are compiled during detector construction, so the hot path
does not parse strategy names from YAML. Process correlation uses the host PID
together with task start time, preventing a reused numeric PID from joining two
process lifetimes. Process-tree correlation additionally tries the immediate
parent identity for a later event; it does not reconstruct arbitrary ancestry
or maintain a persistent process graph. Resource correlation uses the
device--inode pair in compatible event arguments, not the pathname. Cgroup
correlation uses the local kernel cgroup ID. Composite correlation concatenates
the configured dimensions and requires every component to be present and equal.
These values are local observation keys, not Kubernetes workload identities.

The unavailable \texttt{user\_session} strategy is rejected at parsing time
because normalised events do not expose a stable local session identifier. The
implementation deliberately does not approximate a session with a UID. Missing
process, resource or cgroup data yields no correlation key and therefore no
state transition; it does not fall back to a weaker identity.

Listing~\ref{lst:collective-transition} shows the core transition of a
collective detector. The omitted code constructs the initial key and stores the
first matching event; it does not alter the one-state-per-key rule.

\begin{lstlisting}[
    language=Go,
    caption={Advancing one bounded collective sequence (abridged).},
    label={lst:collective-transition}
]
for _, key := range lookupKeys {
    state, ok := d.state[key]
    if !ok {
        continue
    }
    if now.Sub(state.firstSeen) > window {
        delete(d.state, key)
        continue
    }
    matches, err := stepMatches(event, d.steps[state.nextStep])
    if err != nil {
        return nil, err
    }
    if matches {
        state.events = append(state.events, event)
        state.nextStep++
        if state.nextStep >= len(d.steps) {
            delete(d.state, key)
            return []detectors.Alert{d.newAlertFromEvents(state.events)}, nil
        }
        d.state[key] = state
        return nil, nil
    }
}
\end{lstlisting}

results. Expiry is checked for the key addressed by a relevant event and the
detector periodically prunes unrelated state while it processes qualifying
traffic. Although the engine exposes \texttt{Flush}, the production runtime
does not call it on an independent timer. Idle stale state is consequently
removed on later relevant traffic, explicit API use, or capacity pressure.

Alert deduplication is deliberately separate from collective correlation. It
operates after a detector has produced an alert, using detector identity, title,
severity and fields from the first evidence event. It suppresses repeated
equivalent keys within the configured processing-time window, but does not
represent the complete collective sequence, the correlation key or a durable
causal identity. It is therefore a presentation-noise control rather than a
second correlation mechanism.

\subsection{MITRE ATT\&CK Metadata Propagation}
\label{subsec:implementation-attack-metadata}

Detector definitions may contain a framework, version, tactics, techniques,
data sources and data components. The implementation validates the syntactic
shape of tactic and technique identifiers and copies this metadata into each
matching alert. Policies may also use tactic and technique identifiers to
select detector definitions during bootstrap. This gives alert consumers a
consistent \gls{attack} vocabulary for classifying the intended security
meaning of a detector \cite{strom2020attack}.

The local runtime does not download an ATT\&CK catalogue or validate whether a
mapping is semantically appropriate. Unmapped detectors are accepted. ATT\&CK
metadata should consequently be presented as classification and traceability
information attached to detector evidence, not as proof of detector
correctness, technique coverage or research novelty.

\section{Output and Structured Logging}
\label{sec:implementation-output-logging}

The output package is a presentation boundary, not another normalisation stage.
It adapts the decoded event into JSON or compact text and adapts a detector
alert into a user-facing record containing detector identity, severity, ordered
evidence and optional threat metadata. JSON preserves typed values and may add
readable labels, whereas compact text is intended for interactive inspection.
The event model used by output is derived from the same decoded representation
used by policies and detectors.

Normalised event output and alert output both use standard output. They are
configured independently and can therefore use different formats in one run;
the resulting stream is not guaranteed to be one homogeneous machine-readable
schema. The \texttt{alerts-only} option suppresses normalised event output but
leaves detector evaluation and alert rendering active. Point alerts expose one
source event, while collective alerts retain their ordered evidence in JSON and
render a bounded sequence in compact text.

Operational diagnostics follow a separate path. The Zap logger writes to
standard error in console or JSON form, with debug, info, warn and error
levels. It receives runtime lifecycle messages, selected libbpf diagnostics,
perf-buffer loss notifications, decoding failures, detector failures and
presentation failures \cite{uber_zap}. Zap does not serialise monitored events
or alerts. This prevents infrastructure errors from being mistaken for security
observations and allows diagnostics to change without changing the data model
seen by event and alert consumers.

boundaries. Fatal configuration and startup failures are returned to the command

Logger synchronisation errors are currently discarded, so the design does not
claim durable delivery of every diagnostic message.

\section{Containerisation and Deployment Considerations}
\label{sec:implementation-containerisation}

The container build follows a builder/runtime split. The builder stage compiles
the local libbpf dependency, eBPF object and Go executable; the runtime stage
copies the resulting executable and declares the runtime packages used by that
image. As described in Chapter~4, the eBPF object is embedded during the Go
build, so the normal executable path does not require a neighbouring object
file.

The image does not embed or copy the policy and detector YAML catalogues.
Deployments that use these inputs must supply them explicitly, for example
through a bind mount or a derived image. Similarly, BTF and the relevant kernel
facilities remain host resources. The provided Docker path uses broad host
integration and privileges sufficient for the prototype; it is not a
minimal-privilege security profile.

No Kubernetes manifest, lifecycle configuration, least-privilege capability
set or deployment validation is implemented in the repository. A future
orchestration layer may place the monitoring agent in a wider platform, but
this chapter makes no claim that such a deployment has been implemented or
evaluated.

\section{User-Space Implementation Summary}
\label{sec:user-space-implementation-summary}

The user-space implementation turns a selected perf-buffer record into a
typed event, applies explicit admission gates, and then routes admitted
evidence to presentation and deterministic detection. Policies control scope
and suppression, while detectors evaluate point conditions or bounded local
sequences and attach ATT\&CK classification metadata to their alerts. The
runtime keeps kernel-facing resource ownership, record interpretation,
analytical state and presentation responsibilities separate.

The implementation also defines clear boundaries for the following evaluation.
The registry and decoder tests establish important structural invariants, but
attachment behaviour, output under workload, alert quality, loss and resource
consumption require target-environment evidence. Chapter~6 evaluates these
behaviours on the stated Rocky Linux environment.
