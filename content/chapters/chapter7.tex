\chapter{Conclusions and Future Work}
\label{ch:conclusions-future-work}

This thesis achieved its stated objective by producing and evaluating a
node-local runtime security monitoring prototype for the selected Rocky Linux
environment. The implemented pipeline connects bounded kernel observations to
typed evidence and deterministic local detection. Its scope is defined by the
implemented event domain and by the controlled evaluation presented in
Chapter~\ref{ch:experimental-evaluation}.

\section{Summary of the Work}
\label{sec:conclusions-summary-work}

The central problem was the collection of heterogeneous process and
security-related kernel observations while keeping their interpretation outside
the collection layer. The resulting architecture assigns constrained data
extraction and optional early admission to \gls{ebpf}. The Go runtime handles
record normalisation, monitoring scope, detection and presentation. A shared
event contract allows observations produced by different physical hooks to
enter the same logical event model.

In kernel space, complementary observation points retain different stages of
an operation, including requests, security mediation, committed transitions
and returned outcomes. Direct and paired producers use a common bounded
construction framework. Selective probe planning activates the producers and
support programs required by the chosen logical events. Exact \gls{uid}
admission can reject observations before full enrichment and transport when a
suitable fixed identity is available. CO-RE, explicit layout branches and
verifier-visible bounds adapt these mechanisms to the verified Rocky Linux
kernel; the compatibility claim remains tied to that target.

In user space, schema-directed decoding converts perf-buffer records into a
typed representation shared by the subsequent components. Policies determine
the relevant event domain and suppression decisions. Detectors evaluate the
admitted evidence, either as individual events or as short ordered sequences
held in bounded local state. Alerts preserve the observations responsible for
a match and may carry \gls{attack} tactics and techniques as classification
metadata. The contribution lies in the integration of these established
mechanisms into a compact monitoring pipeline adapted to a constrained
enterprise-kernel environment.

\section{Main Results}
\label{sec:conclusions-main-results}

The functional campaign established the intended node-local observation
boundary. In the single-node Minikube testbed, the monitor, vulnerable target
and trigger ran in three separate Pods. All three exploit repetitions recovered
the synthetic flag and produced one complete alert containing the configured
four-event sequence. The three repetitions of the selected benign interaction
returned the expected application response without completing that sequence.
These runs demonstrate repeatable same-node, cross-Pod visibility and detection
for the controlled scenario. The correlation evidence covers the same-process
path exercised by the selected detector; its other process relationships were
outside the experiment.

The performance campaign measured the effect of exact UID admission under the
same workload. Across three runs, the filtered profile consumed a mean of
0.46\% of one \gls{cpu} core in the monitor-container cgroup, and every run
remained below the project's 5\% gate. The unfiltered profile recorded a mean
of 5.73\%. Using the retained measurements, filtering reduced the mean by
approximately 92.0\% while preserving flag recovery and the complete alert in
every monitored run. The metric represents CPU time charged to the monitor
cgroup as a percentage of one core and excludes kernel work charged elsewhere.
The result therefore quantifies the user-space benefit of early admission for
this scenario, without estimating total eBPF, node or system overhead.

\section{Limitations}
\label{sec:conclusions-limitations}

The implemented event surface is broader than the current level of technical
assurance. Kernel and Go representations of the event contract are maintained
separately, and their agreement relies on review and cross-registry tests. The
registry gate also exposes an unresolved classification inconsistency: an
internal socket support probe is treated as a public producer despite having no
decoder schema. Object-backed tests do not yet cover every loading, attachment,
partial-initialisation and cleanup path on the target kernel. Policy and
detector documents receive semantic validation, although the YAML decoder still
accepts unknown fields. Collective sequence state has explicit bounds; some
maintenance and alert-deduplication behaviour continues to depend on subsequent
traffic and has weaker capacity guarantees.

The analytical and operational scope remains local. Detection follows
deterministic configuration rules, with no learned behavioural baseline or
persistent process and cluster graphs. Correlation keys identify local
processes, resources and cgroups. The prototype records and reports activity;
enforcement is outside its implemented functions.

The evaluation covered one enterprise kernel, one two-core Minikube node, one
vulnerable workload and one scenario-specific collective detector, with three
repetitions per condition. The evidence supports the engineering claims made
for this controlled environment. Broader portability, production readiness,
loss-free delivery and statistical detection quality require experiments with
more kernels, workloads, detector sets and event rates.

\section{Future Work}
\label{sec:conclusions-future-work}

Future development should increase the operational capacity of the prototype
while preserving bounded kernel collection and configurable user-space
analysis. Five areas have immediate value: scalability, performance, broader
low-level filtering, additional host-level hooks and richer fields for the
existing event catalogue.

Scalability concerns both the capacity of one agent and its use across several
nodes. A local instance must remain responsive as event rates, monitored
processes, policies and active detectors increase. Longer stress campaigns and
progressively larger detector catalogues can establish these limits. For a
multi-node deployment, each agent can retain responsibility for local
collection and correlation while exporting versioned events and alerts to an
external storage or analysis platform. This arrangement keeps distributed
state outside the kernel-facing runtime and gives cluster-level processing a
clear interface.

Performance analysis should separate the cost of kernel execution, event
transport, decoding, policy evaluation, detector processing and output
rendering. Per-probe and per-event counters would expose the observation points
that generate the greatest load. Workloads with known event volumes could then
measure sustained throughput, perf-buffer loss and the effect of buffer sizing.
The resulting profiles would guide work on transport, memory allocation and
detector state according to measured bottlenecks.

Low-level filtering currently provides exact UID admission, which is effective
when the relevant identity is known in advance. Additional bounded selectors
could cover host process and group identifiers, command names, cgroup
identifiers, namespace identifiers and selected event-specific values. The
control plane could compile eligible policy constraints into kernel map entries
and update them during execution. Expressive predicates and detector logic
would continue to run in user space, preserving flexibility and keeping the
collector acceptable to the verifier.

The host event domain can grow through hooks selected from concrete detection
and investigation requirements. Candidate areas include additional file
modification outcomes, kernel key management, process-isolation changes and
other interfaces capable of altering host behaviour. Every new logical event
must state the kernel stage it observes and preserve the distinction between a
request, a mediation point, a committed transition and a returned outcome.
Support for the required hook and payload extraction must be established on the
target enterprise kernels before public exposure.

The existing hooks can also provide more precise evidence. Useful additions
include return information for operations currently observed only at entry,
richer capability-check context, stable parent identity and more complete
requested-versus-resolved resource details. Such fields can help a security
analyst distinguish operations that currently produce similar records and can
reduce ambiguity in detector conditions. Each enrichment should have a clear
investigative purpose and a bounded collection cost.

New filters, hooks and fields all affect the shared event contract and decoder
schema. Their implementation should include registry checks, decoder fixtures,
target-kernel attachment tests and workload-based measurements. This validation
keeps extensions traceable from the kernel observation point to the evidence
presented to the analyst.
